# 文件生命周期锁与清理扫描：取证及边界

T4测试中，小队列在低于先前饱和完成率的固定到达负载下仍出现拒绝。对照数据：Q10/Q25/Q50在约9.23请求/秒下分别拒绝41/31/20次，拒绝集中于窗口约30秒附近，Q10另在90秒附近出现。Q100同到达率无拒绝，但等待P95约5.24秒、队列峰值76。此处只是阶段数据，不是最终参数推荐。

源码显示，所有执行器主循环周期调用`cleanup_orphans()`；它在整个目录扫描及逐文件数据库核对期间持有共享文件生命周期独占锁。`cleanup_batch_size`只限制删除数，合法文件越多、删除数一直为0时，仍会遍历全部旧文件。结果提交和上传也要获得该锁，因此扫描具有潜在的O(执行器数×旧文件数)重复工作及写入竞争。不能简单取消锁，否则会破坏文件/元数据提交、配额和删除的正确性。

## 正式环境只读取证

一次70秒有限采样（无新增常驻collector、无worker SSH轮询）：324个样本，14次观察到孤立文件核对查询，最多11个推理已完成但结果尚待提交的任务，最长观测等待0.964秒，UNKNOWN=0。见[只读诊断](artifact-lock-readonly-diagnostic.json)。

这些观察与周期维护开销相吻合，但不能据此认定所有拒绝均由GC造成。固定输入按20张DocLayNet、20张RCTW顺序循环，输入耗时变化、并发推理及其他开销也需区分。另一项排队样本分析未观察到“队列达到有效槽位数、运行数却不足一半”的样本；不把问题简单归因为执行器完全不领取。

## 独立环境受控对照

专用PostgreSQL、临时本地文件、模拟鉴权、无GPU推理，仅验证清理/锁行为，不是正式服务容量实验：

| 项目 | 实测 |
|---|---:|
| 已登记有效旧文件 | 3,000 |
| cleanup_batch_size | 200 |
| 数据库存在性核对 | 3,000次 |
| 删除孤立文件 | 0 |
| GC耗时 | 0.169秒 |
| 无GC上传 | 8.3ms |
| GC并发时上传 | 174.3ms |

见[独立对照](artifact-gc-controlled-characterization.json)。它确认了扫描工作量未按删除批次限制，以及锁对并发写入的阻塞；未直接量化当前正式拒绝的因果占比，不能把本表外推成某数据量的正式吞吐。
