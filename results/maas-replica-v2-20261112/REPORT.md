# MaaS 规模调节器新版实现与只读验证

2026-11-12 · [验证数据](validation.json) · [Issue #39](https://github.com/WTaoGitHub/cybercafe-maas/issues/39)

## 已完成什么

R1—R3 的候选代码已实现：显式 v2 策略、结构化阻塞原因、完整现状持续对账、周期兜底、持久接管与人工漂移保护、可选压力模式、串行安全写入和显式有界并行启动。旧 schema v1 不自动迁移。

新节点无需依赖旧节点的 SSH 压力样本才能开始规划；上线事件过去 600 秒后仍按当前权威状态重算。明确无数据源可使用 disabled；advisory 缺样经过持久宽限后按保守预算执行；required 保持严格等待。有效高压不绕过。

未就绪实例已分配 GPU 时，先保留整张卡的剩余预算，再利用其他可证明空闲的卡。引擎启动可以重叠，模型 PUT 始终单写入方逐笔 +1。目标读回确认和持久回执先完成，再清理 PendingWrite；超时结果不确定时不重发。未分配/记录不齐/异常落点仍保守等待。

稳定期到期和写入确认后及时重算，避免多等一个完整 30 秒周期。原生事件仍用于加速，管理 API 故障则冻结。

## 实际发现并修复的问题

初次真实 Observe 将普通 Running 实例标记为 placement_unsettled。原因是 GPUStack 返回了默认 distributed_servers 对象，虽然对象非空，但 subordinate_workers 为 null；首版把“对象存在”误当成“确实跨 worker 部署”。

已改为检查固定版本字段和实际从属清单：null/空清单按单卡处理；存在真实从属或未知字段继续保守阻止。补回归后，第二次真实对照可规划 1→2，但因尚未接管而没有写入。这也证明不能只用简化夹具代替真实字段核对。

固定 runtime 补验过程中，首次源码打包超过 SSH 参数长度，缩小包后发现运行容器使用镜像摘要，无法凭镜像标签识别。两轮有界调整后以已核验容器完成测试；未因此重建、安装或重启服务。

## 尚未完成及接续顺序

1. R4：独立 OCR 部署实写，按当前实际目标显式接管；先上限 1 验证无新事件 0→1，原人工作用中的模型保持不动。
2. R4：验证压力三模式、API/采样故障恢复、人工接管和未知写入保护；不可在现网人为制造模糊写入后自动清日志。
3. R4：资源允许时比较串行/并行 2/4，分别记录冷热缓存、首副本可服务时间、目标容量就绪时间及原服务影响。未知缓存不标记为冷/热。
4. R4：核对实际 Running、Higress 路由、OCR 和 MaaS 异步结果及唯一计量；当前 schema/只读对照不能替代这些业务验收。
5. R5：采用试点实测预算，备份原材料后先 Observe，再受控 Apply，更新常驻镜像、配置和监控。可选动态压力适配独立后续推进。

逐部署人工接管隔离尚未实现，当前任一受管部署人工漂移会冻结整个接管范围；它与“某个模型启动慢时其他模型可继续启动”不同。未知写入仍冻结所有新增。并行参数目前是受控选项，没有全局最优、真实启动耗时或生产 SLA 结论。
