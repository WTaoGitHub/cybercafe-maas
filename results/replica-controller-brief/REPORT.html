GPU 上线驱动的模型部署

第一阶段采用 GPUStack Server 内插件。现有独立进程试点已验证真实 worker 恢复触发扩容，以及三个测试路由的真实 OCR。

01　业务目标与决策规则

系统监听资源相关事件，结合触发事件与可配置的策略决定如何调整模型服务规模，并执行决策。第一阶段处理 GPU 上线和下线，执行动作包括扩大和缩小副本数，目标副本数可以降到 0。

策略面向多个模型。各模型的目标比例权重和优先级均支持预设及运行期间修改。资源允许时先保障各模型至少一个可用实例，再按配置权重分配额外容量。资源不足以同时保底时，按优先级决定先保障哪些服务。

A、B、C 以及 2:3:5 是试点示例。资源减少时，当前试点只输出缩容建议，由人工确认。插件阶段按预设策略自动缩容。默认只缩额外副本，显式授权后才可自动归零，归零保留部署与路由。该执行链路与运行中更新策略尚待实现和验收。

02　第一阶段方案 · GPUStack Server 内插件

  1. 装载与故障隔离。 将插件 wheel 安装进 Server 镜像，以 gpustack.plugins 注册。后台任务直接订阅内部 worker 事件，通过限时对账和退避处理故障。首版只允许单 Server、单写者执行。
  2. 事件与策略。 比较完整快照中的可调度 GPU 集合，以设备变化触发计算。断线或清单不完整时暂停写入。模型清单、权重和优先级采用版本化配置，校验后在运行中生效。配置换版或容量变化时重新计算，撤销过期计划。
  3. 规划和执行。 以逐卡预算、模型适配条件和副本上限做有界整数规划。先保底，再逼近配置比例。扩容可自动下发。缩容按预设规则自动下发。GPUStack 实际移除实例后，核对逐卡显存再补位。GPUStack 保留实例落点和缩容对象的最终选择权。

批量上线的压力控制。 插件将目标规模和启动节奏分开。按全局及集群预算分批启动，优先恢复各服务保底，并把 GPUStack 已有待启动实例计入压力。镜像仓库、网络、磁盘或在线推理承压时降低新增速度，恢复稳定后再放行。实际拉取的硬上限由分发链路配合实施。实施顺序为只读插件、通用策略、启动预算、隔离实写、压力反馈和接替验收。上线阈值以冷缓存和热缓存压测确定。

03　如何预设和维护策略

先设置基础策略。 按 GPUStack 部署 ID 列出受管模型，为每个部署填写副本权重、保底优先级、副本上下限和已验证的单副本显存。权重 2、3、5 表示目标总副本比例 2:3:5。优先级数值越小，资源不足时越优先保留或恢复首个可用实例。另设 auto_scale_down_min_replicas，默认 1，显式设为 0 才允许自动归零。

触发事件示例配置执行效果
普通上线沿用基础策略先补保底，再按权重分配余量。
批量上线每批最多新增 1 个副本维持目标比例，分批释放启动压力。
批量下线将关键模型的保底优先级设为 1，其他模型设为 2卡不足时优先保住关键服务。缩容按各模型预设下限执行。

事件策略只覆盖明示的字段。每次切换事件类型都重新从基础策略计算，未设置覆盖的字段继承基础值。

运行中维护。 运维以更高版本号发布策略配置。插件校验通过后热更新并重新对账，旧版本尚未提交的计划失效。校验失败时保留当前版本。回退时用新版本号发布旧配置内容。移出受管清单只解除插件管理；若要停止服务，显式将副本上下限和自动缩容下限均设为 0。

04　已验证的独立进程试点

worker 上报 → GPUStack Server 推送状态 → 控制器重新读取集群 → 计算副本目标 → GPUStack 放置与启动 → 核对运行状态

  1. 监听与对账。 控制器订阅 Server 的 GET /v2/workers?cluster_id=…&watch=true。事件唤醒全量对账，同时约每 10 秒主动对账。事件只触发重算，重复事件不会直接累加副本。
  2. 筛选并计算逐卡预算。 纳入 ready、可达、未维护且符合共同选择器的节点。每卡预算等于总显存减去 Server 汇总的已分配额度和系统保留。以 worker ID 关联注册记录，以 GPU UUID 去重。多个合格记录同时报告同一 UUID 时暂停扩容。
  3. 枚举整数方案。 在当前目标副本到各模型上限之间枚举候选。将新增实例按显存需求从大到小尝试放到各卡，递归扣减余量，判断组合是否可放置。先按优先级比较保底覆盖；全保底可行后，先最大化可放置副本数，再最小化与加权比例的偏差。现有落点会限制后续选择。
  4. 有界写入。 默认只读。显式启用写入时，复核绑定及目标模型配置，一次只给一个部署增加一个副本。已配置实例未全部在合格节点进入 running 时等待收敛。GPUStack 决定实际落点，下一轮读取结果再规划。试点限定三个部署、最多两台单 GPU worker。

06　旧宿主回收与新克隆接替

项目术语。 VPC、VM、宿主机、克隆机均指由网吧管理员管理、从特定镜像版本克隆创建的虚拟计算机。GPUStack worker 运行在该虚拟计算机上。

新克隆从干净母版首次注册，获得新的 worker ID。GPU UUID 只用于设备关联和去重。新卡可以有不同 UUID，接替容量取决于显存额度、选择器和后端兼容性。

验收顺序为记录旧节点与实例基线、排空受影响流量、观察旧节点退出容量池、确认新 ID 进入 ready、核对新卡上的实际实例落点并发起真实 OCR。前后容量相同时，目标副本数可以保持不变。过渡期若只有一张 16 GiB 卡，按已验证的声明预算按四副本规划。保留旧记录以观察交接，并遵守两台受保护 VM 的操作约束。
