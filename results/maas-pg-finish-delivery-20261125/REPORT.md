# PostgreSQL 结束回执与 PP 容器替换验证

2026-11-25 在测试环境的 worker 32 上用真实 GPU 运行 PP-OCRv4。使用该机已缓存的 PP 推理镜像，挂入提交 `f98637b` 的执行守卫，核对 GPU 进程证明及三个 OCR 阶段的 CUDA provider。测试控制端使用与现场 API 相同的镜像运行结束回调，独立 PostgreSQL 16 容器使用与现场数据库相同的镜像。四笔异步派发使用隔离凭据和预置的任务、活动、授权范围及容量记录。该实验从 GPU 获权测到终态登记，未经过外部用户网关。

| 注入条件 | GPU 端与数据库读回 |
| --- | --- |
| MaaS 已返回 204，代理从独立 PG 连接读到提交，然后关闭 TLS 连接 | 原活动为 `COMPLETED`。代理只收到一次结束回调，推理接口返回 HTTP 500。已登记 [CAPACITY-INC-011](https://github.com/WTaoGitHub/cybercafe-maas/issues/84)。 |
| 在相同提交位置，代理向 GPU 返回 HTTP 503 | 守卫重发原结束回调并收到 204。两次读取的 `gpu_finished_at` 相同，推理接口返回 HTTP 200 和 24 行 OCR 结果。 |
| 引擎已结束，关闭隔离的回调服务，宿主机保留签名回执 | 两次结束回调均遇到上游不可达。删除原 PP 容器、恢复回调服务，再启动带同一宿主机目录的新容器。32 秒内自动补报为 0，PG 活动仍为 `UNKNOWN`。 |
| 相同故障，使用当前无回执目录的配置 | 原容器退出后找不到该次签名回执。新容器启动后观察 32 秒，结束回调新增 0，PG 仍为 `UNKNOWN`，成功计量为 0。 |

后两组由测试夹具在确认原进程已获权、两次结束回调均未提交后，将测试任务置为失败、活动置为 `UNKNOWN`，用来单独验证故障后的结清路径。容器替换前后进程标识不同。带宿主机目录的一组又验证了两次身份检查。用替换进程自己的身份上报原任务，MaaS 返回 409。用测试工具在 worker 侧读取、校验并重送**原进程的签名事件**，MaaS 返回 204，原活动变为 `COMPLETED`。再次重送后结束时间相同，客户任务仍为 `FAILED`，成功计量为 0。测试工具承担了这次补报，当前运行版本尚无跨进程自动补报器。

对于同一台 VPC 上的容器替换，worker 本地持久目录加原回执补报可以结清活动。MaaS 通过现有 HTTPS 回调提交到 PG，本轮没有给控制端挂载 worker 文件系统。整台无盘 VPC 被回收后的恢复仍取决于证据是否已经写到节点之外，本轮未做整机回收。

## 修复后复验

同日在测试 worker 32 上重新运行隔离的 PP-OCRv4、HTTPS 回调服务和 PostgreSQL 16。沿用该节点的缓存模型镜像，注入修复后的执行守卫。对两笔请求分别在确认 PG 已提交后断开 TLS、返回 HTTP 503。两种情况下均观察到一次启动授权、两次结束回调、同一个数据库结束时间，推理接口均返回 HTTP 200 和 24 行 OCR 结果。

第三笔请求在引擎结束时关闭隔离回调服务。两次回调都收到 503，本机留下签名回执。夹具将客户任务标记为失败，将后端活动置为 `UNKNOWN`。删除原推理容器后，启动挂载同一宿主机目录的替换容器并恢复回调服务。以替换进程身份上报返回 409。随后启用隔离的宿主机 systemd 定时器，调用实际的 `maas_bootstrap.receipt_replay`，读取测试签名配置和按卡凭据。从启动定时器到读回 PostgreSQL 并确认文件已删除，上界为 **8.3 秒**。回调携带原进程身份并取得 204，活动为 `COMPLETED`，客户任务为 `FAILED`，该任务的成功计量记录为 0。

此次 GPU 复验使用临时定时器、宿主机目录和独立数据库。镜像构建、签名策略及挂载选取另有自动化回归。测试范围为同一台 VPC 上的推理容器替换，常驻副本和母版沿用原发布版本。

## 当前测试环境常驻部署

2026-11-25 将 `cfde6d4` 部署到本轮三台在线 worker。签名配置为 `tower-e5-receipts-v4` / `e5-local-receipts-cfde6d4`。配置服务、MaaS 准入策略和 GPUStack 的三个模型后端已切换。三个服务都使用由原镜像追加同一执行守卫文件得到的固定摘要。

| 模型 | 注册表摘要前 12 位 | worker 31 | worker 32 | worker 34 |
| --- | --- | ---: | ---: | ---: |
| PP-OCRv4 | `f4a2a7f902e2` | 1 | 2 | 2 |
| OvisOCR3 | `3dec3e28378e` | 0 | 1 | 1 |
| Unlimited-OCR-2 | `4e2efffc9873` | 1 | 0 | 0 |

三台都通过原 GPU UUID 和 worker 编号完成正式接续。首台复用已消费的启动许可时收到 403，随后在旧管理进程退出、心跳过期后，由配置服务核对并签发新会话。后两台直接使用该流程。每台都复核了新会话的原生 Ready 状态以及重复执行 bootstrap 的 `UNCHANGED`。全程没有重启 VM。

在准入策略切换时先核对没有在途派发，通过系统现有的零容量切换保留历史隔离，再替换旧实例。更新模型版本后 GPUStack 仍保留原实例，验收按实际容器逐个核对镜像摘要、守卫代码 SHA-256、只读凭据挂载和可写回执目录。滚动期间一次 PP 探针在 GPU 获权前关闭。另有一笔 Unlimited 副本调度因剩余可分配显存不足而等待，将一个 PP 副本移回 worker 34 后恢复。临时调度选择器已还原为空。最终 8 个副本全部 Ready，全局额度 8、异步上限 6、同步预留 2，API 与执行器均读到新鲜预算。之前的 1 笔历史同步 `UNKNOWN` 仍由 GPU 隔离覆盖，单独计入健康并发占用为 0。

三个模型分别通过实际 MaaS API 提交一笔异步任务，均一次成功、有原 GPU 终态和一次成功计量，结果文件均返回 HTTP 200。另通过正式同步推理处理程序运行 PP，返回 HTTP 200 和 2 行识别结果。测试只为该次已知 token 留存了引擎真正写出的原签名文件，常规回调完成后将同一文件放回 worker 31 的目录。常驻定时器在 4.6 秒内确认并删除文件。数据库的 GPU 结束时间和一次成功计量保持原值。这次核对的是正式链路上的幂等补报，真实断连和容器替换的结果见上节。

已清理三笔异步任务、两笔同步验证记录、验证计量、输入及结果文件、临时许可和回执观察目录。控制端保留发布清单与停机的上一版配置服务供回退，worker 保留私有的接续记录与旧注册数据。旧启动许可只能消费一次，回退运行中的 worker 时也要走正式接续。

旧快照已发布兼容配置 `e5-nfs-guard-compatible-cfde6d4`，可识别三个新版模型的守卫和资源规则。三台 worker 发布完成时，共享 VPC 母版仍为 v3。当日后续的母版更新见下节。从既有 v3 快照新建的 worker 需要安装新版客户端并选用 v4 配置，才能启用本机自动补报。

在受控运维终端取已发布 `gpu-ocr/execution_guard.py` 的 SHA-256，在每台目标宿主机以 Docker 运维权限运行只读核验脚本。将输出的各模型计数与 GPUStack 的 Ready 副本数对照。脚本按签名运行配置检查本机实际容器、挂载和定时器。[常驻部署核验脚本](../../scripts/maas/runtime/verify_worker_receipts.py)

```sh
PYTHONPATH=/opt/maas/lib python3 -B verify_worker_receipts.py --guard-sha256 "$GUARD_SHA256"
```

## Tower 母版更新与快照交接

2026-11-25 经受信 SSH 主机密钥核对后，在 Tower 安装测试 worker 已用的 `cfde6d4` 回执组件。本机配置和安装清单的逻辑镜像标识均从 `tower-e5-nfs-signed-v3` 切换到 `tower-e5-receipts-v4`。修改前已在运维机私有目录保存并校验 11 个目标路径的原始内容或缺失状态，供逐文件回退。

| 检查项 | 母版实测 |
|---|---|
| 安装与清单 | 安装 8 个组件，含客户端、回执读写和投递模块，以及 systemd 服务和定时器。重新连接后，30 个清单文件的 SHA-256 全部匹配。原有启动程序及服务的摘要按实际已部署版本核对并登记。 |
| 签名配置 | 在 Tower 通过 HTTPS 获取并验签 `e5-local-receipts-cfde6d4`，核对 PP-OCRv4、OvisOCR3、Unlimited-OCR-2 三条镜像、入口及回执 UID 规则。按 v3 标识读取并验签旧兼容发布也成功。 |
| 定时器 | `maas-worker-receipts.timer` 和 service 均已加载，开机启用链接指向正式 timer。母版上的 timer 为 `enabled/inactive`。直接运行正式补报入口，在没有 worker 身份及回执的情况下正常退出。 |
| 母版保护 | `boot-check` 返回 `PROTECTED_HOST_WORKER_FORBIDDEN`。已有的 worker 启动服务保留原失败状态，其日志记录了母版保护等待超时。核对容器数为 0，无启动许可、GPU 注册身份或模型 NFS 挂载。主机启动标识和 Docker 主进程与备份时一致。 |

**平台交接。** 母版文件已就绪。管理员可将当前 Tower 保存为新快照，记录平台快照 ID，再从该快照启动一台独立测试 VPC。首启时核对实际 image ID、签名 revision、GPU UUID 注册及 Ready 状态，确认补报 timer 为 `enabled/active`。有真实副本后核对回执挂载，通过 MaaS 提交一笔隔离任务，对照原 GPU 终态及唯一成功计量。本次没有保存平台快照，也没有验证新克隆首启。[逐副本核验与验收](../../docs/handbooks/OPERATIONS.md#134-创建-gpustack-部署并核对真实副本)

## 回归入口

将 `MAAS_TEST_DATABASE_URL` 指向名称以 `_test` 结尾的独立 UTF-8 PostgreSQL 测试库，夹具会重建该库的 schema。从仓库根目录运行以下命令。

```sh
PYTHONPATH=.:plugins/gpustack-replica python -m pytest -q -rx tests/maas/test_pg_finish_delivery.py
```

上述现场结果对应 `f98637b`。后续修复 `2efe254` 将 TLS 提交确认丢失纳入正常回归断言。worker 本机补报回归使用签名配置、独立进程、回环 TLS 和 PostgreSQL，核对回调服务不可用时保留文件、丢失提交确认后的幂等重投，以及收到 204 后的清理。无回执对照组保留未知状态。
