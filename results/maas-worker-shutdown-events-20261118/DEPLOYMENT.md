# worker 关机事件现场部署

2026-11-18 · [Issue #2](https://github.com/WTaoGitHub/cybercafe-maas/issues/2)

MaaS 接收端、无盘 Bootstrap 签发端和 tower 母版客户端已部署。母版上的通知单元已配置开机启用，当前为 inactive。平台快照保存、应用和克隆首启尚未验证。实现及本地测试见[交付报告](REPORT.md)。

| 无盘 Bootstrap | 基于运行中的 `48ff46a` 更新签发逻辑，沿用原运行镜像、发布、授权状态和 TLS 挂载。新容器健康，由服务 UID 读取专用 0600 文件并签发事件凭据。旧容器停放供回退。 |

现场合成验证由 Bootstrap 服务 UID 签发临时凭据，经母版 SSH 转发的 TCP 通道连接私有 TLS 入口。请求在运维端加密，凭据未写入母版。两次新 UUID 返回 201，相同 UUID 再报返回 409。数据库核对两条记录各有 48 小时保留期，随后按合成事件的 ID 和范围删除这两条记录，关闭临时转发。该验证调用签发 helper，真实克隆启动自动领证流程仍待首启验证。

曾按初始母版端口连接失败。使用用户更新的入口后，通过已信任的主机公钥验证身份并继续。首次合成探针在宿主 root 下读取由服务 UID 持有的私有文件，被现有权限检查拒绝。改用实际 Bootstrap 进程的 UID 后通过，未更改密钥权限。

回退材料保存在部署主机的私有目录，包括原 Nginx 配置、API Compose 恢复配置、数据库 schema 和母版原文件。需要停用时先关闭客户端通知和 HTTPS 入口，再移除可选签发与接收配置，保留事件表和清理任务直至记录过期。API 回退到旧镜像时，用本次候选的清理命令补齐这段保留期。操作边界见[设计方案](../../docs/framework/WORKER-SHUTDOWN-EVENTS.md)。

下一步由平台管理员保存并应用新母版快照，在独立克隆中核对通知单元自动启动和节点凭据准备。真实 Ubuntu 关机时序、停止耗时及失败继续关机按用户决定保留待办。XZ-31-001/002 未执行整机关机、重启或等效操作。存量 worker 尚未逐台补装。

## 2026-11-20 003 真实关机试验

在 `XZ-31-003`（worker ID 6）补装当前启动的通知单元，准备该启动的事件凭据。启用前用拒写请求验证 HTTPS 和凭据，返回预期的 422。通知单元随后进入 `active (exited)`，停止预算 `1s`。补装前后容器 ID、启动时间和 worker 身份一致，003 仍为 Ready。

用户随后关闭 003。MaaS 数据库中本轮查到一条 `worker.shutdown.requested`，北京时间 11 月 20 日 14:14:15.772 接收，11 月 22 日 14:14:15.772 到期，保留期恰好 48 小时。GPUStack 于 14:14:43.821 将 003 标成 `unreachable`，比 MaaS 收到事件晚约 28 秒。001 仍为 Ready 并保留 `maas-ocr` 副本。本轮没有做关机后的真实推理探针。

此次确认单机真实关机能上报并入库。所记录的时间是数据库和 GPUStack 的观测值，实际 systemd 停止动作耗时尚未测量。003 的凭据与通知仅为本次启动准备，新克隆自动领证和失败继续关机仍待验。真实关机事件由正常保留策略清理，试点没有写入合成数据库记录。
