新版调节器已通过首轮独立实写和并行对照。原业务 OCR 目标保持 1，前后及过程抽查为 1/1；常驻 E17 镜像与 v1 策略未切换。 本轮不是完整 R4/R5 验收；缺少真实冷缓存、常驻事件循环集成及实际故障恢复的证据，不能把候选试点等同于已正式上线。

结果与建议

两张已 Ready 的 GPU 上，独立试点从目标 0 开始，不等待新的 worker 到达事件。12 个实验完成，27 次自动 +1 全部读回确认；7 次原生授权 OCR 探针成功，文字核对通过。原业务的 2 个 MaaS 异步任务均成功，分别只有一次执行、一条成功用量和一条计量回执，successful_images=1；其中一项在扩容对照进行期间提交。

同样达到 4 副本全部 Running，在途上限 2 的两轮平均耗时为 21.61 秒，串行为 37.85 秒，缩短约 42.9%。在本轮两卡与预算保守预留条件下，2 是后续发布评估的候选；上限 4 的实际在途峰值仍为 2，没有更多效率收益。没有据此认定任何规模下 2 都最优，也没有自动修改常驻预算。

实际服务、问题与修正

原生 Running 后，通过只允许试点模型、有效期 1 小时的临时 inference key，验证实际授权 OCR。最终 7 次原生推理均返回 200，HELLO/2026 文字核对通过。原模型上的两次 MaaS 异步任务完成数据库独立核对；没有把管理员管理 key 当成 MaaS 客户 key。

试点准备暴露了几项操作细节，均已记录：

  • /token-auth 没有通过当前入口暴露，首次探针在 GET 预检返回 404，尚未发送推理；移除这项不适用的预检。
  • 原生 API 创建模型部署不会替代独立 Model Route 的准备。为试点增加其专属 route 后实际 OCR 成功；原业务 route 未修改。这不属于调节器应自动创建业务路由的职责。
  • MaaS 探针最初写死容器端口，连接被拒绝，数据库确认未创建任务；读取实际启动参数后沿用同一个幂等键成功提交，没有重复执行。
  • 原生 API key 管理支持列表和按 ID 删除，不支持按 ID GET。先按列表复核身份与权限，再撤销临时 key；最终撤销返回成功。

没有对不确定的推理/写入盲目重放。本轮临时 key 已撤销；原客户 key、绑定和 MaaS 模型目录未修改。

独立核对与环境收尾

已从原始 trace、状态、持久接管回执、容器退出码和原生 API 重新核对 12 个实验，确认无未确认日志、无超限目标/在途、27 次自动扩容各一次确认。私有归档已复制到 Mac，并在 Mac 再次校验 SHA256 与各实验状态。公开证据只保留匿名统计，不含真实连接信息、凭据或私有日志。

结束状态：

  • 原 OCR 1/1、配置不变，原 E17 容器 ID 与策略不变；旧策略仍为 schema v1 / revision 7 / Apply，上限 2。
  • 独立试点 0/0、0 实例，保留试点部署与 route 供后续使用，不占 GPU 计算实例；未添加到 MaaS 客户目录。
  • 试点控制容器均已退出，没有常驻试点调节进程；候选镜像和证据保留。
  • 2 个 worker Ready，PendingWrite=0，最终 UNKNOWN=0，临时推理 key 已撤销。
  • 未重启 VM、worker 或 Docker 引擎；模型实例在试点内按验证流程新增及归零，原服务未排空或缩容。

本地回归为 110 通过、2 条件跳过。本轮候选基于 d262548 的源码覆盖与原 MaaS 依赖镜像；后续 6067dc7 只加强试点参数校验，防止“预期零写入”与放行参数组合误用，未重建运行中的矩阵，不影响本轮已核验参数组合。此前固定 GPUStack v2.2.3 内 34 项原生 schema/replay 回归已通过，不在本轮重复冒充实写证据。
