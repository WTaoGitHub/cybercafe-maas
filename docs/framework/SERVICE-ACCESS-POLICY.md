# 下游服务接入与容量控制约定

2026-10-29用户确认。当前业务面向一个下游服务，近期仍按单业务项目使用。现有代码已支持项目映射、同项目多凭据共享资源，以及同步/异步统一准入；本次落实职责与接入说明，不修改推理、鉴权、数据库或线上配置。

## 职责

| 能力 | 负责方 |
|---|---|
| 最终用户、用户API Key、套餐、用户级限流、收费与账单 | 下游服务 |
| 下游服务接入认证、逻辑模型授权、项目映射 | MaaS，当前仍复用已登记GPUStack推理Key |
| 实际执行槽位、异步等待队列、输入/结果存储与保留期 | MaaS |
| 模型副本、worker生命周期、GPU放置与推理路由 | GPUStack |
| 任务结果、成功执行记录与故障关联依据 | MaaS保留技术记录，下游决定商业统计与计费 |

下游新增最终用户时，不要求在MaaS同步创建用户、API Key或项目。MaaS接收下游服务持有的已登记凭据；下游最终用户Key不透传为MaaS身份。下游的请求速率控制与MaaS的真实在途/积压上限分别保护不同资源，继续保留两层控制。

MaaS接入凭据由下游后端保存和使用，最终用户前端不持有该服务凭据。容量保护覆盖MaaS入口与执行器；原生GPUStack/Playground调用走现有受控管理通道，不自动纳入MaaS槽位统计。

## 项目和服务凭据

`project`是MaaS的资源隔离与配额归属标识，由管理员在`bindings.json`配置，调用方通过Bearer Key自动归属，无须在请求中选择。`X-Project`、`X-User-ID`不能切换归属或提升权限。项目与GPUStack cluster没有一一对应关系。

同一个Key只绑定一个项目；多份不同Key可以绑定同一项目，共享任务、文件、幂等作用域、执行/排队/存储额度。每份Key的模型允许清单仍分别校验。增发Key不会增加该项目的额度；同项目文件/任务也不按Key形成最终用户个人隔离空间，最终用户访问边界由下游实现。

当前保留既有业务接入绑定和独立测试/维护探针绑定，不将“业务只有一个下游”强制改成“数据库只允许一个技术project”。不合并/重命名已有project，不改动既有任务及文件归属。探针身份继续遵守已有维护窗口及无成功计量规则。

轮换时可先为同项目登记新Key、迁移调用，再处理旧凭据的排队任务并撤销旧Key。排队任务引用提交时的`credential_id`；直接禁用旧绑定可能使其执行授权失败，同项目不代表轮换会自动迁移这些任务。具体操作见[管理员手册](../handbooks/ADMIN.md#5-授权变更禁用与轮换)。

当前仍要求该Key同时在GPUStack有效且具有模型权限。独立MaaS服务凭据与内部GPUStack凭据解耦由既有AUTH增强跟踪，低优先级暂缓；本约定不代表已实现此方案。

## 当前保护参数

2026-10-29只读核对API、四个执行器及observer的配置一致：

| 控制项 | 全局 | 每项目 | 配置项 |
|---|---:|---:|---|
| 执行槽位 | 4 | 4 | `MAAS_MAX_RUNNING` / `MAAS_MAX_PROJECT_RUNNING` |
| 等待队列 | 1000 | 100 | `MAAS_MAX_QUEUED` / `MAAS_MAX_PROJECT_QUEUED` |
| 已登记未删除artifact存储 | 10GiB | 2GiB | `MAAS_MAX_STORAGE_BYTES` / `MAAS_MAX_PROJECT_STORAGE_BYTES` |

以上是当前部署值，不是修改代码默认值或已证明的容量上限。执行器为4个独立进程，每进程一次处理一个异步任务；执行器数、槽位及模型副本数分别配置，不自动相等。API/执行器/observer必须使用一致额度，调整走受控部署流程，不能只改一个容器。

执行槽位统一统计异步`RUNNING/CANCEL_REQUESTED`和同步`DISPATCHING`。排队任务不占执行槽位；异步返回202后仍可能等待或执行，HTTP连接结束不会释放任务的执行归属。UNKNOWN继续触发已有全局隔离，不因连接消失或客户端重发而释放安全约束。

队列统计`QUEUED/RETRY_WAIT`，不含运行中与终态任务。单项目有效上限取全局与项目上限较小值；当前该项目可占最多4个执行槽、保留100个等待任务及2GiB已登记artifact，多个项目合计仍受全局限制。维护/探针等其他活动可能占用全局容量，以上额度不构成保底份额。

当前每项目额度是对所有project应用的统一配置，尚未实现按项目单独定制的套餐/政策表。未来出现第二个独立下游时复用隔离能力，再按需求扩展策略；不同模型的容量控制与现有E1/容量规划衔接，不新增重复调度器。

同步满额返回`429 SYNC_CAPACITY`；异步等待队列满返回`429 QUEUE_FULL`，不创建新任务；存储满返回对应配额错误。已有幂等提交先检查原任务，队列满不阻止合法复用。任务总deadline包含排队时间，文件TTL与任务状态分别管理，不因队列变长自动延长。

## 交付给下游的信息

管理员交付访问地址、适用的证书信任方式、服务持有的Key及有效期、项目标识、允许模型、全局/项目额度、文件大小/保留期、排队计入超时的语义及429/维护/UNKNOWN处理方式。Key通过既有私有文件流程交付，不写入普通说明文档。

下游正常请求只需凭据和业务参数。当前没有`GET /maas/v1/me`、公开额度/用量查询或项目管理接口；身份/额度查询可作为后续便利项，不作为当前接入前置，也不在本次增加接口。
