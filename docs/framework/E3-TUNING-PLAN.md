# E3-TUNE：模型服务容量与参数组合调优计划

2026-10-29。状态：**测试设计已完成，工具扩展与实机测试待实施；本轮不改服务器、不启动负载。** 用户要求补齐6副本、6/8及更高执行器/并发，联合评估等待队列和显存申报。复用E3跟踪，原两GPU试点验收与失败记录保留；原`4/4/4/4/2GiB`是可用基线，不代表吞吐最优或容量上限。

配套：[机器可读测试设计](E3-TUNING-MATRIX.json)。JSON是后续工具的输入设计，现有脚本尚不能直接执行该矩阵。实施从工具改造与本地验证开始，不能直接放宽线上参数。

## 1. 目标与适用范围

在正确性、延迟和资源余量达标的前提下，找出一组成功吞吐较高、资源占用合理、能够稳定运行的部署配置。交付“保守基线、均衡推荐、吞吐候选”及适用边界，允许推荐保留某些现值，不强求显存占满或所有数值增大。

**本轮数值结论只适用于当前PP-OCRv4流水线及对应环境，不能直接用于其他OCR模型。** 模型权重/revision、推理后端与版本、精度、前后处理、GPU型号、CPU/RAM及输入范围均作为profile的一部分；任一重要条件改变，需重新验证。其他模型可复用流程与测量工具，但须创建自己的profile及参数结果。GPUStack升级后的容量也需复核，不继承“最优”结论。

当前profile：`ppocrv4-ortgpu-2x4080s-r1`，逻辑模型`ocr.default`、业务revision `ocr-registry-r1`，RapidOCR 1.4.4 / ONNX Runtime GPU 1.20.2，方向保护开启，现有两张RTX4080 SUPER 16GiB级GPU。实验前重新发现实际worker/GPU和模型实例，不把名称、地址或已有ID当永久身份。001仅作为控制端，不调度模型到其GPU。

固定模型与镜像digest、CPU线程2/2、全局最大边长2000、检测736/min和识别阈值；不在本轮更换模型、关闭方向保护、修改精度或引入合批。OCR算法参数归E10，服务认证解耦仍暂缓，最终用户业务由下游负责。

## 2. 变量及基线

| 符号 | 含义 | 当前基线 | 首轮候选/约束 |
|---|---|---:|---|
| R | 模型总副本数 | 4，两卡各2 | 4、6、8，分别检查2+2、3+3、4+4；有持续收益才扩展10/12等 |
| E | 异步执行器数量 | 4 | 4、6、8；条件满足再12，单进程仍一次一任务 |
| G | MaaS全局执行槽位 | 4 | 4、6、8；具备实际发压能力再12 |
| P | 每项目执行槽位 | 4 | 单业务项目主测P=G；另用较低P验证限制行为 |
| Qg / Qp | 全局/项目等待上限 | 1000 / 100 | 队列专项有效单项目上限10、25、50、100、200 |
| M | 每模型副本显存申报 | 2147483648字节，2GiB | 先固定2GiB；取得可靠峰值后再决定是否改变 |
| L | 原生同步客户端数/负载发生器能力 | 旧矩阵固定4 | 原生4、6、8、12；异步发压能力与E独立 |

G/P不是E的自动派生值；P不得大于G。纯异步实际在途受`min(E,G,P)`约束，测G=12但E=8时不能声称验证了12个异步在途。单项目的队列有效上限为`min(Qg,Qp)`；项目各自的限制当前是同一套配置，不引入项目套餐表。

每卡可容纳R/2个实例必须同时满足GPUStack显存与RAM预算及实际资源余量。显存可见不等于GPU计算份额；调度claim不等于硬限制。当前v2.2.3自定义后端RAM估算至少2GiB，不假定降低显存申报会同时降低RAM预算。

## 3. 实施前置：先解除工具约束，保留运行保护

| 工具/能力 | 现状 | 必须补齐 |
|---|---|---|
| `executor_pool.py` | 执行器/G/P仅允许1–4，只调整副本与运行额度 | 支持显式有界的6/8及条件扩展12；队列额度可在相同暂停窗口一致更新；参数非法时在修改前拒绝 |
| `benchmark_executors.py` | 执行器仅1/2/4，假设模型总副本4、L=E | R/E/G/P/Q/M分别记录，负载发生器与E解耦；不假定副本数或恢复值固定为4 |
| `replica_capacity_matrix.py` | 原生客户端固定4，内置模型/节点及2GiB断言 | 可选6副本及4/6/8/12客户端；范围动态核对、CAS保护；按阶段仅允许批准字段改变 |
| `bounded_map`及混合工具 | 客户端最多4，混合工具固定4额度 | 显式有限范围（首版硬上界16），保留失败后停止补派、在途收尾；不能将所有请求预先无界排入线程池 |
| 发压模式 | 主要是固定客户端完成一笔再发下一笔 | 增加按时间独立到达的有界发压、限速与突发；记录发生器迟发/未发送量，发生器不足时点位无效 |
| 记录/选型 | 缺少统一profile和跨阶段选择依据 | case_id、模块、labels、run_id、参数与样本摘要、实际分布、请求/任务计量、失败分类及候选选择理由 |

先在本地/独立测试库验证：更高额度的多进程竞争、同步异步共享G/P、队列原子准入、同项目多Key不叠加、暂停/generation/UNKNOWN/缩容保护、采样缺失及发生器停止行为。独立库不得指向正式MaaS或GPUStack数据库。

不将首版16上界解释为最佳或硬件极限；若8仍有收益，先逐步验证12，仍有明确收益才另行扩展16。任何扩展都需资源预检，不能只去掉参数校验。所有工具feature验证后分别commit并push。

## 4. 样本、负载与测量口径

- **普通集**：固定现有40张中英文文档/街景平衡样本及顺序种子，沿用校验和；补样时另记版本，不能与旧数值直接拼接。
- **边界集**：3MP/9MP PNG/JPEG、密集小字/长图、方向保护触发样本、空白图，以及接近20MP且不超过10MiB的有效输入。分别报告实际缩放尺度；不提高现有限额。大图只有解码通过，不等于OCR质量达标。
- **业务混合集**：暂按普通80%/边界20%作为实验假设，分组报告；不声称是真实客户流量分布。方向修正与空白图都计入分组，避免只测易图。
- **主容量测量**：输入预上传，饱和异步保持约2G个可执行积压且不超过当前Q；任务提交、完成、轮询和结果下载分别计时。不能再以L=E造成客户端瓶颈。
- **完整端到端复核**：另含上传/base64准备、提交与结果下载，不能将其与预上传容量数字混用。
- **队列/突发测量**：使用独立于完成速度的到达率；统计目标、实际发送、迟发与未发送量。发生器放在稳定的局域网可控进程，记录其CPU/RAM和网络；外部SSH延迟不能冒充模型性能。

每个run使用新ID和独立任务幂等命名空间；客户端不重试，任务`max_attempts=1`。GPUStack内部副本重试沿用现策略，尽可能保存关联日志，不宣称物理推理恰好一次。业务消费者、测试身份和维护探针不得同时产生未区分的干扰流量。

固定客户端负载与独立到达负载回答不同问题，不能仅用前者推断过载排队表现，见[Grafana k6负载模型说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)。方法可用现有Python工具实现，不要求引入k6服务。

## 5. 分阶段矩阵

### T0：工具与当前基线复验

先完成工具前置。只读确认服务、实例、GPU、配额和网络边界，Mac私有备份原模型完整配置、app.env及维护绑定。以当前R4/E4/G4/P4/Q1000:100/M2GiB运行三轮，形成同一时段的新基线。旧报告约122秒的稳态只作参考。

普通集每点预热后**测量至少60秒且至少200次成功**；达300秒仍不满足请求数时保留不足原因，不无限延长。吞吐按测量窗口真实成功完成数计算，固定截止后排空另计；不能在计数时纳入尾部完成、却不纳入尾部时间。

### T1：原生模型副本和请求并行能力

固定2GiB申报，R∈{4,6,8} × L∈{4,6,8,12}，共12个粗筛点。MaaS在维护窗口暂停排空，原生网关发压，避免异步轮询开销混入。每个R记录实际两卡分布；不符合布局的点不冒充计划布局，先记录调度原因再处置。

目标：判断每卡2、3、4副本在较高客户端并发下的吞吐/延迟变化；在相同L下比较R，不用旧4客户端结果排除6/8副本。点位轮次交错，控制预热、温度与缓存差异；所有配置比较在同一模型profile下进行。

### T2：异步副本×执行器联合筛选

R∈{4,6,8} × E∈{4,6,8}，G=P=8，Qp=100（Qg保持不低于Qp）、M=2GiB，共9个粗筛点。发压能维持积压但有界，不将HTTP请求数、202受理数当作OCR完成吞吐。

G/P保持相同值以隔离R和E；实际异步在途分别受E限制。由T1与T2共同选出最多两组候选，而不是原生测量最快就直接替代异步部署结论。硬件、输入处理或控制端资源成为瓶颈时明确记录。

饱和积压测试用于测完成能力，不套用“无排队P95≤1.5秒”的门槛。两组候选还须在**相同外部到达率**下比较延迟/资源，该到达率暂取不高于两者保守完成率较小值的80%；各自80%容量下的延迟可补充报告，但不能用不同负载强度直接证明谁的尾延迟更优。

### T3：全局/项目额度及混合调用

对两组候选分别固定R/E，比较G=P∈{4,6,8}。主业务单项目使用P=G；另测P=ceil(G/2)和P=2的限制行为，这些是策略对照，不因单项目而引入用户限流。

负载覆盖纯异步、纯同步、同步20%/异步80%、同步50%/异步50%。记录同步成功与429、异步等待和完成，验证组合在途及单项目始终不超限。同步成功率/排队待遇单独报告，不允许靠大量429把P95或吞吐“优化”。

若E=8、G=8仍相比6有可重复收益≥5%、资源有余量且尚未出现吞吐平台，条件扩展E=12、G=P=12，再按模型运行时证据决定是否增加R至10/12。不得因工具初始到8而提前宣称找到峰值；如果延迟先触及门槛，则报告该门槛下的合理点。

条件扩展必须记录为已执行或`SKIPPED_CONDITION_NOT_MET`后才进入后续阶段；跳过只表示未触发，不作为12并发通过证据。后续队列与确认使用包含扩展结果在内的最新候选集合。

纯异步E小于G的点仍可作为同步预留空间的比较，但不得说它证明了更高异步容量。G/P是准入上限，不保证CPU/GPU物理同时执行或同步/异步公平；若同步被异步长期挤压，记录现有共享策略的不足，不能假装已有份额预留功能。

### T4：等待队列与到达率

固定候选R/E/G/P/M，以各自稳定完成能力μ为参照，测试到达率0.5μ、0.8μ、1.0μ、1.2μ，以及2μ持续10秒的突发；到达率基于成功业务完成能力，不能用POST任务接口的202吞吐代替μ。

有效队列候选Q∈{10,25,50,100,200}，测试中明确记录Qg与Qp谁先构成限制。单业务主测可设Qg=Qp=Q以比较有效上限；随后验证Qg>Qp、较低P及同项目多Key的保护行为，全局多项目边界优先在独立测试库验证，不借用维护探针身份制造业务负载。

暂定排队预算W∈{5,15,30}秒，默认任务deadline仍120秒、模型运行预算不变。`Q≈保守μ×W`只用于选候选，不是P95等待保证；以实际等待P95/P99、混合大图和突发验证，且应满足`等待预算+处理尾延迟+传输/安全余量 < 总deadline`。

每个队列先做有界突发（25/50/100/200个任务），再做正常到达与过载。正常点至少3分钟；过载点持续到观测到队列满或最多5分钟，未填满不能标记QUEUE_FULL已验证。停止提交后排空至终态，核对受理/拒绝/完成/过期及恢复时间；429不能自动循环重发。

预期超额的429属于该用例的正常结果；202受理的任务若因队列设置过大而超过deadline，记录并淘汰该队列/负载组合，不通过延长超时或不统计失败掩盖。选择能吸收目标突发、满足W的较小Q；大队列不会提高GPU稳态处理能力。最终单业务项目P通常取G，Qg/Qp按实际需要保留明确关系，不必与E/R相等。

### T5：显存申报与资源余量

先固定候选R/E/G/P/Q、保留M=2GiB，覆盖单实例与多实例进程冷启动、集中启动、普通/边界推理，测整卡与可识别进程/容器的显存、RAM、CPU和功率。不能把整卡显存除以副本数当作单实例峰值。

优先复用GPUStack原生指标；降低claim前若现有低频指标不足，则使用测试期间的一次性节点本机只读诊断（例如NVML/容器cgroup采样），记录采样周期和数据新鲜度。不得恢复collector或持续SSH清单轮询，不把诊断数据变成逐请求门禁；诊断不可用就保留2GiB，不伪造峰值。

候选预算从“最高观测启动/推理需求＋有依据的余量”推导；可保留2GiB，也可在证据允许时选一个更低候选（如1.875GiB或1.75GiB），不能默认这些数字安全。每卡至少保留max(1GiB,10%总显存)的实验余量，并覆盖CUDA上下文、其他进程和分配波动；这是本轮保守筛选规则，不是OOM不可能发生的保证。若2GiB仍不足，应上调或减少副本，而非强求降低。

**固定R时下调claim只改变调度预算，通常不会直接降低实际显存或提高吞吐。** 只有确有必要让更多实例被调度，且较高R在前面阶段有收益时，再验证M与更高R的组合。相同R下无收益、无放置需求时优先保留2GiB，不为填满1.99GiB等余额而压缩余量。[固定v2.2.3调度实现](https://github.com/gpustack/gpustack/blob/v2.2.3/gpustack/policies/candidate_selectors/custom_backend_resource_fit_selector.py)为行为依据，环境变量通用说明不能替代具体后端路径。

claim发生改变后的最后一组参数，必须重新通过重复/混合/突发及启动验证，不能拼接不同参数阶段的最好数值来宣称整组通过。

### T6：候选确认与最终运行

对最多两组入围参数各做三轮独立5分钟稳态，交错点位并复测原基线；如果均值差异≤5%或轮次波动覆盖差异，增加至五轮或承认无法区分，优先更少副本/执行器与更大资源余量。报告按轮次的分布/区间，不把反复使用同一图片当成独立业务盲测。

最终均衡候选做2小时持续运行，包含普通/边界混合、同步异步混合、定时有界突发及结果/计量核对，前后真实探针和一次受控执行器排空缩放验证。两小时不替代8小时或生产SLA；本轮不自动重排既有八小时任务。发现异常按停止规则处置，不靠自动重试、续计时或挑选成功窗口完成验收。

## 6. 评价指标与选择规则

| 维度 | 必须记录/暂定实验门槛 |
|---|---|
| 正确性 | 相同权重/流水线的固定样本结果基线对照，尤其空白/倒置/密集小字；无协议、坐标、文本异常。合格吞吐按预先标注/规则验证，未经质量核验只称成功完成吞吐 |
| 延迟 | 普通集无持续积压时暂定P95≤1.5秒、P99≤3秒；边界集单列并与新基线比较，模型运行预算不得超限。排队段按W报告，含排队的E2E不能沿用无排队阈值 |
| 完成能力 | 原生/同步/异步分开，测量成功张/秒、每GPU小时成功/合格任务量；202、轮询GET、429和预热不混入成功吞吐 |
| 准入与结果 | G/P、Qg/Qp始终有效；无UNKNOWN、意外5xx、任务遗失、冲突终态、重复成功事件；异步attempt=1。同步计量按可归因窗口核对，独立区分容量拒绝 |
| 资源 | GPU/整机及可观测实例显存/RAM、GPU利用率/功率、CPU与cgroup节流、控制端负载、DB锁等待和文件锁；CPU长期≥80%或可用RAM低于max(2GiB,10%总RAM)时停止升档并分析 |
| 积压恢复 | 正常到达不持续增长；突发后在预算内回落，已受理任务按deadline结束，拒绝正确且不产生成功事件 |
| 成本 | 若可靠功率数据可用，报告每千张成功/合格图片GPU电耗；1元/kWh、每机每日8小时为当前假设，缺数据则不出数，GPU电费不等于整机成本或利润 |

延迟、等待和资源阈值是本轮暂定实验规则，不是已确认客户SLA。先淘汰质量/正确性/延迟不合格点，再比较吞吐；在最高成功吞吐5%以内，优先较低资源、较短尾延迟及更简单的组合，不用加权总分掩盖错误。给出选择理由，明确未覆盖范围。
