# 调节器只管理副本数，配置与资源声明作为当前输入

2026-11-12 · 用户最新决议 · 候选已实现，尚未部署 · [Issue #39](https://github.com/WTaoGitHub/cybercafe-maas/issues/39)

## 职责边界

模型服务规模调节器只决定受管部署的 `replicas`。运维在 GPUStack 修改镜像、启动参数、环境变量或资源声明时，调节器不回滚、不替换这些配置，不将普通配置变更当成暂停信号，也不因它单独发起模型重启或重建。GPUStack 原生处理这些配置的行为仍由 GPUStack 自己决定。

正常副本对账继续运行：规划采用最新有效配置。配置事件只唤醒完整查询，不等于授权配置修改。副本数量仍按当前策略/容量维护，显式全局暂停优先；按模型控制继续作为后续增强。

集群、归属、受管部署 ID 的变化属于授权范围变化，仍须重新确认。CPU offload、跨节点分布式、LoRA 等尚不支持的放置/序列化方式，不能因本次允许普通配置变化就宣称支持；无法核对时不给出可执行动作，不擅自恢复配置。

## 最新资源声明的来源

当前已接入副本容量规划的是 GPUStack 当前模型 `env.GPUSTACK_MODEL_VRAM_CLAIM`，单位为字节，要求正的十进制整数字符串。每轮完整读取重新解析，不依赖运维同时修改第二份文件。

v2 policy 的 `models.<id>.vram_claim_bytes` 不再必填；旧字段兼容读取但不作为规划依据。`priority/weight/min_replicas/max_replicas/auto_scale_down_min_replicas` 及执行授权仍来自 MaaS 策略。旧 v1/插件继续原资源声明核对规则，不隐式迁移。

新声明缺失/非法时显示 `resource_claim_missing` / `resource_claim_invalid`，清空本轮可执行快照，不退回旧策略值。它不设置 `paused=true`；原配置修复后下一轮可自动恢复规划。当前算法不新增 CPU/RAM 联合容量求解；此类原生配置保持当前值，调度约束继续由 GPUStack 处理。

## 新旧实例资源不能混算

新副本使用新声明，现有实例使用其原生 `computed_resource_claim.vram` 和 worker 已分配显存作为证据；占用预算取 worker 已分配量与实例声明总和的较大值，防止遥测滞后提前释放资源。不能仅因模型声明变化，就认为旧实例已经变大/变小或显存已经释放。

例如一张卡可用于模型的显存为 20GiB：

| 当前旧实例实际占用 | 新声明 | 真实剩余 | 可继续增加的新副本 | 总副本数 |
| --- | --- | --- | --- | --- |
| 1 个、4GiB | 8GiB/副本 | 16GiB | 2 个 | 3 个 |
| 1 个、8GiB | 4GiB/副本 | 12GiB | 3 个 | 4 个 |

表中忽略其他限制，只说明资源口径；实际还受策略上限、selector、稳定期、压力和在途预算限制。不会将第一行直接算成 `20/8=2` 后缩掉旧实例，也不会将第二行算成 `20/4=5` 并凭空增加 4GiB。

同一声明的已核对实例可参与既有总容量/缩容证明。新旧声明混合或旧实例声明缺失时，保留原生占用，只允许用可独立证明的剩余容量规划新增，不凭重新定价缩容；显式策略最大值仍可纠正过量副本，并保留健康/最低服务保护。调节器不修改旧实例资源。全部原生状态收敛到可核对的同一规格后，恢复完整容量规划。

## 写入与并发保护

GPUStack v2.2.3 的模型更新输入要求部署字段，不能直接假设支持只发 `{"replicas":2}`。本轮沿用已核对的原生接口：发送前读取最新部署、保留配置；MaaS 发送边界强制检查，除 `replicas` 外所有字段须与本轮最新快照一致，否则返回 `non_replica_update_rejected`，不发送请求。

完整部署/实例资源指纹纳入稳定期及最终复核。规划后配置再次变化时，旧动作作废，重新取数；明确尚未发送的动作撤销本地预留。可能已发送的超时结果不重试。未确认写入存在期间若配置改变，仍保持只读冲突状态，不能借“接受最新配置”清除未知结果。

原生接口没有比较后写入条件，因此读后到提交之间仍有外部并发窗口，不能承诺对外部持续修改的原子互斥。需要协调的维护继续先暂停调节器。这里的“只改副本数”是受校验的业务变更范围，不是宣称原生请求只有一个 JSON 字段。
