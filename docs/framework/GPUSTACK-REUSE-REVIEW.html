1. 结论

当前设计把 GPUStack 的职责划得过窄，重复规划了模型目录/别名、API key、组织与权限、同步/流式推理入口、基础用量与指标。应把 GPUStack 视为既有模型服务底座，而不只是 GPU 调度器。

建议保留“轻量 MaaS 业务扩展层”：持久异步任务、输入/结果 artifact、任务幂等与重试、网吧节点排空工作流、业务能力 schema、任务级计量。通过 connector 使用 GPUStack 已有能力，不直接读写其数据库、不复制用户/节点/部署表的权威状态。

不建议为复用而直接升级 main。 当前 v2.2.3 已足够承接大部分基础能力；main 作为后续能力参考与隔离验证对象。普通 OCR 的精确排空不能因看到 maintenance 或 draining_since 就判定已解决。

4. 几项最重要的源码结论

4.1 模型目录、同步接口、原生协议入口已经存在

v2.2.3 gpustack/routes/openai.py:90附近的 list_models读取可见路由；proxy_request_by_model解析模型和stream，验证模型权限、选择路由target和实例，再经worker代理调用。gpustack/gateway/utils.py:123起列出chat、responses、embeddings、图片、音频等路由。接口存在只表示转发能力，具体后端仍需实现。

gpustack/gateway/__init__.py:539的generic_proxy_router_plugin与gateway/utils.py:643附近的规则支持/model/proxy/<route_id>/<path>。本地tag的schemas/models.py:259已有generic_proxy字段。

改设计：既有 /v1/chat/completions、模型别名和同步/流式路由留给GPUStack。原生 /ocr 等新接入先验证generic proxy的鉴权、路径、请求体、响应和取消边界，再决定是否需要自建转发。routes/proxy.py的HF/ModelScope代理不是该模型通用代理，不能混用。

4.2 身份与组织可以复用，但新任务API不能直接“继承”权限

v2.2.3 schemas/api_keys.py:17起的scope、:53起的ApiKey包含hashed secret、组织owner和过期时间。api/auth.py提供身份验证及scope检查；api/tenant.py和route principal grants已有组织隔离。main对secret校验和缓存失效增加了实现。

新框架若在另一个服务中，不能仅凭X-User-Id/X-Organization-Id接收客户声明。也不能为了验证身份要求客户提供management key。现有/token-auth是模型级ext-auth，依赖模型上下文；它不是对任意task/artifact端点都适用的通用identity API。

推荐接法：建立一个受信任的身份桥接（在GPUStack侧扩展一个最小identity/scope验证接口，或通过经过验证的网关ext-auth和受保护的内部上下文），输出principal/key/scope；框架按该身份授权任务和artifact。身份桥接若暂不能实现，再用独立业务key作为明确的过渡方案，而非无意中维护两套正式账号体系。提交任务还须检查模型授权，后续查询已有结果的权限规则应单独写定。

4.3 maintenance 不是请求 drain

v2.2.3调用PUT /v2/workers/{id}可更新maintenance；schemas/workers.py:379附近compute_state将worker置MAINTENANCE；policies/worker_filters/status_filter.py:21只允许READY worker进入新的部署候选。

但Python推理入口调用ModelInstanceService.get_running_instances，v2.2.3 server/services.py:905只按model_id和RUNNING过滤，没有联查worker maintenance。WorkerController仅在unreachable/NOT_READY等路径标记实例不可达；maintenance未触发相同处理。worker_instance_cleaner.py还刻意避免对维护节点自动清理离线实例。

因此不能把maintenance当作已有实例停止接单或任务排空证明。 它适合计划维护、避免新放置和避免不必要重调度；需与业务drain组合使用。还需验证网关控制面传播和缓存窗口，不能只看一次PUT成功。

main server/controllers.py:2374的_soft_scale_down_enabled明确仅在model.roles存在且配置drain窗口时启用软缩容；无角色普通模型直接删除缩容候选。带角色组可从router registry移除成员并等待固定窗口，但固定窗口也不是所有在途推理必然结束的证明。cancel_drain辅助函数本身无生产触发入口，不能当成节点drain API。

保留自建：网吧的接单意图→停止新业务任务→核对在途→允许切系统；001控制端不得随普通worker关机。优先为GPUStack增加小的路由资格过滤/排空扩展并测试；暂做不到时，才使用原设计的定向实例connector。

4.4 main 的新 LB 可复用，但不保证通用任务限流和持久排队

main 的routes/plugins/lb/、least_load/、session_affinity/等以Higress规则/WASM插件实现，ModelRouteTarget.max_running_requests为可选过滤参数。相关插件代码依赖manifest中的可用模块，模块不存在会退化/不生效；main Python fallback的http_proxy/load_balancer.py仍默认RoundRobin。

本地tag的gpustack-higress-plugins==0.3.0与main的==0.5.0不同。该独立依赖包源代码不在本次仓库检查范围，不能仅凭Python配置断言具体WASM运行行为已验证。不能只摘拷Python LB类到v2.2.3就期望功能成立。

复用范围：常规请求分配、路由策略、合适的fallback。保留范围：项目任务队列、任务接受语义、幂等、事务租约和实际模型停止后的槽位释放。实时引擎指标过滤也不同于严格事务式并发预留，OCR需确认是否提供插件依赖的指标。

4.5 内部工作队列不等于推理任务平台

两个版本都有server/workqueue.py，开头说明其是controller reconcile的内存队列，提供per-key去重、延迟和退避。它处理部署状态收敛；不是客户提交后的持久推理任务表。

在已检查的注册路由和状态模型中，未找到覆盖我们要求的通用/tasks、任务幂等键、attempt租约/fencing、持久输入/结果、结果TTL和节点故障后任务恢复的完整链路。/responses透传、benchmark任务或后端自己的异步job也不等同于此能力。

保持自建：任务API、PostgreSQL持久任务队列、有限重试、attempt、结果提交及TTL。可借鉴队列设计，但不把上游内部类当作稳定公共SDK。

4.6 用量与监控应复用，业务成功计量仍需补充

v2.2.3已有ModelUsage.request_count、token计数、ModelUsageDetails及/usage/gateway-metrics上报；metered_usage.py明确只计量资源数量，不含价格。资源metering面向GPU/CPU实例和存储，不能直接当成普通模型实例的逐请求板卡电费。

main ModelUsageDetails.request_id支持更好的请求关联。自建层需补task/attempt关联、成功任务唯一事件、图片/任务计量及失败重试成本。当前OCR SSE刻意不伪造usage；不能因此假定GPUStack已完整记录每个OCR请求及其正确单位，需专门验证generic proxy和自定义JSON/SSE路径的统计覆盖。

定向私有实例调用会绕过GPUStack入口鉴权、用量中间件和网关LB。若为drain暂时采用该路径，必须由任务服务承担客户授权、调用凭据保护、任务计量和trace，并明确上游统计缺口；不能报告为“同时完整复用了入口统计”。

6. 修订后的实施优先级

  1. F0先做复用探针：generic proxy原生OCR、现有API key/组织权限、任务服务身份桥接、maintenance下的请求流向、调用链用量覆盖。形成当前v2.2.3可用能力清单。
  2. F1只建设持久任务和artifact最小闭环：使用现有身份映射和模型路由引用；模拟后端加现有OCR，不做第二套模型网关/用户中心。
  3. F2补业务drain和故障恢复：先验证小扩展复用GPUStack入口的可能性；严格drain无法满足时再采用受控定向connector，补齐统计与授权。
  4. F3复用既有Prometheus/Grafana/usage：仅加业务指标、任务配额和计量，不重复采集全部GPU指标。
  5. F4复用网关和交付能力：加任务端点路由、备份恢复、业务隔离与过期清理。main的LB/revision另开隔离验证，不绑定F1关键路径。

原18–28人日估算不能直接按“复用项数量”减去工期：身份桥接、网关策略和定向调用统计仍有集成成本。F0完成后重新估算。此文件为对v0.1设计的审查建议，尚未重写DESIGN/ROADMAP原文或修改线上部署。

7. 必做验证清单

  • 同一inference-only key能否调用原生generic OCR；过期/删除/缩小模型权限后的缓存传播行为。
  • 两个组织访问模型目录及新任务/artifact的隔离；伪造身份头是否被忽略；不使用management key替代客户认证。
  • maintenance期间持续发送请求，分别观察Python fallback和实际Higress入口，确认已有RUNNING实例是否继续接单。
  • drain与任务领取/请求派发竞态；取消/超时但GPU仍执行时不得提前关机。
  • generic代理的JSON、multipart、SSE、错误和模型名重写；原生payload中名为model的业务字段是否被改变。
  • 自定义OCR和generic请求有无usage行；内部任务重试与外部成功任务的统计是否分清；定向路径是否绕过上游统计。
  • main的LB依赖版本/manifest、OCR指标适配与过载行为；不把引擎指标过滤误作持久任务配额。
  • main部署revision回退与已有自定义OCR镜像兼容；备份后离线迁移验证，不直接升级线上001。
