## E1：逐 worker 排空、其他节点继续服务

### 范围与实施任务

| 顺序 | 任务 | 交付物 |
|---|---|---|

| 4 | 验证其余节点具有相同模型版本及足够容量；按剩余容量调整并发/排队，必要时拒绝维护 | 容量预检与过载策略 |

### 新增范围：突发故障时逐 worker 隔离、按剩余容量继续服务

与计划维护先排空再停止不同，突发故障可能已有请求失联，不能假定能正常排空。增加以下任务：

| 任务 | 预期行为 |
|---|---|
| 故障识别与隔离 | 检测worker失联、实例异常或请求失败；区分节点故障与单模型实例故障，按证据确定最小隔离范围；从路由撤出不健康目标并记录检测/收敛时间 |
| 按模型评估剩余能力 | 维护模型→健康副本→worker映射；模型1仍有健康副本则继续服务并降低并发；模型2的健康服务不因模型1故障被全局关闭 |
| collector降级验证 | 对每个模型的健康子集持续验证版本、镜像和容量；不因一个worker异常撤销整个集群其他模型的可用证明 |
| UNKNOWN局部隔离 | 请求/attempt关联实际执行节点，约束网关重试的潜在执行范围；仅在能证明隔离边界时缩小UNKNOWN影响范围，不把未知执行当作已停止，不盲目重放 |
| 容量不足响应 | 剩余容量不足时有界排队、限流或明确拒绝；模型无健康副本时仅该模型不可用，不自动换版本；保留结果查询和其他健康模型服务 |
| 故障恢复与防抖 | 节点重新上线后先验证版本/镜像、处理残留活动并通过真实探针，再逐步接流量；避免反复上下线造成路由震荡 |
| 故障注入验证 | 在多模型并发流量下测试节点失联、单实例崩溃、超时/UNKNOWN及反复恢复，记录各模型成功率、延迟、积压和容量变化 |

若无法确定请求实际落点或隔离潜在后台执行，仍保留必要的保守隔离，并明确报告影响范围；不会为了继续服务而跳过安全判定。

### 依赖与边界

- 首先针对XZ-31-002验证，001继续运行控制端和推理。维护001本机还需要控制端独立部署或迁移，不能直接套用002流程。
- 当前请求通过GPUStack通用入口，任务层不能可靠确定实际执行worker；节点级路由隔离和活动追踪必须先验证，不能仅将现有脚本的worker ID改为参数。
- 当前collector要求两个既定worker及对应实例均健康，需要支持经过授权的维护拓扑和剩余节点验证，同时维持模型版本/镜像约束。
- 剩余节点必须能承载对应模型；没有可用副本或容量不足时拒绝进入该维护模式，另行选择当前全局维护流程。
- GPUStack、Playground及worker直连应遵守同一隔离边界；未知活动未确认结束时，不认定目标GPU已释放。
- 双系统切换、自动关机/开机和精确吞吐目标另行验证，不自动包含在本增强中。

### 验收条件

1. 目标worker撤出后不再收到新请求，路由收敛时间可测量。
2. 既有在途请求完成或明确进入异常处理；UNKNOWN阻止宣告该节点排空，不盲目重放请求。
3. 在剩余节点容量范围内，维护全过程继续受理和完成请求，不执行全局暂停或集群副本归零；报告错误率、延迟、积压及容量变化。
4. 非目标worker及其正常推理实例不被停止或重建；目标节点实际GPU占用清除有证据。
5. 恢复节点通过真实探针后才重新接流量；恢复失败保持该节点隔离，不影响健康节点继续服务。
6. 无跨项目越权、任务遗失、重复成功计量或静默模型版本切换。
7. 模型1某worker突发故障时，在健康副本与剩余容量可用的前提下继续服务；模型2的健康请求继续完成，不触发全局暂停或全局副本归零。
8. 模型1所有副本不可用时，对模型1明确返回不可用/有界排队，模型2仍继续服务；故障与UNKNOWN的影响范围、隔离依据可审计。
9. 故障节点未经探针和残留活动检查不能重新接流量；故障恢复失败不使健康节点停止。

正式服务仍为全局受控维护及全局UNKNOWN隔离，collector要求既定节点集合健康。新增E1候选模块已在本地实现单worker别名验证、独立健康子集、持久落点/共享容量、局部隔离状态机与单次HTTP传输；未接入正式API/执行器，未提供真实运维hooks，未部署或完成实机验收。今晚P4版本、配置和测试计划保持不变。

### 2026-10-27新增：显存预算、副本数与吞吐联合优化

只读观测基线：model18/maas-ocr-registry-r1目标14副本，7 running/7 pending；worker7的GPU总显存约15.99GiB，GPUStack allocated约14GiB，GPU实际used约4.42GiB、采样时GPU core利用率0%。模型显式环境变量GPUSTACK_MODEL_VRAM_CLAIM=2147483648，即每副本调度声明2GiB。7份声明后剩余约1.99GiB可调度预算，因此不足再安排一个2GiB副本。此处是**低负载时刻的整卡观测**，不是单副本实测、峰值或可安全继续分配容量的证明。

GPUStack调度预算不是CUDA实际占用，也不是强制显存硬上限；降低claim不会降低模型实际显存需求，不能凭空增加GPU容量。当前custom selector的RAM声明也至少2GiB，降低VRAM声明不代表RAM预算同比减少。14副本不等于14张GPU、14并发或14倍吞吐；不以显存填满率为优化目标。

## E4：同步接口持久幂等与原结果复用

状态：已登记，暂缓实现；2026-10-21用户要求纳入后续开发计划。**当前优先级：中低，P4之后按业务触发条件重评**，不作为P4验收或首期OCR接口兼容的强制前置，也不因登记而改变现有同步行为。

### 背景与需求

外部消费者的[接入契约分析](CONSUMER-API-GAP.md)指出，其网关具有持久业务去重且不重试/改派，但上游调用仅带Bearer/Content-Type；body中的request_id可选，消费者自动生成的ID不保证透传。本系统现有异步任务已支持project作用域的Idempotency-Key；同步 `/v1/chat/completions` 没有持久幂等，客户端断连/超时后重新发送可能再次推理及计成功用量。X-Request-ID目前是服务器生成的诊断标识，不是幂等键。

目标：调用方用相同业务键重试时复用原请求记录和已保存响应，不重复发起应用层推理或成功计量；请求仍执行或结果未知时明确反馈，不能因超时自动重新执行。未来若新增消费者兼容 `/ocr` 或文生图入口，应复用相同机制，而非各自实现内存去重。

不承诺端到端GPU“恰好执行一次”：数据库与远端推理不是分布式原子事务，GPUStack内部网关重试也属于另一层约束。

### 优先级、收益与成本考量

| 情境 | 收益与安排 |
|---|---|
| 当前少量私有OCR验证 | 单次算力成本较低，节省重复GPU资源的收益有限；先做稳定性、容量/成本与真实消费者接入验证 |
| 已有异步任务可被消费者采用 | 优先复用现有任务幂等/查询/持久结果，避免立即建设第二套完整结果复用机制 |
| 消费者已有持久幂等且明确不重试 | 首期可由其负责业务去重，本系统保留UNKNOWN保护；不能因此宣称同步上游已具备幂等 |
| 同步调用必须支持超时安全重试、找回原结果 | 提升为高优先级，先完成稳定必传业务键与保留期约定，再承诺此能力 |
| 高成本/长耗时图像生成或重复计量争议增加 | 重新测算收益；若需要对外收费和可对账，幂等价值提高，先解决计量一致性 |

主要工程成本在并发仲裁、跨文件/数据库一致性、进程崩溃、UNKNOWN、鉴权与过期恢复，而非增加一个header。OCR响应较小，存储成本通常相对可控，但仍需量测请求量×保留期×平均结果大小及数据库/清理开销；图像大结果应走有界artifact引用，不直接无限存入数据库。不能预先承诺具体工期或“零开销”。

触发重评：消费者明确要求同步强保证；重复推理/计量事件已有可量化成本；上线高成本同步模型；或商业对账要求提出。触发后与E1–E3按实际业务价值排序，不预设必须排在所有增强之后。

### 当前阶段的替代与对外约定

- 需要可靠重查的消费者优先使用现有异步任务接口，保存Idempotency-Key、原请求体与task ID。
- 同步OCR继续作为便捷接口，明确“无同步幂等、发送结果不明不自动重试”；保留全局UNKNOWN规则。
- request_id如后续被接纳，首期只用于关联，不把诊断字段宣传为业务幂等。消费者去重不能替代本系统远端未知执行判定。
- 不建议用图片/prompt内容哈希短窗口去重：合法的两个独立请求可以内容相同，图像生成还可能期望不同结果。

### 候选解决方案

1. **键与作用域**：接受Idempotency-Key；未来兼容接口可将body request_id映射为同一业务键，两者同时提供且不一致时拒绝。唯一作用域为project+接口/操作+key，而不是API key或全局裸ID。旧客户端无键可保持旧语义；强保证渠道要求稳定必传键，服务端临时生成值不能帮助调用方重试找回。
2. **摘要与原子占位**：在现有独立PostgreSQL任务库新增同步幂等记录，保存逻辑模型/revision关联、规范化请求摘要、执行token、状态、响应/结果引用、有效期与审计时间。唯一约束仲裁并发；只有占位成功且确认提交的执行者可以发送。摘要不含密钥；规范化覆盖图片及有效参数，须事先约定相同原请求遇到目录升级的处理，不能静默换revision执行。
3. **状态处理**：同键异内容409；进行中有界等待或明确IN_PROGRESS（具体HTTP状态需消费者确认，不静默改为异步成功）；成功返回原HTTP状态/内容；已确认失败复用原错误；UNKNOWN不重放；过期明确返回过期，不把旧键直接当新任务。
4. **成功响应与计量一致性**：远端完整结束、业务输出校验通过后保存可复用响应，将幂等状态、同步活动及唯一成功事件同事务确认。大结果文件采用现有原子写入/共享生命周期锁及受保护引用，不能先回成功再异步缓存；文件与DB提交不确定时保留恢复证据。
5. **崩溃与恢复**：持久化执行意图先于发送。占位后未发送/发送前提交确认丢失、发送后进程退出、响应已到但提交未确认等情况分别判定；只有有证据未发送才允许接续，无法确认远端结束进入UNKNOWN，不能按租约到期直接重新执行。响应提交成功但客户端断连时，同键重试读取原结果。
6. **保留与清理**：建议首版响应保留24小时，幂等键墓碑保留更久；两者为待容量评估/双方约定的候选值，不是当前已发布承诺。记录与结果引用/GC联动，设置项目/全局存储及等待者上限；墓碑到期后的键复用语义必须明确，不能承诺无限期去重。
7. **安全与兼容**：每次复用仍校验当前身份/project/模型权限，禁止跨项目读取缓存；key轮换不丢失同project幂等关系，禁用凭据不能借缓存绕过鉴权。不得缓存Authorization或原始敏感日志；探针与业务计量分开。
8. **后端重试边界**：应用层幂等阻止重复客户端请求再次发送。2026-10-21用户已明确，消费者“不重试”仅为自身行为声明，不要求本系统禁重试；E4不包含关闭GPUStack重试，保留现有策略和UNKNOWN安全约束，不作为接入前置问题。

## E6：退役自建collector，复用GPUStack服务状态

状态：**2026-10-22已完成代码迁移和正式发布，线上collector已停止并永久mask，专用访问资产已清理；真实OCR、完整维护及备份恢复通过，2026-10-23新基线8小时复测通过（5760/5760、SQL一致），E6关闭。** 本项属于P4失败后的架构整改，需在新基线8小时复测前完成依赖迁移与验证；不是等待P4通过才处理的普通后续项。编号不表示顺序，**安排为E6整改 → P4重新验收 → E5立即启动**。E5仍是P4完成后的最高优先级，E1–E4保持暂缓新增实施。

### 最近讨论与决策背景

1. 夜间8小时测试在约3小时16分钟时因PREFLIGHT_UNAVAILABLE失败。collector采集异常会撤销证明，异步任务在推理发送前失败，backend intent=0。两节点当时都出现SSH MaxStartups限流，后续也曾同窗复发；SSH是高概率诱因，原日志没有采集失败阶段，不能声称每轮异常的唯一根因均已证实。见 [原因分析](../../results/maas-p4-release/CAUSE-ANALYSIS.md)。
2. 自建collector原本用SSH/Docker与控制面查询，独立核对实际镜像、固定worker集合/分布及网关策略，再向应用提供30秒新鲜证明。这个严格门禁是本项目增加的，不是GPUStack运行所必需；它使管理采集链路故障转化成客户推理不可用。
3. 大规模节点下，中心串行SSH与重复控制面查询难以维持现有周期，固定全节点共同通过的条件也不适合动态资源池。若强行按1万节点每5秒采集，理论约2000次节点采集/秒；这是简单预算，不是实测性能。当前尚无量化证明显示该额外运行成本带来必要业务收益。
4. GPUStack v2.2.3已有worker注册/心跳、GPU与系统资源上报、实例状态、路由和就绪/失联处理。用户明确：信任其服务可用性声明，由GPUStack解决其声明与实际不一致的问题，本系统不重复建立节点健康仲裁平台。
5. 据此决定**退役自建collector，而不是为了保留它继续新建专用SSH基础设施或定期全池审计**。发布时必要的版本/镜像核验保留为按需工具；正常运行不依赖这些工具在线。详见 [职责重评](GPUSTACK-TRUST-BOUNDARY.md)。

### 目标与范围

- 删除推理必须读取动态preflight、必须固定两worker都健康及约5秒SSH镜像采集的依赖，让GPUStack透明提供服务。
- 退役对象为本仓库自建maas_platform.collector、maas-collector.service及其专用SSH inventory/consumer证明链路；**不删除GPUStack worker内置collector/心跳/资源上报**。
- 保留MaaS鉴权、project/模型权限、静态逻辑模型/revision绑定、输入/输出校验、任务/文件、队列/共享配额、维护、发送活动账本、UNKNOWN和唯一成功计量。
- 保留observer与宿主机业务监控，调整其collector关键依赖项；仍观察API/DB/执行器、磁盘、积压、调用失败及GPUStack必要状态，不新增全节点重复巡检。

### 三类能力与首轮候选（2026-10-28用户决议）

以通用OCR、文档解析、专用识别三类为基准，每类规划至少1个、最多2个候选服务方案，同一模型可跨类别复用；以下为首轮拟测试名单，测试后再决定保留与部署哪些模型，不因登记启动部署。检测/识别组合及字段提取流水线按一套候选服务方案管理，同时分别记录内部模型、推理框架和适配模块。

| 类别与输出 | 首轮候选 | 测试定位及范围 |
|---|---|---|
| 通用OCR：文字、坐标、置信度 | 当前RapidOCR-ONNXRuntime 1.4.4＋PP-OCRv4系＋方向保护；PP-OCRv6 small | v4为正式候选和现网默认基线，不预设淘汰；以相同真实样本比较中英文、扫描件、截图、拍照及大图质量、延迟和每GPU小时合格任务量 |

1. 收集真实业务样本并固定标注和留出集；确定文字、车牌、金额/税号/日期等关键字段、表格与跨页结构的合格标准和延迟上限，按上述三类首轮名单开展比较。
2. 为候选固定权重revision、许可证、镜像digest、推理框架及前后处理；Unlimited-OCR-2单独核对定制wheel依赖、CUDA/驱动、GPUStack v2.2.3自定义backend、共享内存和显存峰值。单页/低并发通过后再评估多页，不照搬官方高并发配置。
3. 为文档解析设计独立逻辑模型/driver和结果schema，保留ocr.default基线。现有异步connector仅接受单张PNG/JPEG及固定OCRResult，不能只替换模型名；评估PDF分页渲染、页数/像素/文件限制、输出页关联、超时、取消、失败及UNKNOWN行为。生成式模型不得伪造置信度/坐标来满足旧schema。
4. 统一报告质量、每GPU小时合格任务量、延迟分位数、峰值显存、失败率和电耗；明确硬件、副本、并发、输入规模与测试时长。早期成本按用户电价1元/kWh、每台每日8小时估算时，只算GPU电费的结果不等于整机成本或利润。
5. 交付选型报告、可复现配置、原始结果及推荐/不替换理由；确有收益再另行安排受控接入与回退。模型实验与E3的执行器并发、副本和显存claim矩阵分开记录，不直接改现网claim，不自动重放未知完成请求、不解除UNKNOWN、不恢复collector。

长期约束继续适用：001/002禁止VM重启及等效操作；资源不足或驱动不兼容不构成重启/升级授权。独立feature完成适当验证后分别Git提交，不push。本项当前仅登记，未部署。


### E10补充：大图片支持（2026-10-28用户需求）

将大图片列为选型及服务验收维度，分别记录原始文件字节数、宽高/像素数、检测/视觉编码实际尺寸、缩放/切图策略与文字最小尺寸；不能把预处理尺寸当成原图上传硬上限，也不能将可解码当成质量达标。当前代码基线为单图10MiB、2000万像素，未授权提高线上限制。

优先评估现有模型扩展，不将更换模型作为大图支持的前置条件。在独立环境中固定当前ocr.default对应的RapidOCR/PP-OCRv4权重与方向保护，使用相同样本比较两种方案：①提高服务字节数/像素准入限制后整图识别，记录实际缩放尺度；②重叠切图识别并合并结果，验证边界文字、去重、坐标回映及阅读顺序。当前10MiB/2000万像素是MaaS与OCR后端服务主动设置的保护限制，不是模型固有上限；只放宽MaaS入口仍会被后端拒绝，实验需分别核对两层限制。比较识别质量、延迟、吞吐、内存/显存峰值与稳定性后，再确定可对外承诺的文件大小、宽高/像素范围及适用条件；未验证前不承诺超限支持，不修改线上限制。确有不足再与其他候选模型比较。

- PP-OCRv6 small/medium及v5 server历史评估配置均为limit_side_len=736、limit_type=min、max_side_limit=4000；这是旧流水线配置，不是模型最大可接收宽高或当前服务承诺。调整检测尺度/切图须独立验证。
- [PaddleOCR-VL原版预处理配置](https://huggingface.co/PaddlePaddle/PaddleOCR-VL/blob/main/preprocessor_config.json)max_pixels=2822400（约2.82MP）；属于视觉编码缩放预算，不是原图文件上限，也不能直接推广到其他VL版本或区域解析流水线。
- [DeepSeek-OCR-2官方配置](https://github.com/deepseek-ai/DeepSeek-OCR-2/blob/main/DeepSeek-OCR2-master/DeepSeek-OCR2-vllm/config.py)为1024全局视图、768局部切块，最多6块；没有据此证明原图分辨率硬上限。
- [Unlimited-OCR-2 Transformers源码](https://huggingface.co/baidu/Unlimited-OCR-2/blob/main/modeling_unlimitedocr.py)默认1024全局视图、640局部块、最多16块；infer_multi默认关闭切图。定制SGLang实际处理器还需独立核对，不能用Transformers默认值替代SGLang验收。超长文档能力不等于单张超高分辨率无损编码。
- PP-StructureV3/MinerU按所选pipeline/backend逐阶段核对，不给工具名称指定一个统一模型分辨率上限。

后续使用4K（3840×2160）、手机12MP（4000×3000）、A4 300dpi（约2480×3508）、A4 600dpi（约4961×7016）、8K（7680×4320）及长截图样本，比较整图缩放与重叠切图的漏字、重复字、坐标回映、表格/阅读顺序、延迟及内存/显存峰值。600dpi A4和8K均超过当前20MP限制，只能在另行确定的独立验证范围内评估；文件大小另行检查，不从像素数推定。产出按模型与硬件配置划分的“可接收上限”和“质量/资源达标范围”，尚未实测的尺寸明确标注。本轮仅调研及登记，不改线上限额、不启动大图压测。

## E11：CPU OCR纳入GPUStack统一管理

状态：**2026-10-28用户要求登记，待设计、实现和实测；本轮仅记录结论，未修改推理代码、镜像或线上部署。** 不改变当前E3→E8/E7等已确认执行顺序，具体优先级待后续安排；与E10模型选型协同，但不作为其前置条件。

### 背景与架构决定

利用空闲CPU和内存提供OCR服务，同时复用GPUStack v2.2.3的模型实例生命周期、健康检查、模型路由及负载均衡。MaaS不另建CPU模型实例管理器、worker健康仲裁或负载均衡器；继续保留现有鉴权、配额、同步/异步任务、结果存储、UNKNOWN和成功执行记录职责。内存用于容纳模型和中间数据，计算仍依赖CPU，不能以可用内存推算吞吐。

已核对本地GPUStack仓库v2.2.3标签的`docs/tutorials/inference-on-cpus.md`、`docs/user-guide/model-deployment-management.md`及CPU后端过滤代码：自定义后端支持纯CPU推理，可使用`custom_framework: cpu`并开启`Allow CPU Offloading`；非OpenAI协议另有Generic Proxy路径。这是版本能力与接入路径证据，尚未证明当前worker拓扑、具体OCR镜像、资源隔离和多副本运行通过。官方强烈建议CPU推理使用CPU worker，带GPU节点的CPU调度行为需单独验证。[CPU推理文档](https://docs.gpustack.ai/2.1/tutorials/inference-on-cpus/)及[自定义后端文档](https://docs.gpustack.ai/2.0/tutorials/using-custom-backends/)为参考，实施以固定v2.2.3源码与实测为准，不套用旧版llama-box结论。

### 首轮实施范围

| 任务 | 内容与交付 |

| 运维交付 | 提供登记、扩缩容、维护、停止/恢复、日志定位及回退步骤，复用GPUStack状态；故障不自动切换CPU/GPU或模型版本，不自动重放未知完成请求 |

### 验收条件与边界

1. CPU OCR由GPUStack实际创建并管理实例，健康检查通过；运行证据确认使用CPU provider，不依赖CUDA或GPU显存；状态不只停留在配置登记。
2. 经GPUStack统一鉴权入口完成真实OCR；至少两个CPU副本的请求分配有可核对证据，验证扩缩容、单实例异常后的路由收敛和恢复，记录失败窗口，不承诺无损切换。
3. MaaS同步/异步、结果读取、权限、配额、维护、UNKNOWN及单次成功计量回归通过；输出文字、坐标、置信度符合当前契约，不产生虚构token计费。
4. 明确实际可用的CPU worker拓扑、RAM申报与CPU/内存限制；多副本不会仅因每实例线程过多或预算失真耗尽宿主资源。CPU/GPU混跑需要独立竞争测试，不能由CPU-only结果推导。
5. 报告相同样本下的质量与容量、资源余量和适用场景；历史CPU服务约2.208秒中位响应仅为旧环境小样本，不能作为当前性能承诺。收益不足可保留GPU默认方案。
6. 实施先在独立验证范围开展；本登记不授权改动现网副本、worker、镜像或默认路由。001为控制端，不能默认占用其空闲CPU开展压测；实际节点先重新只读核对。XZ-31-001/002禁止VM重启及等效操作的长期约束继续有效，未做整机重启不得标为已验证启动持久性。

交付物：CPU镜像和协议适配、GPUStack后端/部署配置、MaaS模型登记、可复现验证报告及运维回退文档。每个独立feature适当验证后分别Git提交，不push；当前仅完成事项登记。
## E12：KubeEdge多网吧边缘管理候选

记录日期：2026-10-29。来源：用户要求保存本轮讨论，未来再评估。状态：架构候选、待讨论；未做集成验证，不构成选型或迁移决定，不改变现有认证及其他任务优先级。

### 初步判断与适用条件

本轮按“将网吧闲置GPU转换成可通过API消费、按使用量计费的推理服务”理解算力Token化。KubeEdge适合作为未来多网吧的容器部署、配置同步、状态管理及弱网自治候选；当前继续以MaaS＋GPUStack推进推理稳定性、容量验证和计量闭环。

现有E5负责克隆启动配置与worker接入，GPUStack负责资源上报、模型部署与推理路由，MaaS负责鉴权、配额、任务、租约及计量。现在引入KubeEdge会增加Kubernetes控制面、边缘运行时和网络组件的维护成本，并与现有职责重叠。不能假定它能解决当前worker代理连接503，或直接提供Token计费、结算、可信资源认证和游戏优先退让策略。

当跨多个网吧统一发布、分批升级、长期弱网或站点自治成为主要瓶颈，且团队能承担Kubernetes运维成本时，重新讨论引入价值；不以节点数量作为唯一门槛。

### 后续讨论问题

1. **职责边界**：KubeEdge管理哪些站点组件，GPUStack管理哪些模型实例？每个容器必须有明确的生命周期管理者，避免双重控制。现有Docker worker能否以合理成本集成，需要独立验证。
2. **业务连续性**：边缘模型进程断网后仍运行，不代表中心消费者仍能调用。若要离线接单，需另行设计站点本地网关、授权额度、任务及结果存储、恢复同步和防重复计费。
3. **网络与成本**：区分云边控制通道和推理数据通道；评估CNI、跨网吧连接、EdgeMesh穿透/中继、带宽、延迟和安全边界，不假定引入后网络问题自动消失。
4. **网吧资源策略**：游戏占用时如何停止新派发、排空任务、释放GPU及恢复接流量；节点失联时如何处理UNKNOWN、重试和计量，仍须业务策略支持。
5. **身份与可信性**：节点注册不能直接证明物理GPU唯一、资源真实或使用量可信，需要单独评估资产身份、凭据撤销、租户隔离及审计。
6. **投入产出**：与继续增强E5、GPUStack及站点网关相比，明确KubeEdge减少了什么维护工作，以及新增的部署、升级、监控和故障处理成本。

若未来决定试验，先明确独立环境、对照方案、验收指标及回退路径；XZ-31-001、XZ-31-002永久禁止VM重启及等效操作的约束继续适用。当前仅文档记录，未部署或开展实验。
