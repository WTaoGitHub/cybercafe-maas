## E1：逐 worker 排空、其他节点继续服务

状态：本地候选已实现基础模块并完成本地验证，未部署、未完成E1整体验收。来源：用户明确要求；2026-10-21授权先做设计/代码/本地测试，P4通过后再部署。详见 [E1设计与路线图](E1-DESIGN.md)。范围包含计划维护与突发故障两条路径：维护或故障时仅目标worker退出推理，其他健康节点按剩余容量继续提供同步与异步模型服务，不全局暂停、不将整个集群副本归零。

### 范围与实施任务

| 顺序 | 任务 | 交付物 |
|---|---|---|
| 1 | 核对GPUStack v2.2.3可复用的节点/实例路由控制及实际行为；不能将maintenance等同于停止接收请求 | 能力验证及方案决策，升级另行评估 |
| 2 | 将目标节点从新请求路由中撤出，并验证路由收敛；控制模型实例调度，避免维护期间再次向该节点部署 | 可恢复的节点准入隔离 |
| 3 | 获取实际执行节点与请求/attempt关联，核对该节点在途及UNKNOWN；覆盖同步、异步和网关重试/旁路 | 节点级活动账本与排空判定 |
| 4 | 验证其余节点具有相同模型版本及足够容量；按剩余容量调整并发/排队，必要时拒绝维护 | 容量预检与过载策略 |
| 5 | 仅停止目标节点实例/worker，确认实际GPU进程退出；保存原配置、执行阶段和失败恢复材料 | 逐节点维护命令与审计 |
| 6 | 恢复目标节点，通过版本、健康和真实推理探针后重新加入路由 | 节点恢复与回退流程 |
| 7 | 在其他节点持续承载流量时，测试空闲/在途/超时/UNKNOWN、路由收敛和恢复失败 | 自动化测试、服务连续性报告 |

### 新增范围：突发故障时逐 worker 隔离、按剩余容量继续服务

与计划维护先排空再停止不同，突发故障可能已有请求失联，不能假定能正常排空。增加以下任务：

| 任务 | 预期行为 |
|---|---|
| 故障识别与隔离 | 检测worker失联、实例异常或请求失败；区分节点故障与单模型实例故障，按证据确定最小隔离范围；从路由撤出不健康目标并记录检测/收敛时间 |
| 按模型评估剩余能力 | 维护模型→健康副本→worker映射；模型1仍有健康副本则继续服务并降低并发；模型2的健康服务不因模型1故障被全局关闭 |
| collector降级验证 | 对每个模型的健康子集持续验证版本、镜像和容量；不因一个worker异常撤销整个集群其他模型的可用证明 |
| UNKNOWN局部隔离 | 请求/attempt关联实际执行节点，约束网关重试的潜在执行范围；仅在能证明隔离边界时缩小UNKNOWN影响范围，不把未知执行当作已停止，不盲目重放 |
| 容量不足响应 | 剩余容量不足时有界排队、限流或明确拒绝；模型无健康副本时仅该模型不可用，不自动换版本；保留结果查询和其他健康模型服务 |
| 故障恢复与防抖 | 节点重新上线后先验证版本/镜像、处理残留活动并通过真实探针，再逐步接流量；避免反复上下线造成路由震荡 |
| 故障注入验证 | 在多模型并发流量下测试节点失联、单实例崩溃、超时/UNKNOWN及反复恢复，记录各模型成功率、延迟、积压和容量变化 |

若无法确定请求实际落点或隔离潜在后台执行，仍保留必要的保守隔离，并明确报告影响范围；不会为了继续服务而跳过安全判定。

### 依赖与边界

- 首先针对XZ-31-002验证，001继续运行控制端和推理。维护001本机还需要控制端独立部署或迁移，不能直接套用002流程。
- 当前请求通过GPUStack通用入口，任务层不能可靠确定实际执行worker；节点级路由隔离和活动追踪必须先验证，不能仅将现有脚本的worker ID改为参数。
- 当前collector要求两个既定worker及对应实例均健康，需要支持经过授权的维护拓扑和剩余节点验证，同时维持模型版本/镜像约束。
- 剩余节点必须能承载对应模型；没有可用副本或容量不足时拒绝进入该维护模式，另行选择当前全局维护流程。
- GPUStack、Playground及worker直连应遵守同一隔离边界；未知活动未确认结束时，不认定目标GPU已释放。
- 双系统切换、自动关机/开机和精确吞吐目标另行验证，不自动包含在本增强中。

### 验收条件

1. 目标worker撤出后不再收到新请求，路由收敛时间可测量。
2. 既有在途请求完成或明确进入异常处理；UNKNOWN阻止宣告该节点排空，不盲目重放请求。
3. 在剩余节点容量范围内，维护全过程继续受理和完成请求，不执行全局暂停或集群副本归零；报告错误率、延迟、积压及容量变化。
4. 非目标worker及其正常推理实例不被停止或重建；目标节点实际GPU占用清除有证据。
5. 恢复节点通过真实探针后才重新接流量；恢复失败保持该节点隔离，不影响健康节点继续服务。
6. 无跨项目越权、任务遗失、重复成功计量或静默模型版本切换。
7. 模型1某worker突发故障时，在健康副本与剩余容量可用的前提下继续服务；模型2的健康请求继续完成，不触发全局暂停或全局副本归零。
8. 模型1所有副本不可用时，对模型1明确返回不可用/有界排队，模型2仍继续服务；故障与UNKNOWN的影响范围、隔离依据可审计。
9. 故障节点未经探针和残留活动检查不能重新接流量；故障恢复失败不使健康节点停止。

正式服务仍为全局受控维护及全局UNKNOWN隔离，collector要求既定节点集合健康。新增E1候选模块已在本地实现单worker别名验证、独立健康子集、持久落点/共享容量、局部隔离状态机与单次HTTP传输；未接入正式API/执行器，未提供真实运维hooks，未部署或完成实机验收。今晚P4版本、配置和测试计划保持不变。

## E2：面向用户的批处理服务

状态：已登记，待设计和估算。来源：用户明确要求。排在P4之后，与E1基本独立；不要求先实现E1，但须兼容其剩余容量准入。目标是用户一次选择一批图片，查看整体进度，按需重试失败项，最终下载全部结果包。

### 首版范围与框架复用

首版建议最多100张PNG/JPEG，使用既有普通文字提取服务；数量和总字节上限可配置。支持多选上传，不包含视频、ZIP输入上传或模型内部合批推理。采用“一个批次关联多个独立子任务”，复用现有artifact、持久队列、执行器、GPUStack、版本约束、项目授权及成功计量；批次层不另建GPU调度器。

### 实施任务

| 任务 | 交付物 |
|---|---|
| 批次协议与持久记录 | batch_id、项目/模型、批次与子任务关联、原文件名/内部条目ID映射、生命周期与进度聚合；区分上传失败、待接纳、排队、执行及终态 |
| 多图上传界面 | 多选文件、数量/格式/单文件与总字节校验、逐文件上传进度、失败补传和幂等提交；不一次性将全部文件读入服务端内存 |
| 有界接纳与公平性 | 按队列/项目/全局及模型剩余容量逐步接纳子任务，不绕过已有配额；批次条目数和上传占用也有上限，避免以批次表形成无限等待队列 |
| 批次进度与操作 | 查询总数、各状态计数、逐文件错误；取消未完成项、仅重试符合条件的失败项；明确取消与完成竞态，不盲目重试UNKNOWN |
| 输入与结果保留 | 未转成子任务的已接纳批次条目也须保护输入；成功子任务结果保留到批次下载窗口；明确上传未完成、取消、批次超时和过期的回收规则 |
| 结果打包 | 有界、可恢复的ZIP生成，包含逐文件识别结果、原文件对应表和失败清单；同名文件按条目ID区分，过滤路径穿越文件名；控制并发、磁盘、包大小和有效期 |
| 权限与计量 | 全部上传/进度/重试/下载绑定project；重复操作不重复创建子任务/成功事件；首版按成功子任务沿用现有计量，批次/ZIP不重复计费 |
| 运维与验收 | 批次/打包积压、空间、失败率和过期指标；覆盖重启、部分失败、配额不足、取消、过期、并发项目及异常恢复 |

### 依赖与边界

- 底层保持单文件独立任务；批次成功不意味着所有条目成功，必须明确“全部成功、部分失败、取消”等汇总状态。
- 100张图片不能简单等同于一次创建100个队列任务；应设计有界接纳、等待期限和项目公平策略。
- 当前输入TTL从上传计算、结果TTL从结果创建计算，尚无批次级保留；必须先补齐引用与保留策略，避免早完成结果在整批完成前被回收。
- UNKNOWN隔离与模型版本约束不能因用户点击批次重试而绕过；E1未完成时仍遵守当前全局隔离规则。
- 控制端存储、打包和下载会增加CPU/磁盘/带宽占用，需要容量预算；对象存储、大文件分片/断点续传及视频批次另行评估。
- 本项登记不代表已有用户门户、批次API或服务端ZIP下载能力，也不改变当前运行服务。

### 验收条件

1. 用户通过页面选择100张合规图片，获得稳定batch_id，可看到上传与处理进度；超限和部分上传失败可定位、可补传。
2. 各图片独立完成或明确失败，一张失败不导致整批重做；重复提交/补传/重试不形成重复子任务或成功计量。
3. 队列与存储始终受限；大批次不会绕过配额或无限堆积，其他项目在约定公平策略下可继续获得执行机会。
4. 重启后批次、条目、进度和结果可恢复；尚未派发的输入、早完成结果不会在承诺的批次处理/下载窗口内被误删。
5. 下载ZIP可逐项对应原文件，包含成功结果和失败清单；同名/恶意文件名处理安全，打包失败可恢复且不重复推理。
6. 跨项目查询和下载被拒绝；取消、部分失败、全部成功、过期、UNKNOWN及恢复路径均有明确行为与验证记录。

## E3：多执行器并发与容量验证

状态：已登记，待实现和实测。来源：用户明确要求。安排在P4之后；优先采用多个独立执行器、每进程单任务的方案，单进程线程池/异步并发留作后续优化。目标是让多个任务同时调用模型服务，利用健康副本及GPU资源；不以模型支持合批为前提，不保证增加并发必然提升吞吐。

### 首轮范围

### 依赖与边界

- 当前代码包含竞争领取、租约及fencing基础机制，但尚未完成常驻多执行器部署与完整实测，不能把“已有机制”当作扩容验收。
- 首轮同项目并发2、全局并发2仅为候选实验配置；同步流量占槽时异步实际并发减少，生产额度由实测确定。
- 当前只有全局/project配额，按模型和健康副本动态调整需与E1的容量准入设计衔接；E1未完成前仍遵守现有全局UNKNOWN隔离。
- E2批次可利用E3提升子任务并行度，但E2基本流程不以E3为前置；批次不能绕过项目公平及队列上限。
- 本轮不实现跨主机独立artifact目录、对象存储或另建broker。单进程内部并发只有在进程开销成为明确瓶颈时另行设计。

### 验收条件

1. 有两个可执行任务且配额允许时，两个执行器能同时持有不同任务并发起请求；单项目及全局额度始终有效，同步占槽正确计入。
2. 竞争领取/进程退出/租约过期/旧提交不导致任务遗失、冲突终态或重复成功事件；不承诺网络推理恰好执行一次，UNKNOWN保持安全约束。
3. 暂停、取消、恢复及缩容在多执行器下行为可解释；一个执行器退出不无故停止其他执行器，必要隔离仍按现有规则生效。
4. 所有执行器共享数据和一致配置，文件引用、配额及清理正确；已有成功结果可读。
5. 给出并发1/2的可复现对比及容量建议；吞吐不提升或错误/显存超标时保持较低并发，不以启动两个容器代替性能验收。

本项仅登记后续增强，当前常驻执行器数量和配额不变。

## E4：同步接口持久幂等与原结果复用

状态：已登记，暂缓实现；2026-10-21用户要求纳入后续开发计划。**当前优先级：中低，P4之后按业务触发条件重评**，不作为P4验收或首期OCR接口兼容的强制前置，也不因登记而改变现有同步行为。

### 背景与需求

外部消费者的[接入契约分析](CONSUMER-API-GAP.md)指出，其网关具有持久业务去重且不重试/改派，但上游调用仅带Bearer/Content-Type；body中的request_id可选，消费者自动生成的ID不保证透传。本系统现有异步任务已支持project作用域的Idempotency-Key；同步 `/v1/chat/completions` 没有持久幂等，客户端断连/超时后重新发送可能再次推理及计成功用量。X-Request-ID目前是服务器生成的诊断标识，不是幂等键。

目标：调用方用相同业务键重试时复用原请求记录和已保存响应，不重复发起应用层推理或成功计量；请求仍执行或结果未知时明确反馈，不能因超时自动重新执行。未来若新增消费者兼容 `/ocr` 或文生图入口，应复用相同机制，而非各自实现内存去重。

不承诺端到端GPU“恰好执行一次”：数据库与远端推理不是分布式原子事务，GPUStack内部网关重试也属于另一层约束。

### 优先级、收益与成本考量

| 情境 | 收益与安排 |
|---|---|
| 当前少量私有OCR验证 | 单次算力成本较低，节省重复GPU资源的收益有限；先做稳定性、容量/成本与真实消费者接入验证 |
| 已有异步任务可被消费者采用 | 优先复用现有任务幂等/查询/持久结果，避免立即建设第二套完整结果复用机制 |
| 消费者已有持久幂等且明确不重试 | 首期可由其负责业务去重，本系统保留UNKNOWN保护；不能因此宣称同步上游已具备幂等 |
| 同步调用必须支持超时安全重试、找回原结果 | 提升为高优先级，先完成稳定必传业务键与保留期约定，再承诺此能力 |
| 高成本/长耗时图像生成或重复计量争议增加 | 重新测算收益；若需要对外收费和可对账，幂等价值提高，先解决计量一致性 |

主要工程成本在并发仲裁、跨文件/数据库一致性、进程崩溃、UNKNOWN、鉴权与过期恢复，而非增加一个header。OCR响应较小，存储成本通常相对可控，但仍需量测请求量×保留期×平均结果大小及数据库/清理开销；图像大结果应走有界artifact引用，不直接无限存入数据库。不能预先承诺具体工期或“零开销”。

触发重评：消费者明确要求同步强保证；重复推理/计量事件已有可量化成本；上线高成本同步模型；或商业对账要求提出。触发后与E1–E3按实际业务价值排序，不预设必须排在所有增强之后。

### 当前阶段的替代与对外约定

- 需要可靠重查的消费者优先使用现有异步任务接口，保存Idempotency-Key、原请求体与task ID。
- 同步OCR继续作为便捷接口，明确“无同步幂等、发送结果不明不自动重试”；保留全局UNKNOWN规则。
- request_id如后续被接纳，首期只用于关联，不把诊断字段宣传为业务幂等。消费者去重不能替代本系统远端未知执行判定。
- 不建议用图片/prompt内容哈希短窗口去重：合法的两个独立请求可以内容相同，图像生成还可能期望不同结果。

### 候选解决方案

1. **键与作用域**：接受Idempotency-Key；未来兼容接口可将body request_id映射为同一业务键，两者同时提供且不一致时拒绝。唯一作用域为project+接口/操作+key，而不是API key或全局裸ID。旧客户端无键可保持旧语义；强保证渠道要求稳定必传键，服务端临时生成值不能帮助调用方重试找回。
2. **摘要与原子占位**：在现有独立PostgreSQL任务库新增同步幂等记录，保存逻辑模型/revision关联、规范化请求摘要、执行token、状态、响应/结果引用、有效期与审计时间。唯一约束仲裁并发；只有占位成功且确认提交的执行者可以发送。摘要不含密钥；规范化覆盖图片及有效参数，须事先约定相同原请求遇到目录升级的处理，不能静默换revision执行。
3. **状态处理**：同键异内容409；进行中有界等待或明确IN_PROGRESS（具体HTTP状态需消费者确认，不静默改为异步成功）；成功返回原HTTP状态/内容；已确认失败复用原错误；UNKNOWN不重放；过期明确返回过期，不把旧键直接当新任务。
4. **成功响应与计量一致性**：远端完整结束、业务输出校验通过后保存可复用响应，将幂等状态、同步活动及唯一成功事件同事务确认。大结果文件采用现有原子写入/共享生命周期锁及受保护引用，不能先回成功再异步缓存；文件与DB提交不确定时保留恢复证据。
5. **崩溃与恢复**：持久化执行意图先于发送。占位后未发送/发送前提交确认丢失、发送后进程退出、响应已到但提交未确认等情况分别判定；只有有证据未发送才允许接续，无法确认远端结束进入UNKNOWN，不能按租约到期直接重新执行。响应提交成功但客户端断连时，同键重试读取原结果。
6. **保留与清理**：建议首版响应保留24小时，幂等键墓碑保留更久；两者为待容量评估/双方约定的候选值，不是当前已发布承诺。记录与结果引用/GC联动，设置项目/全局存储及等待者上限；墓碑到期后的键复用语义必须明确，不能承诺无限期去重。
7. **安全与兼容**：每次复用仍校验当前身份/project/模型权限，禁止跨项目读取缓存；key轮换不丢失同project幂等关系，禁用凭据不能借缓存绕过鉴权。不得缓存Authorization或原始敏感日志；探针与业务计量分开。
8. **后端重试边界**：应用层幂等阻止重复客户端请求再次发送。2026-10-21用户已明确，消费者“不重试”仅为自身行为声明，不要求本系统禁重试；E4不包含关闭GPUStack重试，保留现有策略和UNKNOWN安全约束，不作为接入前置问题。

## E6：退役自建collector，复用GPUStack服务状态

状态：**2026-10-22已完成代码迁移和正式发布，线上collector已停止并永久mask，专用访问资产已清理；真实OCR、完整维护及备份恢复通过，2026-10-23新基线8小时复测通过（5760/5760、SQL一致），E6关闭。** 本项属于P4失败后的架构整改，需在新基线8小时复测前完成依赖迁移与验证；不是等待P4通过才处理的普通后续项。编号不表示顺序，**安排为E6整改 → P4重新验收 → E5立即启动**。E5仍是P4完成后的最高优先级，E1–E4保持暂缓新增实施。

### 最近讨论与决策背景

1. 夜间8小时测试在约3小时16分钟时因PREFLIGHT_UNAVAILABLE失败。collector采集异常会撤销证明，异步任务在推理发送前失败，backend intent=0。两节点当时都出现SSH MaxStartups限流，后续也曾同窗复发；SSH是高概率诱因，原日志没有采集失败阶段，不能声称每轮异常的唯一根因均已证实。见 [原因分析](../../results/maas-p4-release/CAUSE-ANALYSIS.md)。
2. 自建collector原本用SSH/Docker与控制面查询，独立核对实际镜像、固定worker集合/分布及网关策略，再向应用提供30秒新鲜证明。这个严格门禁是本项目增加的，不是GPUStack运行所必需；它使管理采集链路故障转化成客户推理不可用。
3. 大规模节点下，中心串行SSH与重复控制面查询难以维持现有周期，固定全节点共同通过的条件也不适合动态资源池。若强行按1万节点每5秒采集，理论约2000次节点采集/秒；这是简单预算，不是实测性能。当前尚无量化证明显示该额外运行成本带来必要业务收益。
4. GPUStack v2.2.3已有worker注册/心跳、GPU与系统资源上报、实例状态、路由和就绪/失联处理。用户明确：信任其服务可用性声明，由GPUStack解决其声明与实际不一致的问题，本系统不重复建立节点健康仲裁平台。
5. 据此决定**退役自建collector，而不是为了保留它继续新建专用SSH基础设施或定期全池审计**。发布时必要的版本/镜像核验保留为按需工具；正常运行不依赖这些工具在线。详见 [职责重评](GPUSTACK-TRUST-BOUNDARY.md)。

### 目标与范围

- 删除推理必须读取动态preflight、必须固定两worker都健康及约5秒SSH镜像采集的依赖，让GPUStack透明提供服务。
- 退役对象为本仓库自建maas_platform.collector、maas-collector.service及其专用SSH inventory/consumer证明链路；**不删除GPUStack worker内置collector/心跳/资源上报**。
- 保留MaaS鉴权、project/模型权限、静态逻辑模型/revision绑定、输入/输出校验、任务/文件、队列/共享配额、维护、发送活动账本、UNKNOWN和唯一成功计量。
- 保留observer与宿主机业务监控，调整其collector关键依赖项；仍观察API/DB/执行器、磁盘、积压、调用失败及GPUStack必要状态，不新增全节点重复巡检。
- 正常GPUStack状态与实例路由由其负责；超时/断连仍由MaaS正确记录为失败或未知结束，不把“信任GPUStack”解释为可以盲目重放、伪造完成或自动安全关机。
- 镜像/配置的变更核验迁入发布流程，审计按需执行；不再承诺逐请求独立验证实际容器镜像或完全固定副本分布。

- 取得独立测试资源、端口、数据目录/数据库、测试凭据和可用GPU；不能共用现网数据库，也不能让同一worker同时归两个控制面管理。资源不足可先开展本地适配，不执行现网替代实验。
- 获取并固定server/worker镜像digest及runtime、runner、网关插件版本，审查正式版安全修复、迁移与API权限差异。
- 现网部署前具备私有备份、独立恢复验证、明确维护窗口及回退方案。001/002禁止VM重启约束继续有效；管理员快照和独立克隆创建由管理员操作。

### 验收条件与边界

1. 独立正式2.3环境的上述核心回归通过，API行为和MaaS任务/结果/一次计量契约无未解释退化，保留原生身份与模型挂载隔离证据。
2. 配置回退明确区分“已保存配置”和“运行实例已更新”；独立路由、MaaS目录/业务revision及数据库不由原生部署revision自动回退。历史环境变量可能含秘密，不提交到Git。
3. 验证版本匹配、凭据权限、TLS信任、key吊销生效与故障响应；不得用全局跳过TLS或扩大key权限掩盖兼容性问题。
4. 备份恢复通过，升级及回退步骤可执行；数据库迁移后不能仅换回旧容器镜像当作恢复。自动克隆接入须使用更新后的管理员快照另验，容器重建不等于真实首启验收。
5. 交付适配代码、固定版本清单、独立验证报告和运维手册；仅计划登记或源码审查不能标成实施完成。现网切换未执行时明确写“未部署”。
6. 不把此项扩大为共享KV缓存、PD分离、GPU切分或后端合批实施；不将负载均衡/定时副本数等同于E1完整排空，不将OTA元数据更新等同于模型文件分发，不宣称已达到E7千节点容量。
