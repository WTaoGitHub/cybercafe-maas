# 后续增强计划

2026-10-21。以下为已登记、尚未实现的增强项，排在P4发布与耐久验收之后；不作为当前试点交付的前置条件。

## E1：逐 worker 排空、其他节点继续服务

状态：已登记，待技术验证和估算。来源：用户明确要求。范围包含计划维护与突发故障两条路径：维护或故障时仅目标worker退出推理，其他健康节点按剩余容量继续提供同步与异步模型服务，不全局暂停、不将整个集群副本归零。

### 范围与实施任务

| 顺序 | 任务 | 交付物 |
|---|---|---|
| 1 | 核对GPUStack v2.2.3可复用的节点/实例路由控制及实际行为；不能将maintenance等同于停止接收请求 | 能力验证及方案决策，升级另行评估 |
| 2 | 将目标节点从新请求路由中撤出，并验证路由收敛；控制模型实例调度，避免维护期间再次向该节点部署 | 可恢复的节点准入隔离 |
| 3 | 获取实际执行节点与请求/attempt关联，核对该节点在途及UNKNOWN；覆盖同步、异步和网关重试/旁路 | 节点级活动账本与排空判定 |
| 4 | 验证其余节点具有相同模型版本及足够容量；按剩余容量调整并发/排队，必要时拒绝维护 | 容量预检与过载策略 |
| 5 | 仅停止目标节点实例/worker，确认实际GPU进程退出；保存原配置、执行阶段和失败恢复材料 | 逐节点维护命令与审计 |
| 6 | 恢复目标节点，通过版本、健康和真实推理探针后重新加入路由 | 节点恢复与回退流程 |
| 7 | 在其他节点持续承载流量时，测试空闲/在途/超时/UNKNOWN、路由收敛和恢复失败 | 自动化测试、服务连续性报告 |

### 新增范围：突发故障时逐 worker 隔离、按剩余容量继续服务

与计划维护先排空再停止不同，突发故障可能已有请求失联，不能假定能正常排空。增加以下任务：

| 任务 | 预期行为 |
|---|---|
| 故障识别与隔离 | 检测worker失联、实例异常或请求失败；区分节点故障与单模型实例故障，按证据确定最小隔离范围；从路由撤出不健康目标并记录检测/收敛时间 |
| 按模型评估剩余能力 | 维护模型→健康副本→worker映射；模型1仍有健康副本则继续服务并降低并发；模型2的健康服务不因模型1故障被全局关闭 |
| collector降级验证 | 对每个模型的健康子集持续验证版本、镜像和容量；不因一个worker异常撤销整个集群其他模型的可用证明 |
| UNKNOWN局部隔离 | 请求/attempt关联实际执行节点，约束网关重试的潜在执行范围；仅在能证明隔离边界时缩小UNKNOWN影响范围，不把未知执行当作已停止，不盲目重放 |
| 容量不足响应 | 剩余容量不足时有界排队、限流或明确拒绝；模型无健康副本时仅该模型不可用，不自动换版本；保留结果查询和其他健康模型服务 |
| 故障恢复与防抖 | 节点重新上线后先验证版本/镜像、处理残留活动并通过真实探针，再逐步接流量；避免反复上下线造成路由震荡 |
| 故障注入验证 | 在多模型并发流量下测试节点失联、单实例崩溃、超时/UNKNOWN及反复恢复，记录各模型成功率、延迟、积压和容量变化 |

若无法确定请求实际落点或隔离潜在后台执行，仍保留必要的保守隔离，并明确报告影响范围；不会为了继续服务而跳过安全判定。

### 依赖与边界

- 首先针对XZ-31-002验证，001继续运行控制端和推理。维护001本机还需要控制端独立部署或迁移，不能直接套用002流程。
- 当前请求通过GPUStack通用入口，任务层不能可靠确定实际执行worker；节点级路由隔离和活动追踪必须先验证，不能仅将现有脚本的worker ID改为参数。
- 当前collector要求两个既定worker及对应实例均健康，需要支持经过授权的维护拓扑和剩余节点验证，同时维持模型版本/镜像约束。
- 剩余节点必须能承载对应模型；没有可用副本或容量不足时拒绝进入该维护模式，另行选择当前全局维护流程。
- GPUStack、Playground及worker直连应遵守同一隔离边界；未知活动未确认结束时，不认定目标GPU已释放。
- 双系统切换、自动关机/开机和精确吞吐目标另行验证，不自动包含在本增强中。

### 验收条件

1. 目标worker撤出后不再收到新请求，路由收敛时间可测量。
2. 既有在途请求完成或明确进入异常处理；UNKNOWN阻止宣告该节点排空，不盲目重放请求。
3. 在剩余节点容量范围内，维护全过程继续受理和完成请求，不执行全局暂停或集群副本归零；报告错误率、延迟、积压及容量变化。
4. 非目标worker及其正常推理实例不被停止或重建；目标节点实际GPU占用清除有证据。
5. 恢复节点通过真实探针后才重新接流量；恢复失败保持该节点隔离，不影响健康节点继续服务。
6. 无跨项目越权、任务遗失、重复成功计量或静默模型版本切换。
7. 模型1某worker突发故障时，在健康副本与剩余容量可用的前提下继续服务；模型2的健康请求继续完成，不触发全局暂停或全局副本归零。
8. 模型1所有副本不可用时，对模型1明确返回不可用/有界排队，模型2仍继续服务；故障与UNKNOWN的影响范围、隔离依据可审计。
9. 故障节点未经探针和残留活动检查不能重新接流量；故障恢复失败不使健康节点停止。

当前实现仍为全局受控维护及全局UNKNOWN隔离，collector要求既定节点集合健康；尚未实现上述局部故障降级。本次仅登记计划，不改变运行行为。
