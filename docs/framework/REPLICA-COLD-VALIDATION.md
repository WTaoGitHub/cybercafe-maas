1. **准备和保留通路**：保留002当前状态；备用003管理通道已验证可到同一控制机，后续操作前再复核。该验证不等于已实测002离线。将后续运行需要的节点配置、网络规则、批准发布/证书元数据和控制端状态私有备份到Mac；设置有界采样和停止条件。当前检查不包含配置修改或服务启动。
2. **解决接入前置**：对比002的引导与隔离代码和当前批准版本，核对证书/签名/配置范围；保留旧失败日志后，计划受控恢复网络隔离依赖，再启动引导/worker。不得把reset-failed当作修复，不盲目删除保护或套用旧控制端规则。此阶段不得先拉OCR；不重启VM、Docker、控制端或现有worker，不影响跳板的SSH通路。当前没有执行或证明恢复。
3. **隔离试点目标**：准备独立Cold OCR部署，固定已批准镜像digest、3.5GiB声明、min1/max1及专用路由/推理凭据，用唯一worker选择器限制其只落到002。正式模型保持2/2。仅新增Ready节点并不会使已达max2的正式模型继续扩容，需要明确的试点缺口和写入授权。
4. **先取证、后放行**：在第一次模型调度前确认OCR镜像缺失、缓存目录和辅助镜像状态。准备完整记录，再让试点调节器自动0→1；由GPUStack原生机制拉取镜像并启动，不手工docker pull/load。若准备阶段已发生提前拉取，降格为部分缓存或热缓存，不能继续标冷。
5. **验收闭环**：分开记录worker注册、Ready、调节发送/读回、原生调度、拉取准备、模型Ready和首次OCR成功。确认一次实际MaaS异步任务有结果、唯一尝试/成功事件/计量，UNKNOWN0；核对正式OCR探针、正式目标/配置/实例和网络边界。未观测到的分段标unavailable。冷启动上界按镜像体积、网络和初始化余量事前确定，不沿用热缓存180秒或运行中调门槛。
6. **同节点热对照及清理**：冷轮完成后保留镜像缓存，仅在试点暂停/停止且journal空后运维归零，再用相同模型和统一计时起点跑热对照。最后清理试点路由/临时key、保留证据，worker是否保留由后续部署决定，不自动退役或回收VM。

该路线能验证002上模型首次取得、初始化及调节器正确动作；由于002本次未重新开机，不能把结果写成“新快照首次开机自动接入验收”。冷/热计时必须使用一致起点；现有热报告是Apply后的时间，不能与开机到推理的全链路时间直接混比。
