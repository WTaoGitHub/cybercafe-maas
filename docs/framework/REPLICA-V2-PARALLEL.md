## 如何发挥作用

新节点无需先进入 SSH 压力采样名单。MaaS 通过 GPUStack 完整管理快照反复计算当前可执行目标；事件负责唤醒，周期读取负责兜底。以 disabled 明确不依赖压力，或以 advisory 在缺样宽限后按降级预算执行；required 仍保持严格采样要求。已有 v1 策略不自动迁移。

默认仍为串行试点。只有显式设置 `startup.parallel_startup: true`，且本轮原生实例预留可核对，才按 `execution.max_inflight_global` / `max_inflight_per_cluster` 放开启动名额。每笔更新仍是单写入方逐笔 +1，前一笔目标读回和持久确认后才能发下一笔；允许重叠的是引擎启动过程，不是同一部署的并发 PUT。

例如两张空闲卡、在途上限 2：先请求一个副本；GPUStack 将它分配到卡 A 后，即使它仍在下载或初始化，也可在重算中利用卡 B 的预算请求第二个。待两副本就绪再补齐其他可行缺口。不是每次必须等所有模型 Running。

## 当前保守边界

| 原生情况 | 行为 |
| --- | --- |
| 已分配的 scheduled / initializing / downloading / starting 实例 | 消耗一个在途名额；暂时不再使用该 GPU 的剩余显存规划新增，即使 allocated 遥测仍为 0 |
| 完全 Running 且落点合法 | 按原生 allocated / reserved 预算计算余量 |
| 尚未创建实例、未分配 Pending/Analyzing、记录多于或少于目标 | 等待原生收敛，本集群不新增 |
| Error、Unreachable、正在删除、分布式或落点无法核对 | 本集群等待；不删除记录、重试推理或伪造可用预算 |
| 本集群非受管部署有待启动实例 | 同样核对数量和落点、保留预算，不能只数受管模型 |
| 其他集群有待启动目标 | 占用全局预算，不直接消耗本集群卡预算；最终原生快照还会独立核对 |
| 规划后发生容量、全局目标、实例状态或落点变化 | 新鲜快照指纹不一致则放弃本轮，重新读取规划 |
| advisory 缺样 | 宽限/冷却持久化，预算额外收敛至 degraded_inflight_max，默认 1；有效高压不绕过 |

预留整张待启动 GPU 是为避免迟到遥测造成重复计算，不是 CUDA 显存硬隔离；GPUStack 仍决定实际落点。它不保证“一张卡一个副本”，也不保证请求第二个就一定落到卡 B。并行初期偏保守，同卡多个引擎的同时冷启动暂不作效率承诺。不可核对的未分配目标可能暂缓本集群全部新增，这优先保护资源预算。

不同模型在资源可证明时可独立继续启动，优先满足配置的最小副本和优先级。受管范围内的人工目标/配置漂移仍冻结整个作用域，须显式重新接管；逐部署人工接管隔离尚未实现。单个未知写入依旧冻结所有新增，不自动清日志。

## 启动节奏和状态

稳定期到期会主动重算，不为此补等完整周期；写入确认后下一轮及时检查是否还有安全名额。事件风暴由同一循环串行处理，保留短合并等待；断开订阅会丢弃稳定基线，完整 API 连续读取重新建立后可轮询降级执行。管理 API 失败则冻结。

私有状态包含 `parallel_safe`、`startup_reservation`、`execution_profile`、`effective_startup_limit`、全局/集群在途、当前/计算目标、压力原因及 `write_attempted`。`writes_enabled` 只表示 Apply/接管/范围配置成立，不代表资源/压力门槛已通过，也不证明发出了请求。确认目标不等于引擎已可服务。

## 验证结果与下一步

本地合并回归 **102 通过、2 条件跳过**；覆盖无新事件 0→1、缺样降级、手工漂移/暂停、确认落盘失败/超时隔离、启动上限 1/2/4、两卡同时启动、分配遥测滞后、未分配/消失/多余/异常实例、非受管占用、全局预算、多模型首副本优先，以及规划后全快照变化。一个新增测试起初向接管夹带非受管模型，被范围校验按预期拒绝；已修正测试夹具后全量通过。

替身测试不证明 GPUStack 实际会怎样分配或冷启动多快。2 项跳过需要固定 GPUStack 原生 runtime。R4 尚须在独立 OCR 试点：

1. 只读核对当前版本、在线资源、授权、原生部署、未知日志和备份材料，旧插件保持 Observe。
2. 用新镜像先 Observe；不覆盖现有人工作用中的模型，采用独立试点当前目标。
3. 验证无新事件 0→1；分别核对 required、advisory 丢样/过期/恢复和 disabled，管理 API 故障与人工接管。
4. 在资源实际允许时比较串行与并行 2/4，记录原生事件/分配/下载/启动/Running 和路由可用时间；资源不足的档位明确未验收。
5. 冷缓存与热缓存分别记录，完成真实 Higress OCR、MaaS 异步结果和唯一计量；检查已有服务受影响情况。
