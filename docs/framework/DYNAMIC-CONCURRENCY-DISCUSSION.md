## 2026-11-27 确认的职责边界

GPUStack 报告各部署的就绪副本数并负责选路和执行。MaaS 用每个就绪副本一路的规则计算发往模型入口的上限，允许下游排队。工作节点、显卡布局、模型进程和历史请求的物理落点由下游管理。MaaS 保留请求身份、并发准入、队列、同步预留、幂等和客户结果记录。

一次传输以未知结果结束时，释放这次 MaaS 派发占用，原尝试停在 `UNKNOWN`，仅作记录。任务重发另项实施。[后续需求 #87](https://github.com/WTaoGitHub/cybercafe-maas/issues/87)

例如新上限 50，仍在途的调用为 40，另外 40 笔已记录为 UNKNOWN，全局最多还可新增 10 路，各模型与异步预留仍分别生效。A4、B2、C1 的基线始终对应 7 路；三者归零后全部停止新增派发。

以下为历次讨论记录。涉及 UNKNOWN 继续占额、每卡扣额和预先选择副本的条款属于旧试点。[现行设计与验收](DYNAMIC-CONCURRENCY-IMPLEMENTATION.md)

## 开发目标与验收主线

MaaS 自动感知各模型服务的可服务副本规模，随容量变化更新该模型的有效最大并发数及相关准入参数。副本的实际就绪、健康和可路由状态决定可用容量，事件触发刷新，周期完整快照用于对账。新增副本确认可服务后开放容量，掉线或缩容后降低额度。零可服务副本时派发额度为零，容量快照过期或缺失时保守限制新增派发。

首版随副本自动更新模型和全局有效并发上限，并按配置比例重算同步预留、异步派发上限和剩余额度。同步准入、异步领取和发送前复核使用同一份有效预算。全局硬上限、同步预留比例、各模型等待队列上限、执行器进程数和每进程槽位以实测后的配置为边界。

端到端验收覆盖副本上线、批量掉线、零容量、恢复和容量状态过期。记录副本状态变更至生效的时间、各模型可用副本数、有效额度和实际在途数。验证容量增加时执行器能利用新增额度，容量下降时新准入和派发服从新额度，复核失败且确认未发送的任务安全归队。

## 背景与约束

网吧在线 worker vPC 数量可能短时间剧烈变化，MaaS 需要根据各模型实际可服务副本调整执行并发。用户明确：执行器数量不能跟随副本数持续增加，200 个模型服务副本不应要求 200 个 MaaS 执行器。

建议保留少量常驻执行器进程，每进程使用有界异步协程管理多个在途请求；副本变化调整模型预算。进程数和每进程上限仍需根据控制端资源、故障影响范围及压测确定，讨论中的 4 个进程仅为示例。

## 已确认的设计要点

1. **各模型独立计算并发上限。** 按实际可服务的副本和实测单副本安全并发计算，同一副本池的模型别名共用额度。同卡多个副本或模型按混合负载验证，同步与异步同时受模型额度、全局额度和项目额度约束。当前单项目实验的项目执行上限和等待上限分别与全局设齐。
2. **少量常驻执行器，按本地槽位逐笔领取。** 执行器有空闲槽位时，在一个数据库事务里领取一个可执行任务并预留占用。任务准备好后通过发送前复核，才取得最终派发额度并立即发送。进程之间按空闲槽位竞争，单进程上限约束占用集中程度。遇到满额或暂不可用的模型时，继续查找其他模型的可执行任务。执行器数量由实测的单进程承载能力决定。
3. **发送前复核，降额时安全归队。** 按最新额度复核，并在同一个短事务中登记通过任务的持久发送意图，提交后再发 HTTP。复核失败且确认尚未进入发送阶段时，撤销领取并归队，保留原任务和截止时间，本次延后不消耗推理重试预算。结果不明的远端执行沿用 `UNKNOWN` 处理。详见下文问题 2。
4. **同步优先使用比例预留。** 同步 API 和异步执行器共用数据库准入。全局及需要保护同步的模型按有效额度计算预留，异步最多占各层有效上限扣除预留后的额度，同步可用全部剩余额度。已发出的异步任务继续按原流程收尾。
5. **异步保留全局队列上限，另按模型限制等待数。** 复用现有持久队列，受理时同时检查全局和模型等待上限。首版按模型配置等待上限，并发额度随可用副本调整。队列候选深度约为 `同步预留和混合负载下的保守异步完成速率 × 可接受排队时间`，并为推理、结果提交和截止时间留出余量。以等待 30 秒为例，每秒完成 5 个或 0.5 个任务时，候选等待上限分别为 150 和 15。优先看按期完成数，队列接满后明确拒绝新增提交。

## 有效额度与同步预留联动

2026-11-18 确认采用比例联动。全局有效额度取当前可服务总容量与配置全局硬上限的较小值。同一副本池只计一次，共享 GPU 的容量采用混合负载验证后的预算。每个模型也按自己的有效容量和硬上限计算额度。

全局及启用同步保护的模型按 `同步预留 = 向上取整(有效额度 × 配置比例)` 计算。`异步上限 = 有效额度 − 同步预留`。新异步派发同时检查异步上限和同层同步加异步的总占用，继续受项目和本地槽位限制。同步请求可使用该层的全部空闲额度。

以 **25%** 为起测比例，以下是同一层额度的计算示例。

| 有效额度 | 同步预留 | 异步上限 |
| ---: | ---: | ---: |
| 8 | 2 | 6 |
| 6 | 2 | 4 |
| 4 | 1 | 3 |
| 1 | 1 | 0 |
| 0 | 0 | 0 |

启用同步保护且只剩 1 个额度时，该槽位留给同步，异步继续排队。有效额度为 4 且同步已占 2 时，即使异步上限为 3，异步最多也只能占 2 个。降额后按新额度处理准入和发送前复核，已发请求沿用原收尾流程。压测覆盖容量降到 1 和恢复，以及同步优先对异步按期完成率的影响，实际比例由压测确定。

## 执行器技术选型

首版沿用 Python。每个执行器进程运行一个常驻 `asyncio` 事件循环，以本地槽位限制在途协程，复用 HTTPX 连接池并集中续租。现有 OCR 适配器已经使用异步 HTTP，同一进程可以在等待 GPUStack 响应时处理其他任务。同步数据库调用和文件操作放入有界处理池，重型本地处理单独限流。保留现有领取事务、发送前复核、未发送归队和 `UNKNOWN` 恢复规则。

从 2 个进程 × 4 个槽位起测，记录控制端 CPU、内存、事件循环延迟、数据库锁等待和 GPUStack 响应时间。若瓶颈在数据库、网关或 GPU，先优化对应环节。若优化后实测仍是 Python 执行器本身的 CPU 或内存开销限制目标容量，用同一负载小范围对照 Go。Rust 留待有明确的内存或延迟目标时评估。当前尚无语言对照压测结果。

## 问题 1：执行额度如何控制 4 个执行器

执行器领取任务时，共同经过数据库事务中的“检查额度并占用额度”步骤。额度由执行器共享，不预先平均分成 4 份，也不是每个进程各有一份完整额度。

以共享上限 10、当前占用 9 为例：

1. 执行器 A 取得共同的数据库行锁，检查占用与上限。
2. A 领取任务并将状态改为 `RUNNING`，这条记录代表新增一个占用；事务提交后总占用为 10。
3. B、C、D 随后取得同一把锁，看到占用已到 10，暂不领取受该预算约束的新任务。
4. 后端执行结束并提交终态后，空出的共享额度可由任一执行器申请。执行器的本地槽位在当前任务的结果处理完毕后释放。

检查与占用必须在同一事务、同一共享锁保护下完成，避免多个进程同时读到“剩余 1”后各自派发。当前实现从任务和同步活动记录计算占用，没有另设一个需要手工递增、递减的总计数器。

锁只覆盖数据库准入事务。事务提交、释放锁后才发送推理请求，不在等待 GPU 响应期间持有这把锁。

## 追问：同步请求不经过执行器，如何共享额度

同步请求由 MaaS API 进程在转发前自行检查并占用额度；异步任务由执行器领取时检查并占用额度。两条路径共享额度存储和锁，无需把同步请求改为经过执行器。

```text
同步：请求 → MaaS API → 数据库检查并占用额度 → GPUStack
异步：持久队列 → 执行器 → 数据库检查并占用额度 → GPUStack
```

例如 7 个已获最终授权的异步任务、2 个同步请求已占用全局额度 10 中的 9 个。新同步请求与执行器竞争最后一个派发额度时，同一把锁保证只有一方成功。动态模式下，领取还会统计待复核的预留，最终派发依据已授权占用。后端终态提交后，异步本地收尾从动态派发的占用统计中移除。

静态模式使用配置中的全局、项目上限。动态模式下，同步准入、异步领取和发送前复核读取同一份数据库预算，同一上游副本池的逻辑别名共享预算。各进程仅凭本地额度快照自行放行会产生重复授权风险。

保证范围是共用额度存储且经过这些检查的 MaaS 入口。不同数据库的 MaaS 部署不会自动共享额度，直连 GPUStack 的请求也不计入；入口边界须保证客户不能绕过 MaaS。

## 追问：同步请求拿不到数据库锁，是否等待

会等待。当前采用普通 `SELECT ... FOR UPDATE`，持锁事务提交或回滚后才能继续；数据库事务配置 `lock_timeout = 5s`。该值是单次锁等待的上限，不是整个 HTTP 请求的总时限或必然等待时长。

- 在锁等待超时前取得锁：继续统计占用；有额度才预留，无额度返回 `SYNC_CAPACITY` / HTTP 429。
- 锁等待超时：数据库抛出锁超时异常，当前通用 API 异常处理返回 `SERVICE_UNAVAILABLE` / HTTP 503，不等同于容量不足。
- 请求等待的是短暂的准入事务结束，不是已有推理请求完成。

当前同步入口通过线程池运行数据库准入和收尾，锁等待发生在执行数据库调用的线程。检查与预留仍在同一个事务内。

## 问题 2：降额后，复核失败的未发送任务归队

**2026-11-18 用户确认**。异步任务领取后，在发送给 GPUStack 前按最新共享额度复核。复核不通过且能确认尚未进入发送阶段时，撤销本次领取，将原任务安全归队，等待重新取得执行资格。本决策取代 [已领取任务保留资格的候选方案](https://github.com/WTaoGitHub/cybercafe-maas/issues/60#issuecomment-6943508045)。

1. **复核和登记发送意图在同一短事务中完成。** 额度更新、同步准入与异步复核通过同一数据库协调机制串行判定。复核校验当前领取 token、租约和任务状态。通过时登记持久发送意图，提交成功后释放锁，再向 GPUStack 发送 HTTP 请求。本次领取和最终派发授权只计一次占用。
2. **容量复核失败时安全归队。** 在事务内确认本次领取仍有效且没有发送意图，记录本次尝试为 `DEFERRED`，解除租约和占用。任务保留原 ID、幂等关系、输入和截止时间，等待下次符合派发条件。本次延后不消耗推理重试预算。取消或过期按原规则进入终态，执行器在结束本次处理后释放本地槽位。
3. **持久发送意图划定归队边界。** 只有收到数据库提交成功的确认才允许发送。发现已有发送意图时，沿用现有完成和恢复流程。远端执行结果无法确认时按 `UNKNOWN` 处理，避免仅凭超时或进程退出重派。

例如模型预算降为 4，已有 3 个授权占用，还有 5 个已领取但未授权的任务。其他限额允许时，最多再授权 1 个，其余复核失败的任务归队。最终复核应区分已授权占用和待复核领取，避免待复核任务彼此占满最终派发额度。同步请求继续参与同一预算。队列领取也检查容量，归队后须等到重新满足派发条件，避免持续领取和退回。

现有 `begin_backend()` 已接入动态预算复核。降额归队复用 `DEFERRED`，阶段 2 已用隔离 PostgreSQL 验证未发送任务归队和多执行器竞争。后续继续验证已授权执行、额度归还与降额并发时的行为。

## 额度何时归还，以及 UNKNOWN 如何影响缩容

**用户确认将发送前记录可能落点、取得可信终态后自动归还额度纳入同一动态并发 feature。** 区分共享推理额度、异步领取预留和执行器本地槽位。同步 API 和异步执行器继续使用同一个 PostgreSQL 账本。按本次执行的唯一 token 写入状态，额度由准入时统计占用得出，重复终态只生效一次。

| 执行情况 | 额度处理 |
| --- | --- |
| 已领取，发送前复核失败 | 确认没有发送意图后，在原任务归队的事务中释放领取预留。任务保留原 ID、截止时间和重试预算。 |
| 后端执行已确认结束 | 成功、明确失败或确认取消均可作为终态。终态提交后，共享额度可由下一次符合规则的同步或异步请求使用。本地槽位继续约束结果校验和保存，直到本次本地处理结束。 |
| 已授权，远端结束情况无法确认 | 将本次执行记为 `UNKNOWN`，保留可能占用的额度和隔离。执行器本地处理退出后可以释放本地槽位。任务超时、客户端断开、租约到期和 worker 重新就绪都不足以证明远端执行已结束，原请求不自动重跑。 |

首版复用原派发迟到的完整可信响应自动结清。如果连接彻底丢失，按执行 token 查询上游终态须以经过验证的后端能力为前提。运维可以根据真实执行结束证据结清，例如确认原执行进程已退出，并确认该请求无法在其他目标继续运行。只收到取消确认收件时，仍需等待后端确认执行终止。任务结果和计量继续通过既有提交规则处理。

**确认容量下降就提交新上限，无需等待 UNKNOWN 结清。** 例如原上限为 100，80 个请求已在途，其中 40 个失联后转为 `UNKNOWN`。新上限降到 50 时，40 个正常在途和 40 个 `UNKNOWN` 合计仍占 80 个。首版可新派发 0。占用降到 49，且模型池、同步预留等其他准入和隔离检查通过时，才有 1 个新增名额。已经授权的在途继续收尾，只有领取预留的任务按新预算复核。

健康资源上的 10 个理论余量需要单独验证。只有确认 40 个 `UNKNOWN` 的所有可能落点均已从新路由和容量计算中排除，且这些目标与健康资源的共享 GPU、网关重试和回退范围都不重叠，才能按健康资源的 40 个在途计算 `50 − 40 = 10`。仍须遵守适用的全局、项目、模型和异步上限。不确定记录继续保存在原资源下，相关资源恢复接单前须核对遗留执行。当前实现按逻辑模型、路由和容量池隔离，并将 `UNKNOWN` 计入全局占用。逐副本和共享 GPU 的额度核算仍待开发和验证。落点完全无法界定时沿用整库保护。见[当前隔离契约](../../deploy/maas/INFERENCE-QUARANTINE.md)。

开源方案提供了几条参考原则。Kueue 按队列限制新准入，Kubernetes Job 支持等待旧 Pod 终态后再替换，Ray Serve 的取消需要执行端配合，Temporal 对可能重跑的 Activity 要求考虑下游幂等。MaaS 采用这些原则设计共享资源隔离及终态归还。 [Kueue](https://kueue.sigs.k8s.io/v0.17/docs/concepts/cluster_queue/#stoppolicy) · [Kubernetes Job](https://kubernetes.io/docs/concepts/workloads/controllers/job/#delayed-creation-of-replacement-pods) · [Ray Serve](https://docs.ray.io/en/latest/serve/http-guide.html#request-cancellation) · [Temporal](https://docs.temporal.io/activity-definition#idempotency)

## 代码依据与验证边界

- [同步准入与推理入口](../../maas_platform/sync_ingress.py)：`begin()` 锁定 `maintenance` 中 `id=1` 的记录，检查共享占用并插入同步活动；`infer()` 在提交准入后转发请求。
- [异步领取与终态记录](../../maas_platform/service.py)：`claim()` 使用同一条维护记录的锁统计占用并领取任务；`complete_backend()` 按任务 ID 和执行 token 提交后端终态。
- [UNKNOWN 隔离](../../maas_platform/quarantine.py)：按发送时持久化的逻辑模型、路由或部署池匹配，缺少历史路由证据时整库隔离。[占用视图](../../maas_platform/migrations/012_inference_quarantine_scope.sql) 同时统计正常授权和未结清的 `UNKNOWN`。
- [数据库事务](../../maas_platform/db.py)：锁等待超时 5 秒、语句超时 15 秒；事务结束后关闭连接。
- [API 异常处理](../../maas_platform/api.py)：`ServiceError` 保留明确错误，其他异常返回通用 503。
- [部署配置](../../deploy/maas/compose.yaml)：API、executor 复用共享应用配置与同一个任务数据库。

按执行终态归还动态异步额度已通过隔离数据库回归。真实网关的副本级隔离和断连后的逐请求终态查询仍待验证，详见[设计与实施方案](DYNAMIC-CONCURRENCY-IMPLEMENTATION.md)。
