# 规模调节器：闲置资源到可服务容量的启动效率

2026-11-12 · 补充设计，待实现及验证 · [Issue #39](https://github.com/WTaoGitHub/cybercafe-maas/issues/39)

调节器的两个核心目标是：**按策略把可用资源转化为实际就绪容量，并尽快完成这个转化。** 只证明副本目标被写入、或为了避免失败而长期全局串行，不能算启动效率完成。本文补充[持续对账改进方案](REPLICA-RECONCILIATION-IMPROVEMENT.md)，本轮不修改现网。

## 1. 两个时间目标

- **首副本可服务时间**：从 GPUStack 首次报告新增可调度资源且模型有授权缺口，到首个新增模型副本通过原生就绪检查、路由可用。无服务时优先满足业务策略中的首副本需求。
- **目标容量就绪时间**：从上述起点到本轮资源预算和策略允许的目标副本全部就绪。已有服务时，衡量扩容真正释放了多少可用容量。

目标数写成 2，不等于两个模型已能服务；镜像下载 100%，也不等于引擎初始化和网关同步完成。既有活跃任务的吞吐、模型质量和单次推理性能另按 E3/E10 验证，不能用副本数代替。

## 2. 分阶段定位耗时

| 阶段 | 采集的时间点 | 主要负责方 / 优化方向 |
| --- | --- | --- |
| 资源出现 | 原生 Ready 且满足可调度条件 | GPUStack；MaaS 读取权威状态 |
| 规划与写入 | 收到事件、完成快照、动作发送和读回确认 | MaaS；事件快速唤醒、合并重算、避免不必要固定等待 |
| 调度与准备 | 实例创建、分配、原生可见的拉取/准备状态 | GPUStack；受预算约束的并行，复用现有分发与缓存 |
| 引擎启动 | 原生可见的加载/初始化到就绪 | 模型引擎；区分权重加载、CUDA 初始化、必要预热，专项调优 |
| 路由与可服务 | 原生 Running/健康及路由可用，试点真实推理完成 | GPUStack/Higress；实例更新与动态路由验收 |

仅记录实际上游可观察到的时间点，缺少某段就标记 unavailable，不通过虚构时间补齐统计。就绪依据复用 GPUStack 原生状态；真实 OCR/异步探针用于受控验收，不新增每次请求前的 SSH 或镜像实物证明。

## 3. 正常快路径与保守退路

### 3.1 事件后及时行动

收到 Ready 或容量变化事件即唤醒，读取完整现状，强制门槛通过后提交可执行动作；30 秒周期用于兜底，不是每次上线必须等满 30 秒。实例就绪事件也应立即释放启动预算并继续填补缺口，不等下一周期。

容量稳定等待要区分首次可用、抖动和断线恢复。候选快路径稳定窗口为 2—5 秒，抖动/恢复可采用较长窗口；只比较影响放置的身份、容量和部署字段，不被心跳时间变化不断重置。窗口须实测，不宣布已有延迟保证。

advisory 的首次可信资源、目标缺口大于 0、没有待确认写入且有保守启动名额时，建议允许一个显式授权的“首副本快速启动”，不必先等待补齐可选压力采样。缺样仍标记未知；只有这一个起步名额，后续按降级间隔和在途预算执行。required 模式不适用此例外。新策略需明确开启，旧 schema 不改变语义。

原方案的 30 秒缺样宽限、60 秒新增间隔与全局在途 1 是保守候选，不作为全部扩容动作的永久上限；有可靠资源和执行预算时使用正常快路径。

明确不部署压力数据源的环境，应显式选择 disabled，并使用经过试点验证的启动预算；不应长期假装处于“采样故障”而永久全局串行。有数据源的 advisory 在临时缺样时可降低预算、延长间隔，降级预算仍应配置并验证，初始 1 不是未来几百节点的固定值。required 继续保持严格依赖。本条细化前一方案“无 feed 也可起步”的可用性设计，避免可选监控变成效率瓶颈。

### 3.2 受预算约束的并行启动

增加可验证的启动预算：全局/集群同时启动数量、每次目标增量，以及已有实例和未分配实例的资源预留。单一写入方与“一个未知写入都不能继续”保持不变；并行启动不等于并发发送相互覆盖的部署更新。

首轮依次对比在途上限 1、2、4，必要时再验证有界批次。数值只用于试点，不能直接认定 4 最优。多个空闲 GPU 可以由一次确认的目标增量释放多个启动名额，也可以由连续已确认的小步更新填满名额；每次都要重新核对原生资源和已有意图。

当前实现有两处需要一起改：

- planner 在任意受管模型未全部 Running 时冻结全部新增；
- writer 固定每次 +1，全局/集群在途又固定为 1。

只提高一个配置值无法获得有效并行。需要按部署跟踪待启动、已分配和未分配实例，将已有目标与启动资源预留计入预算；没有安全计入的 Pending 不能当作免费空闲容量，也不能每轮重复算成新的需求。资源/落点无法证明可行时，该范围退回串行。

不同部署在共享预算内独立推进，某个模型卡在下载或初始化时不应无条件冻结所有其他模型。卡住的实例仍占用其资源和启动名额；失败隔离、超时告警不能靠删除占用记录伪造空位。

GPUStack 决定实际落点。优先利用已验证的原生 spread 等放置配置，但不能承诺“并发 4 就一定分到 4 个 worker”。逐 worker/GPU 的强启动限额只有在原生放置约束和实际预算可核对时才能启用；否则先用集群与部署级预算，不另写节点分发调度器。

### 3.3 先形成可服务能力，再补齐规模

沿用策略的首副本优先级、最小副本与权重。无服务时优先让重要模型至少一个副本就绪；后续名额再按策略填充，不能被同一个低优先级模型的批量冷启动占满。

已就绪实例持续服务，扩容不为追求重新均衡而迁移它们。不因启动速度快就绕过副本上限、低报显存预算或替换模型版本。

## 4. 缩短模型自身的冷启动

- 复用已有私有镜像仓库、固定摘要与原生拉取能力；梳理 runtime:pause 等辅助镜像依赖，避免只有主镜像走局域网、辅助镜像仍成为公网瓶颈。复用[辅助镜像 Issue #57](https://github.com/WTaoGitHub/cybercafe-maas/issues/57)，具体原生配置须验证。
- 复用已设计的独立只读模型目录、可写缓存与原生模型文件能力；缓存命中和未命中分别计时，不把临时 VM 内上一次下载视为长期缓存保证。
- 模板预置常用固定镜像/必要依赖、已验证的共享权重或局域网缓存可作为独立分发优化；不得把 worker 身份或会话凭据打进模板/共享目录。涉及母版时另行封版验收，不阻塞 MaaS 控制逻辑本地开发。
- 预取与预热要有额度，优先服务重要模型；避免所有克隆同时拉满仓库带宽。复用原生机制，不开发新的镜像下载队列作为首发前置。
- OCR/LLM 等引擎加载、CUDA 初始化、线程与预热差异交由相应运行时专项画像；调节器使用实际就绪反馈控制后续名额，不声称一套初始化参数适合所有模型。

## 5. 度量与验收

同时报告首副本可服务时间、目标容量就绪时间、新增 Ready 副本/分钟、在途等待、失败/重试和各可见阶段耗时。按模型、冷热缓存、节点数、并发档分别记录；不能把冷拉取与热缓存混成一个结论。

同时观察控制端 CPU/内存、仓库带宽、节点写盘压力及已有推理服务的延迟和错误。选择能缩短总就绪时间且不过度干扰现役服务的并发档，不能仅凭同时 Starting 的实例多就认定优化成功。

报告每轮样本数、P50/P95及原始分段证据；样本不足时明确说明，不能把少量测试的百分位当作生产 SLA。规划与写入延迟以秒级为优化方向，缓存/模型加载和全池就绪时长先测基线再定具体目标。原方案 90 秒为保守正确性验收上界，不是正常启动效率目标。

关键测试：

1. 一节点/多节点、冷热缓存分别比较串行与并行 2/4 的首副本时间和总就绪时间，确认是否因网络/磁盘竞争反而变慢。
2. Ready 事件和实例就绪事件不额外等待 30 秒周期；重复事件不重复占用启动名额。
3. 没有压力 feed 的首副本快路径、后续保守节奏与 required 拦截分别验收，不伪造低压数据。
4. 未分配 Pending、目标已增加但实例尚未创建、单模型初始化卡住时，核对资源预留和其他部署可用的启动预算。
5. 在途上限、模型上限、显存、单一写入方、未知写入隔离与人工接管保护不能因并行优化失效。
6. 原生实例 Running 后核对 Higress 动态路由、实际 OCR/异步成功及唯一计量，证明形成真实服务能力。

## 6. 纳入实施计划

沿用 R1—R5，不另起平行项目：R1 增加启动阶段和启动预算契约；R2 增加事件快速唤醒、阶段时间及目标缺口观测；R3 分独立 feature 完成安全可用性路径与可配置并行路径；R4 比较串行/并行、冷热缓存并验证真实服务；R5 采用实测参数受控发布。缓存、辅助镜像、模板预置沿既有分发事项独立推进。

核心可用性修复可先用保守预算发布，但启动效率项不得因此标记为完成。已知当前两台 worker/当前模型的实验不能外推千节点。当前人工维持的副本和配置未修改，未执行 VM/worker/Docker 引擎重启。
