# OCR与多媒体文件能力分阶段计划

2026-11-02，用户采纳讨论并要求记录，后续按优先级选择实施。当前仅设计登记，无API、媒体类型、大小限制、部署或存储配置变更。归入E14公共文件/契约能力、E10图片/PDF OCR与E15非OCR模型适配，不新增重复E项。

## 决策与当前差距

保留两个公共路径及已有调用方式：

- `POST /maas/v1/artifacts`：原始文件字节上传，返回id、size、sha256，不是multipart或base64。
- `GET /maas/v1/artifacts/{ident}`：用artifact ID下载；输入ID来自上传响应id，结果ID来自任务result_artifact_id。鉴权及project隔离保持。

当前底层可保存任意字节，但上传白名单仅PNG/JPEG、text/plain、application/json、application/octet-stream，默认输入10MiB。application/pdf、audio/*、video/*尚未正式开放。octet-stream保存成功不意味着模型支持对应文件。

现有OCR适配器仅处理PNG/JPEG，执行器将结果统一序列化为JSON；不能把它宣称为可输出原生图片/音频/视频的任务框架。上传接收及下载读取会将整个文件放入内存，小图片可用，大PDF/视频及并发传输需另行评估。

OpenAPI保持第一版结构，Headers显示不清曾是Swagger主题文字/背景对比问题，不能因UI显示而虚构body的file字段。未来接口变更必须同步OpenAPI及实际入口，而不是仅补文档宣称可用。

## 第一阶段：优先完善现有图片OCR

定位：当前近期优先项，先保证既有OCR能力、接口说明和兼容性；具体feature由后续排期选取，不立即启动全部实现。

- 核对同步/异步、上传/下载、各入口路由与鉴权，补正确调用例子、参数/错误和能力说明，复用已提前的对外API优化计划。
- 保持原始图片上传→artifact引用建任务→查询→结果下载流程。已讨论“一步上传并创建任务”是便利性候选，可在同一任务接口增量支持内嵌图片；字段形式/大小/幂等尚未冻结，不作为当前能力或必选前置。
- 若选择一步提交：图片输入与已有artifact引用互斥，复用原任务返回、查询/取消与幂等机制；处理文件保存/任务提交失败、重复文件、配额及GC，不用同步request_id代替持久幂等。仍保留两步接口供复用文件及后续大文件使用。
- 当前10MiB图片场景不强制先做流式改造，不因多媒体远期需求扩大近期范围；不更换OCR模型或降低质量/资源保护门槛。

完成标准：已选feature输入/输出与鉴权/限额明确，原接口回归、真实同步/异步/下载通过，文档和实现一致；未选功能明确标待办。

## 第二阶段：支持PDF OCR

E14负责通用文件/契约增量，E10负责模型或逐页渲染适配及质量，不另建PDF专用上传/下载路径。

- 上传明确允许application/pdf，校验真实格式，冻结文件字节、页数、加密/密码、损坏文件及资源限制；不凭扩展名或octet-stream绕过。
- 优先“一个PDF→一个异步任务”，引用同project的artifact。模型原生处理PDF或内部逐页渲染，由已选适配器决定；限制DPI、总像素、内存、总期限与单次执行预算。不是模型名称支持PDF就自动可接入。
- 结果按页组织，声明页码/坐标、文字、表格或Markdown等真实支持范围；保持既有任务终态；部分成功的业务定义、聚合及收费由下游处理，本系统不新增部分成功任务状态或计费逻辑。PDF页面输出契约另行冻结。
- 原PDF下载返回application/pdf；识别JSON及派生文件通过统一artifact引用访问。多个输入/派生文件若纳入处理，需扩展当前单输入关联，确保任务与全部引用的权限、完整性和生命周期保护。
- 在已验证安全小文件限额内可先保留内存传输；若目标较大PDF/并发使内存预算不可接受，先完成所需流式能力再放宽限制，不能仅调大max_input_bytes。

完成标准：PDF输入/页数/异常/取消超时/版本/结果页码、project隔离、配额/清理、OCR质量和资源均有实测，能力查询及OpenAPI更新；保持图片OCR兼容。

## 最终阶段：统一多媒体文件上传下载

E14承担公共机制，E15承担文生语音、文生图、文生视频、图生视频等模型与业务适配；E10不负责音视频生成。按实际引入的模型逐类开放，不一次允许所有MIME。

- 扩展媒体类型和类别限额：图片、PDF、音频、视频；实际格式/解码及尺寸、时长、页数等由文件层与适配层分工校验。纯文本提示词通常直接放任务请求，不要求先上传文件。
- 让适配器/执行器保存二进制产物。任务result_artifact_id继续指向结果JSON，JSON内用files等结构引用一个或多个媒体artifact及媒体类型、大小、尺寸/时长等元数据；该结构是设计候选，正式字段在实施前冻结，原OCR输出保持兼容。
- 媒体元数据、任务成功、产物关联及成功计量需一致性控制；失败/取消/提交确认丢失时不发布错误引用、不误删有效文件，孤儿清理可兜底。不得只在JSON写一个无法管理的外部URL。
- 所有生成媒体计入项目/全局配额；输入、派生产物与结果采用明确TTL、活动引用保护及GC策略。结果JSON仍可访问而媒体已过期时的行为，与E13生命周期提示协调，不因本登记宣称E13完成。
- 需要时流式上传到临时文件，增量计算长度/哈希及配额控制，完整落盘并提交元数据后才发布ID；中断临时文件须有清理机制。大文件写入不长期占用全局生命周期锁，应重新设计暂存/提交及GC协调，不能简单把现有整文件锁延长。
- 流式下载前仍校验权限、期限和完整性，处理与GC的竞争并提供正确Content-Type/Content-Length；当前下载每次整文件哈希的实现需共同评估，不能为流式而取消完整性保证。Range/206、断点续传及播放器拖动在视频需求驱动下实施，流式本身不等于这些能力。
- 分片上传、对象存储、直传或签名URL作为后续可选扩展；不强制首版建设，不新增模型分发调度器。

完成标准：每类已开放媒体有真实上传/生成/下载/取消/超时/过期/配额/并发与故障验收，旧OCR/PDF回归通过，文档反映实际范围。大文件内存、磁盘、锁持有和网络预算可解释，不能仅以单次传输成功验收。

## 排期和操作边界

顺序为图片OCR完善→PDF OCR→按需多媒体文件能力。该顺序细化对外API/E14/E10/E15功能演进，不代表全平台E8/E7等必须等所有阶段结束；根据实际优先级选择独立feature。当前不启动模型安装、流式改造、存储扩容、公开端口或负载测试。每feature验证后提交并立即push；遵守AGENTS、禁VM重启、无collector及无未知请求重放约束。

## 后续独立文件服务

上传下载计划先拆为独立服务，由现有 MaaS 网关转发，调用方继续使用原 Base URL。专用对外入口就绪后，接入同一个文件服务并验收实际链路，调用方仅切换文件接口的 Base URL。两个阶段均沿用 artifact 路径和任务引用语义。阶段顺序、隔离要求和验收见[后续增强计划 E14](ENHANCEMENTS.md#e14-后续增强独立文件服务与对外入口)。
