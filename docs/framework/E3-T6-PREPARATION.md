# T6：输入更新与全周期预检

## 边界

只增强测试工具，不更新MaaS业务镜像、GPUStack、worker或Docker引擎。不得重启VM。原始manifest、T5及历史失败证据保持不变；不会续期已有文件、增加配额或清理有效文件。

上传引用不是图片内容身份。新旧manifest只允许`input.image.artifact_id`变化，逐项核对原图SHA256、数量、顺序、其他元数据及推理参数；文字参考只允许整体manifest摘要变化，逐图校验标准不变。普通40张必须与50张混合集的前40张完全一致。旧证明继续绑定旧manifest；新引用、质量参考和T5证明由独立、不可覆盖的刷新收据关联。正式每点另记录实际workload摘要，不能覆盖旧manifest冒充原文件ID。

## 一次性流程

入口：`scripts/maas/runtime/run_t6.py --config <私有配置文件> --execute`。配置和日志只保存在私有目录，不提交Git。默认不加`--execute`只做dry-run。

私有配置必须提供：`template_file`、`claim_proof_file`（完成的T5）、`reference_mu_proof_file`（同profile的T3-MU）、`expected_runtime_file`（已核对的当前运行快照）、`baseline_parameters_file`、新`output_directory`、新`run_id`及`run_tag`。

1. 核对冻结证明、业务镜像、精确当前运行快照、空闲/无UNKNOWN/未暂停及50张原图哈希。
2. 零重试上传50张原图，逐次落盘意图和回执；生成普通/混合集的新引用、质量文件及刷新收据。中断不恢复、不重传不确定请求。
3. 检查全部50个新输入都能覆盖从准备时起6小时的预留结束时间。正常24小时上传有效期足够，无须修改业务保留策略。
4. 保持原运行参数，提交50个真实诊断任务，各图一次，核对唯一执行、计量、下载和文字结果。准备队列必须至少可容纳50个任务；不提高队列或并发。这是准备探针，不是T6候选或容量通过。
5. 按实测普通/混合结果大小、T3-MU最快观测速率，预估9个容量窗口、4个延迟窗口、混合资格测量及两小时分段、突发、尾部结果，并加25%余量。项目/全局配额均保留10%，磁盘保留至少max(2GiB,配置最小值)；不抵扣尚未发生的过期清理。预测不是硬上界，业务配额保持生效。
6. 仅`READY`允许顺序执行完整T6确认和两小时阶段；`BLOCKED_STORAGE`直接停止，不能拿退出码0或50个准备任务成功当成T6通过。

确认阶段与两小时阶段开始前重新核对运行画像、空间和预留时间；每点改变参数前重新核对全部输入、收据、预检摘要及有效期。实际使用的输入还由每点准备流程核对内容。两小时阶段另保留原有混合资格/空间核对。

后台入口显式处理SIGINT/SIGTERM，只停止当前测试驱动；阶段中断记录检查状态，不自动恢复运行参数、不解除UNKNOWN、不重放请求。中断后仍须核对意图、受理、执行、计量、结果及当前运行状态，再决定是否执行有门禁的恢复。

## 证据

准备目录包含：新旧引用摘要、`refresh-private.json`、`reservation-private.json`、逐请求意图/回执、准备前后运行快照。流水线另记录`pipeline-status-private.json`，确认与两小时阶段绑定同一刷新收据和预检摘要；输出目录必须全新。

工具回归：145通过、13项因缺少独立数据库等专用条件跳过，跳过不等于通过；不是145个真实OCR验收点。真实50图准备探针及T6结果另行记录。
