# GPUStack Server 内副本策略插件设计

2026-11-05 · 第一阶段设计 · [GitHub Issue #39](https://github.com/WTaoGitHub/cybercafe-maas/issues/39)

## 目标与范围

**项目术语。** 在本项目范围内，VPC、VM、宿主机、克隆机均指由网吧管理员管理、从特定镜像版本克隆创建的虚拟计算机。下文的 worker 指运行在该虚拟计算机上的 GPUStack worker。

**第一阶段只响应 GPU 上线并扩容。** 新增或恢复的 GPU 确认可调度后，按最新资源和策略为多个模型计算扩容目标，再通过 GPUStack 执行。策略更新可重新计算扩容方案。第一阶段不响应 GPU 下线，不因下线生成动作，不实现缩容或归零。快照中的失联设备只用于核对当前可用容量和阻止过期扩容计划。模型清单、比例权重、优先级可预设并在运行中修改。A/B/C 和 2:3:5 作为验收样例。GPUStack 继续负责调度、实例生命周期和路由。插件同时负责控制自身引入的启动与下载压力，避免批量上线或恢复时挤占在线推理和控制面。

**后续阶段保留设计，第一阶段不实现。** 资源下线按预设策略自动缩容。 在启用写入的范围内，插件默认只缩额外副本，单模型自动缩容下限默认是 `1`。只有明确配置为 `0` 的部署才允许自动归零。运维在发布策略时确定授权范围。每次动作由插件核对容量、写入边界和批次预算后执行。归零保留部署、路由和配置，GPU 恢复后自动拉起。资源不足时按优先级计算保底，实际缩容仍受各模型的授权下限约束。

第一阶段支持多个独立部署和多张独立 GPU，单个副本使用一张 GPU。多卡副本、跨 worker 分布式推理、CPU offload 和共享显存模式待单独适配。每个模型可有不同的已验证显存规格和设备适配约束。规划规模和性能上限由验收确定。

## 组件与启动

| 组件 | 设计 |
| --- | --- |
| 插件适配层 | 将 Python wheel 安装进 GPUStack Server 镜像，通过 `gpustack.plugins` entry point 注册 `gpustack.extension.Plugin` 子类。镜像和依赖固定到已验收版本。使用 `setup_start_cmd` 接收配置路径和模式，在 `async_tasks()` 中启动受监管的异步任务。 |
| 事件与状态适配 | 订阅 Server 内的 `Worker.subscribe(..., replay_existing=False)`。事件只标记受影响范围需重算，任务另读全量状态。对实例变化、启动、重新订阅、周期校验和配置更新也执行对账。 |
| 纯策略模块 | 输入不可变策略版本和资源快照，输出目标副本向量、可放置证据、原因与候选动作。与 FastAPI、GPUStack ORM 和 HTTP 解耦，便于复用试点规则和本地测试。 |
| 资源压力控制 | 在目标副本规划与实际写入之间做启动准入。用在途实例、共享资源压力和可配置预算控制每批下发量。 |
| 执行与审计 | 每个受管集群串行执行。首版通过本机 GPUStack 管理 API 读取权威状态，使用官方模型更新接口提交 `replicas`，保留其它字段。权限凭据存放在 Server 私有挂载。 |

插件在 Server 构造应用时加载，后台任务通过 GPUStack 主任务组启动。事件任务、API 调用和规划需要独立超时，CPU 密集搜索放入有界执行器。后台异常在插件边界捕获，记录故障并退避，取消信号向上透传。连续故障触发停止写入和告警，GPUStack 继续管理已经提交的目标。插件任务在多个 Server 实例上均可能被启动，首版仅在单 Server、单写者条件下允许执行。后续多 Server 需要单独实现并验证带任期的写入互斥。

## 事件分类与一致性

第一阶段只将确认的上线或恢复当作扩容触发。设备退出、归零和缩容相关的分类与动作保留为后续设计。

1. **以可调度 GPU 集合变化为输入。** 读取集群、worker 状态和设备清单，比较前后两个完整快照。GPU 首次进入可调度集合为上线，离开为下线。支持同一 worker 下设备增减，以及旧 worker 退出、新 worker 以新 ID 注册。worker ID 用于跟踪实例落点，GPU UUID 用于检测设备重叠。GPUStack worker 的名称和身份恢复沿用原机制。
2. **区分设备下线与观测失败。** 核对 `ready`、可达、维护标记、设备清单和运行条件。API 超时、分页不全、清单缺失或可调度记录的 UUID 冲突进入待确认，冻结受影响范围的写入。临时不可达需在可配置的稳定窗口内反复确认，明确的维护状态可直接剔除容量。完整可信的零 GPU 快照可以生成降至零的计划。
3. **用事件触发，按状态收敛。** 启动时先订阅再对账，事件按集群合并为待重算标记。周期全量读取补偿漏报。相同资源快照、策略版本和部署状态得到相同决策。实例变化用于确认收敛，定期对账也可恢复遗漏的收敛通知。GPU 恢复、配置换版或维护状态变化时重算，撤销过期动作。

## 策略参数与维护

采用**基础策略加事件覆盖**。基础策略声明受管部署和默认分配规则。事件覆盖可调整模型权重、优先级、上下限，以及本类事件的执行步幅。以下清单同时保留第一阶段扩容和后续缩容参数。下线策略、自动缩容下限、缩容批次和归零动作在第一阶段均不生效。

### 受管范围和模型参数

| 参数 | 取值与约束 | 用途 |
| --- | --- | --- |
| `schema_version` | 必填，首版为 `1` | 配置格式版本。 |
| `revision` | 必填，单调递增整数 | 标记生效策略。回退旧内容时发布新版本。 |
| `scope.cluster_id`、`scope.owner_principal_id` | 必填，分别校验 GPUStack 集群和归属组织 | 限定读取、规划和写入范围。 |
| `models.<deployment_id>` | 以已存在的 GPUStack 模型部署 ID 为键，至少一个，允许多个 | 确定管理哪几款模型。同一模型权重可对应多个独立部署，分别管理。未列出的部署继续按原设置运行，占用的 GPU 额度仍计入容量。 |
| `priority` | 正整数，默认 `1`，越小越优先 | 只有资源不足以同时保底时决定保障顺序，同级按可放置性和稳定顺序处理。 |
| `weight` | 正整数，默认 `1` | 同一策略范围内的相对目标比例。填写 `2,3,5` 即目标为 `2:3:5`，无需换算为百分比。 |
| `min_replicas` | 非负整数，默认 `1` | 正常资源条件下的保底目标。物理资源不足时允许规划更低，执行仍受自动缩容下限约束。 |
| `max_replicas` | 必填非负整数，且不得小于 `min_replicas` | 单部署的硬上限。显式停用时将上下限和自动缩容下限都设为 `0`。 |
| `auto_scale_down_min_replicas` | 非负整数，默认 `1`，不得超过生效的 `max_replicas` | 自动下调目标的下限。显式设为 `0` 才允许归零；仅提高优先级不会改变缩容授权。 |
| `vram_claim_bytes` | 必填正整数，使用已验证的单副本规格 | 逐卡规划输入。与 GPUStack 原生显存声明核对，缺失或冲突时拒绝执行该部署的动作。选择器、后端及实际调度约束从 GPUStack 读取。 |

添加部署前校验其归属、运行条件和资源规格。移出清单只解除插件管理，停止服务使用显式归零流程。模型镜像、权重文件、启动命令、路由和鉴权在 GPUStack 中维护。

### 事件策略参数

`gpu_removed`、`gpu_removed_burst` 和 `capacity_zero` 行描述后续阶段行为。第一阶段只使用上线、恢复及冷启动策略。

`event_overrides.<event_type>.models.<deployment_id>` 可以覆盖既有部署的 `priority`、`weight`、`min_replicas`、`max_replicas` 和 `auto_scale_down_min_replicas`。未填写的字段继承基础策略。每个模型在覆盖后重新校验上下限。事件覆盖不增加部署归属范围，也不改变显存规格。

| `event_type` | 判定依据 | 可采用的策略 |
| --- | --- | --- |
| `cold_start_empty` | 启动后首份完整快照为零容量，且没有前次运行态容量基线 | 等待合格设备，避免把启动空窗当作批量下线。 |
| `gpu_added` | 确认有新 GPU 进入可调度集合，未达到突发门槛 | 正常保底和比例扩容。 |
| `gpu_added_burst` | 合并窗口内新增设备数达到上线突发门槛 | 可提高指定模型保障顺序，限制每批新增量，先恢复保底。 |
| `gpu_removed` | 确认有 GPU 离开可调度集合，未达到突发门槛 | 优先观察原生恢复，容量仍不足时按预设下限自动缩容。 |
| `gpu_removed_burst` | 合并窗口内退出设备数达到下线突发门槛 | 可调整保底优先级与比例，延后比例扩容，按预设下限自动缩容。 |
| `capacity_zero` | 曾有可用 GPU，完整快照确认可调度集合归零 | 允许归零的部署自动降至零，其余保持受保护的目标并记录无法放置。 |
| `capacity_restored` | 从已确认零容量恢复为非零 | 优先恢复可放置的首个实例，再补额外容量。 |

分类依据是合格设备集合的实际变化。相近事件在有最大等待时间的窗口内合并，较长时间陆续发生的少量事件独立处理。上线和下线同时出现时先核对最终集合。集合有退出时采用相应的下线策略，即使同时有设备加入或总数不变。真实归零和从零恢复优先于普通增减分类。观测不完整、UUID 冲突等情况走安全门槛，暂停受影响范围的写入。

事件策略作为最近一次确认的容量变化上下文。周期对账、实例进展及热更新使用该上下文，直到下一次确认的容量变化。插件重启后从审计状态恢复并用完整快照校验。首次启动即有资源且无历史上下文时使用基础策略。配置变更会在同一上下文中重新规划，已失效的计划停止后续写入。

### 执行参数

| 参数 | 范围和用途 |
| --- | --- |
| `events.merge_window_s`、`events.max_merge_wait_s` | 事件合并窗口和最长等待。均为正数，最长等待不得短于合并窗口。 |
| `events.burst_add_count`、`events.burst_remove_count` | 上线和下线各自的突发阈值，按窗口内确认的 GPU 数计，均至少为 2。 |
| `events.offline_stable_s`、`events.reconcile_interval_s` | 确认暂时失联转为下线的稳定时间，以及补偿漏报的全量对账周期。 |
| `execution.mode` | `observe` 或 `apply`，默认 `observe`。由基础配置设定，事件覆盖不能开启写入。 |
| `execution.max_inflight_global`、`execution.max_inflight_per_cluster` | 在途启动硬上限。必须显式设置才可开启写入，首轮隔离实写从 1 起步。共享资源上限由 Server 运维配置统一管理。 |
| `execution.scale_up_batch_max`、`execution.scale_down_batch_max`、`execution.batch_interval_s` | 每批增减副本的最大数量和批次间隔。事件可降低每批限额或延长间隔。设每批上限为 `0` 可暂缓对应方向的操作。 |
| `execution.convergence_timeout_s`、`execution.plan_ttl_s` | 单批收敛期限和计划有效期。超时后核对真实状态并重算。 |
| `execution.solve_timeout_s`、`pressure` | 单轮规划时限，以及各压力指标的高低水位、最长样本年龄和恢复观察时间。阈值由压测决定。 |

示例中 ID 和数值仅用于说明格式。基础比例为 `2:3:5`，突发下线时优先保障部署 103，并暂缓扩容。容量归零时，只有部署 102 被授权自动归零。示例处于只读模式。

  "revision": 7,

    "102": {"priority": 1, "weight": 3, "min_replicas": 1, "max_replicas": 6, "vram_claim_bytes": 3758096384},
    "103": {"priority": 2, "weight": 5, "min_replicas": 1, "max_replicas": 10, "vram_claim_bytes": 3758096384}

首版通过原子替换私有配置文件发布新版本。插件发现新版本后先校验，再一次切换并触发对账。无效版本告警并保留最近一次有效版本。每份计划固定策略版本、事件类型和快照指纹，旧版本未提交的动作失效，已提交动作先核实结果。配置和日志保留字段来源及覆盖结果，便于解释本轮为什么采用特定优先级、比例或批次上限。

## 逐卡规划与执行

第一阶段只提交高于当前副本目标的变更。下文有关缩容、归零、释放显存和健康实例保护的设计留给后续阶段。

1. **构造资源约束。** 每卡从可调度显存额度减去系统预留、其他工作负载的已分配量，以及应保留的受管实例分配。用原生实例分配核对可回收额度，同一显存只记一次。待启动且已分配的实例计入占用，未分配的实例计入期望而不计为可用。逐模型生成可落点的 GPU 集合，考虑选择器、后端兼容、资源规格等条件。
2. **求解目标。** 用整数变量表示模型在各 GPU 的副本数，要求逐卡预算和模型上限成立。按优先级层次最大化达到保底的服务数，先覆盖每个服务的首个实例。全部保底可行时，在配置限额内优先填充可用副本容量，再最小化总副本数相对权重的偏差。可用整数误差 `Σ |xᵢ·Σw − (Σx)·wᵢ|`，以改动量和模型 ID 处理平局。实现采用有界整数搜索，按 GPU 剩余预算、可放置集合和目标上界剪枝。求解超时只保留可解释的建议，未完成的求解结果不自动写入。规划中的落点用于判断可行性，GPUStack 的实际放置仍需对账。
3. **生成分步动作。** 有安全余量时可先补缺失的首个实例。需要释放资源时，先按策略计算允许的减量，并绑定策略版本、部署当前值、容量指纹和有效期。逐批写入前重新校验，等实际实例移除且目标 GPU 的显存释放，再重算补位。GPUStack 会自己选择缩掉的实例。若释放发生在其它 GPU，记录偏差并重新规划。只有自动缩容下限为零的部署才允许自动归零。
4. **提交与收敛。** 每次只写一个部署，执行前重新核对模型归属、策略、维护状态和旧目标。原生 `PUT /v2/models/{id}` 为整对象更新，首版要求受管部署由插件独占副本写入，避免与人工修改或未来的原生定时扩缩容并行。插件每次读取最新对象并保留其他配置。由于该接口缺少原子的比较交换能力，观察到外部改动时停写并告警。遇到超时或响应不明确，先读取原生目标和实际实例再决定后续动作。缩容可处理无法收敛的旧目标，避免沿用试点的全量收敛门槛而一直等待已经无法放置的副本。

**保护健康实例。** 自动缩容下限约束目标值。由于原生接口只设置副本总数，还需要保护实际可用实例。若部署下限为 `1`，而本批原生缩容在最坏落点下可能删除最后一个健康实例，则暂停该批并继续对账，即使写入后的目标仍大于零。确认没有健康实例的部署仍可减少无法放置的目标，直至其授权下限。保护规则限制自动执行，物理资源不足时可能保留未收敛的目标，并记录原因。待状态重新可信或 GPU 恢复时，插件继续自动对账与重算。

GPUStack 原生模型允许 `replicas=0`。其控制器按目标创建待调度实例或选出缩容实例；插件要额外核实目标零时实例已全部移除，以及重新扩容后路由确有可用实例。 [副本字段定义](https://github.com/gpustack/gpustack/blob/v2.2.3/gpustack/schemas/models.py#L227-L228) · [原生副本收敛与缩容](https://github.com/gpustack/gpustack/blob/v2.2.3/gpustack/server/controllers.py#L300-L359)

## 资源压力调节

目标副本数表达最终希望达到的规模，执行预算决定这一轮能启动多少。即使一次收到大量设备上线事件，也先计算整体目标，再按负载逐步兑现。优先放行可恢复服务保底的动作，剩余名额用于比例扩容。多个集群共用镜像仓库、模型存储或网络出口时，先检查共享资源预算，再检查各集群预算。

### 执行预算与在途计数

- **合并事件和读取。** 每集群只保留待重算标记，使用短窗口和最大等待时间合并密集事件。限制并发对账和 API 读取速率，规划任务有独立时间预算。长时间持续注册也要定期对账。
- **限制启动批次。** 配置全局和每集群的在途启动上限、每批新增上限及批次间隔。首次运行从保守值起步，按实测校准。写入前为拟新增副本预占预算；提交后直到实例可用、明确失败退出，或经权威对账确认写入未发生，才释放对应名额。已写目标但实例记录尚未出现、已排队、下载或初始化中的实例都算作在途压力。待启动副本在对账时按同一目标和实例去重。
- **把原生动作算进压力。** 已有 pending 副本可能在 GPU 上线后自动启动；下线触发的原生重调度也会产生启动负载。只要能够观测，就计入占用并压缩插件的新增预算。启动超时或连续失败进入退避与告警，不能仅凭超时释放名额并重发。插件重启时从原生目标与实例状态重建预算，有不确定状态时暂停追加。

### 按共享瓶颈反馈

| 观察面 | 建议采集 | 触发后的动作 |
| --- | --- | --- |
| 网络与镜像仓库 | 出口带宽、仓库请求延迟、429/5xx、并发拉取数 | 达到高水位时减小或暂停新增批次。冷缓存或缓存状态未知时按高成本处理，低水位持续一段时间后逐步放行。 |
| Worker 与模型存储 | 磁盘 IO 延迟或队列、空闲空间、共享存储吞吐、镜像解包与模型加载耗时 | 预算能绑定实际节点时按节点限制。落点未确定时用集群及共享资源的保守预算，避免假定某台 worker 已有缓存或会承接实例。 |
| 控制面与在线推理 | GPUStack API 延迟和错误率、启动积压、MaaS 推理 P95 和错误率 | 控制面拥塞时降低读取与写入频率，优先保留状态对账；在线服务承压时优先保底恢复，延后比例扩容。关键指标过期时使用配置的保守批次，无法确认已有负载时暂停新增。 |

高低水位、恢复观察期和各资源预算均可配置。每轮记录观测值、样本新鲜度、允许下发数、受限资源和已延期的模型目标。首轮交付先做静态启动预算、在途计数和启动失败退避；随后接入可获取的压力信号，验证反馈能降速及恢复后再启用。安全阈值由冷缓存与热缓存的对比压测确定。

**控制边界。** 插件能限制自身下发的目标增量和读写速率。GPUStack 会按已存在的副本目标创建、放置或重新调度实例，所以插件预算只能减少追加压力。若要求对实际镜像拉取或权重下载设置硬上限，需要在对应的容器运行时、仓库或模型分发链路实施并实测。worker 注册和母版首启的流量也需要接入侧按批次放行。 [GPUStack 副本收敛](https://github.com/gpustack/gpustack/blob/v2.2.3/gpustack/server/controllers.py#L300-L359) · [现有克隆镜像拉取记录](../../results/maas-e5-dual-clone-20261028/REPORT.md)

### 八类事件验收

第一阶段验收第 1–4 类。第 5–8 类保留为后续验收记录，第一阶段只检查这些情况不会触发副本变更。

| 场景 | 验收观察 |
| --- | --- |
| 1. Server、插件与 MaaS 冷启动，无 worker | 初次快照确认后等待容量，不产生启动写入。首个合格设备加入后无需重启组件即可触发对账。 |
| 2. 短时间大量 worker 注册 | 合并期间有最大等待时间，持续事件不能阻塞决策。以 ready 的 GPU 计算容量，先恢复保底，再分批兑现比例目标。记录读取频率、启动峰值和目标收敛时间。 |
| 3. 短时间少量 worker 注册 | 单批小幅扩容，去重且不重写相同目标。已有 pending 能消化新增 GPU 时，不再重复追加。 |
| 4. 较长时间少量 worker 陆续注册 | 每次稳定增量可独立触发，健康实例持续运行，规模逐步逼近权重目标。 |
| 5. 较长时间少量 worker 陆续回收 | 先观察原生重调度，必要时按预设下限自动缩容。后续设备变化使旧计划失效。 |
| 6. 短时间少量 worker 被回收 | 合并退场信号，分别注入短暂失联与明确退场。短暂失联期间暂停缩容，确认退场后按剩余逐卡资源规划并自动执行可行的减量。 |
| 7. 短时间大量 worker 被回收 | 旧计划停止下发。恢复按保底优先，原生重调度计入启动预算，容量不稳时延后比例扩容。 |
| 8. 运行中无可用 worker | 对比真实归零和 API 不可用。只有完整快照确认归零，才按下线策略把已授权部署自动降至零。受保护部署保留目标。所有部署和路由保留，合格 GPU 恢复后验证自动拉起及真实推理。 |

### 需要先取证的指标和限制

- **能看见多少原生启动。** 核对 v2.2.3 能否区分未分配 pending、下载或初始化和可用，测量目标写入到实例可见的间隔。验证断线或插件重启时如何重建在途量，并单独记录原生重调度产生的负载。
- **实际拉取压力与启动配额的关系。** 每档对比冷缓存和热缓存，记录仓库并发请求、出口带宽、磁盘 IO 延迟、GPUStack API 延迟与错误率、MaaS 推理 P95 与错误率、首实例恢复时间。区分插件新增、既有 pending、原生重调度和母版首启。若无法可靠归因，按共享资源实测峰值定预算。
- **阈值从基线推导。** 先记录没有新增启动时的基线，再从单个在途启动逐档加量。上线前根据资源余量和在线服务指标确定批次、上下水位、恢复观察期及规模上限。缺少关键指标或无法确认资源已释放时，以只读或暂停新增作为回退。
- **测试边界。** 事件风暴和容量不足先用事件回放、设备快照和替身 API 验证。两台真实 worker 验证插件与 GPUStack 的行为，规模及共享基础设施峰值另行压测。worker 容器启停用于模拟状态变化，旧宿主回收与新克隆接替单独验收。

截至本设计，已经验证的是 API 试点的真实 worker 恢复触发扩容、三个独立 OCR 路由、以及离线缩容建议。以上插件阶段待实施，压测阈值待采集，新克隆接替待现场安排。 [试点实现与证据](REPLICA-POLICY-PILOT.md)

### 2026-11-05 隔离运行验证

使用 GPUStack v2.2.3 原镜像，在无外部网络、无宿主端口映射、无生产数据挂载的临时容器中安装 `f944928` 的 wheel。镜像入口负责启动内置 PostgreSQL，隔离容器显式使用 loopback 通告地址。API 在无 worker 的情况下成功启动，返回 v2.2.3，内部日志确认加载 `maas_replica` 并订阅 worker 主题。

### 2026-11-05 只读容量对账

插件 0.2.0 用 worker 内部事件唤醒对账，并定期从 Server 数据库读取未删除的 worker。它排除不可达、未就绪及维护中的 worker。就绪 worker 缺少 GPU 清单、UUID 缺失或重复、读超时时记录未知状态。零容量需要完整读成功并经过稳定窗口，未知状态会重置该窗口。

在无外部网络、无生产数据挂载的 v2.2.3 临时容器中，实测 API 正常响应，容量从 `zero_pending` 约 11 秒后变为 `zero`，期间无需 worker 事件。另在同镜像的独立测试进程中用替身读取模拟零容量、读失败、恢复和 GPU 出现，验证只靠周期读取也能识别状态变化，并验证重复 UUID 会被拒绝。临时容器和匿名卷已清理。

本轮只记录 Server 范围的容量状态和设备数量。逐集群设备集合、GPU 归属变更、逐卡显存和真实 GPU 上下线尚待接入或验收。

### 2026-11-05 逐集群 GPU 快照

插件 0.3.0 按集群记录 GPU UUID、所在 worker、设备索引和剩余显存。逐卡使用 GPUStack 原生分配缓存，以总显存扣除已分配量和系统预留。缺失设备数据或跨集群 UUID 冲突会标记受影响集群的容量未知。记录加入、退出和换归属的数量，避免只看 GPU 总数而遗漏同数量换卡。该显存值是资源观测输入，完整模型放置仍需其他约束。

隔离 v2.2.3 实测创建两个空集群后，周期对账分别从 `zero_pending` 转为 `zero`。同镜像内用替身 GPU 清单验证了逐卡扣减、重复或缺失 UUID、离线旧记录、同数量换卡和 UUID 转移。临时容器和匿名卷已清理。本轮尚未实测接入真实 GPU 后读取原生分配缓存，未触发现网 worker 上下线或副本写入。

### 2026-11-05 策略热更新和只读规划

插件 0.4.0 可选读取 `MAAS_REPLICA_POLICY_PATH` 指向的私有 JSON 文件。接受单集群与组织范围、受管部署清单、模型上下限与权重、事件覆盖、批次上限和静态在途预算。只接受 `observe`，非法配置保留当前有效版本。未配置路径时继续运行容量对账。首次确认空集群时等待容量。运行中确认归零时，计划区分实际可放置目标和受自动缩容下限保护的目标。

### 执行层替身演练

插件 0.5.0 打包独立执行模块。其读写适配器通过注入提供，当前 Server 插件仍只允许 `observe`。本次替身测试覆盖：

| 场景 | 结果 |
| --- | --- |
| 写入超时，远端迟到提交 | 发送前持久化请求。重启后读到旧目标仍保留待确认状态，阻止重放和后续写入。远端迟到提交后，匹配部署绑定和目标值才清理日志。 |
| 写入超时，回读不完整或配置冲突 | 保留请求并停止写入。替身接口没有提供可证明未提交的信号，旧目标不能解除保护。 |
| 重建在途预算 | 按部署取已配置目标、已观察实例数和未确认增量后的目标最大值，减去可信的健康实例数。新实例行出现时额度不重复计入。分别累计单集群和全局预算。 |
| 一个健康实例和多个 pending | 按最坏情况下可能先移除健康实例计算，拒绝这批缩容，即使写入目标仍大于零。 |
| 可安全缩容或显式归零 | 读取原生新目标后，等多余实例行实际消失才释放本轮写入保护。只有策略授权归零的部署可写入零目标。 |

六项执行演练和五项策略回归通过，wheel 也包含执行模块。隔离实写前仍需接入真实管理 API 和可信健康快照，验证原生目标读回、实例删减与逐卡显存释放。执行阶段要求单写者，并需要定义能证明请求未提交的恢复证据。本轮未向真实 GPUStack 写入副本数。

### 2026-11-05 隔离管理 API 实写

插件 0.6.0 新增 v2.2.3 管理 API 适配器，分页读取 worker、部署和实例，按实际落点生成健康快照。写入前复核策略版本、部署 ID、集群、归属、配置指纹及旧副本目标。PUT 以原生 `ModelUpdate` 保留模型设置。常驻插件依旧只接入 `observe`，实写通过独立测试进程调用适配器和执行模块。

在无外部网络、无端口映射、无 GPU、无生产数据挂载的临时 v2.2.3 Server 中创建独立集群、测试模型及私有路由。真实 PUT 将副本从 `0 → 1 → 0`，读回原生目标，观察到 GPUStack 创建并移除一条 `pending` 实例，在途计数为 1。随后再次执行真实 PUT 并在客户端模拟响应丢失。新执行器从持久日志读回已提交目标，确认仍只有一个 `pending` 实例。最后恢复零目标，验证实例清空、模型配置指纹和路由 ID 一致。临时容器与匿名卷已清理。

该试验验证了管理 API、待调度实例的增减及目标恢复。健康实例缩容和真实逐卡显存释放需要独立 GPU 条件，仍待实测。现网没有写入、进程或 VM 变更。

### 2026-11-05 批量上线和资源压力回放

### 双机冷拉压力门槛离线回放

按 2 秒节拍回放双机冷启动计数，使用每台 VM 最近约 2 秒的网卡接收和数据盘写入速率，同名指标取两台最大值，并加入最近 6 秒内已完成的应用侧 OCR 探针结果。仓库拒绝信号在实测回放中以 0 占位，另用模拟 429 和 503 验证拒绝路径，未把占位解释为仓库实测错误率。

试验规则使用网卡接收低/高水位 40/150 MiB/s、磁盘写入 100/300 MiB/s、样本有效期 6 秒、低压恢复观察期 10 秒。实测窗口的 65 个评估点中，23 个为高压、39 个处于恢复观察、3 个开放。首次高压在发出扩容请求后约 8 秒。移除样本或让样本过期均返回 `pressure_unavailable`。模拟 429/503 均返回 `pressure_high`，随后每 2 秒提供一份低压样本，持续覆盖 10 秒才重新开放。反复读取同一份样本不会推进恢复时间。
