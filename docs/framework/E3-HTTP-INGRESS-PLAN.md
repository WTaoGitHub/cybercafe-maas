# E3-TUNE：HTTP请求接入容量专项

2026-10-29，用户采纳建议后加入T4。**状态：已设计，专用HTTP驱动/隔离环境与实测待实施。** 本次不修改运行配置、不扩大发生器上限、不部署新服务、不启动线上负载。复用E3 / GitHub Issue #4，不新增重复增强编号；T0基线、T1–T3先按原计划推进。

## 目标和计数口径

回答“在给定请求、响应延迟和资源条件下，接入端能够稳定处理多少并发请求、每秒受理多少任务，以及可吸收怎样的突发”。输出测试包络，不给脱离条件的无限期“最大并发”。

| 变量 | 定义 | 与现有限制的关系 |
|---|---|---|
| C_http | 同时已发出、尚未收到最终HTTP响应的请求数 | HTTP请求数，不是TCP连接数、排队任务数或执行槽位；HTTP/2多流也按请求计 |
| λ_offer / λ_sent | 目标与实际发送请求/秒 | 独立到达时钟下分别记录；未发送、迟发不能算服务已处理 |
| λ_202 | 首次受理202任务/秒 | 不等于OCR成功完成吞吐；200幂等复用不计新受理 |
| λ_429 | 明确QUEUE_FULL拒绝/秒 | 与202延迟、吞吐分开；不能靠快速429把“成功吞吐”变好 |
| q / Q | 当前等待数 / 当前有效队列上限 | 单项目Q=min(Qg,Qp)；执行中任务不属于等待数 |
| μ | 成功业务任务完成/秒 | 由模型、R/E/G/P和输入决定；HTTP并发不能自动提高μ |

当稳定受理速度λ_202>μ，队列增长近似为λ_202−μ；从q到Q的填满时间近似`(Q−q)/(λ_202−μ)`。这是规划估算，不能替代实测。队列有界也不能证明入口连接、鉴权和数据库等待开销有界。

## 实验环境和前置

**A：隔离API接入环境。** 专用入口/数据库/文件目录/测试project，使用当前API代码、代理链、HTTP/TLS方式、鉴权和任务准入逻辑。仅执行后端使用可控mock/快速消费者，不做GPU推理；不绕过准入，不直接向数据库灌任务冒充HTTP受理。优先保留真实鉴权链；如鉴权被stub替代，必须作为另一profile单列，结果不能直接代表正式端到端入口能力。端口、资源和访问范围先核对，当前尚未部署该环境。

隔离环境验证后才做**B：真实OCR有界复核**。固定当轮R/E/G/P/Q/M、镜像与输入，使用真实业务入口；不通过提高Q、取消任务、删队列、延长deadline或修改执行并发维持接入测量。所有202任务进入收尾对账。A与B分开报告，mock完成率不是OCR吞吐，A的容量也不直接等于B的容量。

开始前冻结：控制端硬件与CPU/RAM限制、API进程数、数据库连接方式/超时/资源、代理和TLS配置、HTTP版本、keep-alive/连接策略、输入/输出大小、project/key绑定、存储余量与发生器位置。没有正式公网入口时只对实际私有入口得出结论，不把回环测试当互联网容量。

主测`POST /maas/v1/tasks`，使用固定且已上传的有效图片引用、唯一run/幂等键、max_attempts=1，客户端不重试；保留真实鉴权。不混入上传、base64解码、结果下载流量。上传/大body另做输入包络复核，使用现有大小限制；其数值不能与小JSON任务提交混用。过载期间另以固定低频探针观察任务查询及健康接口，报告其流量与延迟，不能把查询吞吐算进任务受理吞吐。

## 用例及顺序

| case_id | 目标与负载 | 关键验收 |
|---|---|---|
| T4-HTTP-ACCEPT | 队列未满，逐档C_http测首次202；独立到达率另测，不随完成速度降速 | 成功受理延迟/RPS，队列趋势、实际并发、发生器迟发/未发，CPU/内存/DB连接及锁等待 |
| T4-HTTP-REJECT | 明确预填至队列上限，逐档施加有界请求 | QUEUE_FULL/429清晰快速，q不突破Qg/Qp，拒绝无新增任务/成功事件，无意外5xx或超时 |
| T4-HTTP-RECOVER | 沿用拒绝测试产生的真实受理任务，停止新增过载，让消费者正常排空 | 所有202可追踪并在原deadline内结束，恢复后新请求受理/查询/结果下载正常，无重启或人工清理 |

在线依赖：`T4-QUEUE → T4-HTTP-ACCEPT → T4-HTTP-REJECT → T4-HTTP-RECOVER → T5-CLAIM`。隔离环境和驱动的开发可在T0-TOOLS后独立准备，不能因此跳过真实T4所需的候选/队列证据。C_http预期影响入口开销，不随E/G/P联动修改。

### 正常受理

- 首轮C_http∈{1,2,4,8,16}，每档至少60秒且至少200个HTTP响应，最多180秒/100000次发送；达到预算仍未满足最小窗口/样本量则标为证据不足，不能算通过。所有响应应为首次202；队列须低于上限且无持续增长。任一QUEUE_FULL出现，该窗口不能用于“持续202受理能力”排名。
- 在隔离环境通过可控消费者保持队列稳定，记录消费者数量/资源/实际消耗率及额外数据库开销。如果消费者或数据库成为约束，明确报告该条件，不能删除排队片段、临时加大Q或宣称已经测到纯HTTP极限。
- 对筛选档位另按其已测λ_202的0.5/0.8/1.0/1.2倍独立到达率运行。C_http作为明确上限，λ_offer独立设置；忙而未发送、迟发超预算标为INCONCLUSIVE_GENERATOR，不算服务通过。过载点可预期429，但需提前标注模式，不与202-only窗口混算。
- 真实OCR复核使用短突发：每批请求数不超过起始观察到的有效剩余队列预算，停止提交后排空，再开始新批次。队列预算不足以验证某C时记SKIPPED_QUEUE_BUDGET，不算入口不支持该C；短突发结果也不能称持续受理上限。

首版工具并发保护仍为16。只有16档资源/延迟健康、发生器具备余量，且完成专用HTTP工具的独立有界扩展和回归后，才考虑32、64；不去掉全局校验，不将R/E/G/P上限随之扩大。未执行更高档时只报告“已验证到C”，不能称它就是系统最大值。

### 满队列拒绝

- 隔离环境可先停止专用消费者领取并预填到Q，保持固定满队列，专测429路径；不暂停正式集群或关闭正式worker。正式OCR复核保持正常消费，允许腾出位置后少量202，逐状态分组统计并全部收尾，不能强求每个请求均429。
- 每档最多30秒且最多10000次请求；队列满后不循环重发原请求。429必须来自预期接口并带`QUEUE_FULL`；代理限流的429、鉴权失败、客户端预算不足分开分类，不能冒充MaaS队列拒绝能力。
- 记录HTTP并发、q、运行中任务、全局/项目上限及已受理ID。并发受理下不得超过Q；429对应的全新幂等键不能有任务行或成功事件。不得通过扩大队列掩盖入口拒绝缓慢或资源耗尽。

### 过载后恢复

停止新增压力，不自动重发429/超时请求；保留完整意图和已受理ID，不覆盖旧run。隔离环境恢复原专用消费者领取，真实环境让现有执行器继续正常处理，不重建容器。按预先记录的q、运行数、保守μ和执行尾延迟给出排空预算，硬上限180秒；任务仍须遵守各自原deadline。

排空后30秒内做小规模新任务受理、任务查询及结果下载探针，验证唯一attempt/成功事件与资源回落。任一不确定受理/UNKNOWN、连接失败、意外5xx立即停止新增压力；已发请求只查询/收尾，不自动恢复服务或解除UNKNOWN。不靠取消、删任务、重启、延长deadline通过恢复验收。

## 记录、判定与交付

保存每请求发送/应答时间、request/task ID、HTTP状态和业务错误码、幂等键、body字节数；不得保存key或图片内容。分别统计目标/实际请求数、202/429/其他错误、各类P50/P95/P99、实际最大在途、迟发/未发、队列峰值/增长、填满和排空时间。HTTP无应答与服务已确认拒绝分开，均不可自动重放。

同时记录发生器CPU/RSS/连接和网络、API/代理资源、DB连接/锁等待与任务执行状态。指标不可用或发生器受限时标明INCONCLUSIVE，不把对服务不完整的供给当作成功上限证据。复用测试期原生指标/只读观察，不新增常驻collector或逐请求SSH门禁。

初稿实验门槛（**非生产SLA，首次执行前冻结**）：202受理和QUEUE_FULL拒绝分别P95≤0.5秒、P99≤1.5秒；意外5xx/超时、额度突破、任务丢失或重复计量均为0。沿用总计划的CPU持续80%及可用RAM下界作为停止升档条件。顶端候选至少3次独立重复，取可重复达标且保留余量的档位；如果低档已不达门槛，先诊断并记录，不在看见结果后改宽门槛让它通过。

最终分开交付：稳定202受理的`C_http/λ_202/请求包络`、满队列拒绝的`C_http/λ_429/响应包络`、真实OCR可吸收突发及恢复范围。保留“未测更高档/硬件/公网”等边界。额外预算约1–2小时另加顶端重复、工具/环境准备和必要扩展，不计入此前5–8小时原调优预算，不挤掉T0基线或T6两小时确认。
