# MaaS 动态模型并发：设计与实施方案

2026-11-18。跟踪 [Issue #60](https://github.com/WTaoGitHub/cybercafe-maas/issues/60)，决策来源见[讨论记录](DYNAMIC-CONCURRENCY-DISCUSSION.md)。状态为待实施，表中运行参数均为试点候选。

## 1. 交付目标

MaaS 自动发现各模型实际可服务的副本变化，更新模型和全局有效并发、同步预留和异步派发上限。变更须反映到实际准入和派发。副本恢复后，少量固定 Python 执行器能够使用新增容量。副本失效或缩容后，未获得最终派发授权的任务按新预算复核。

首版使用现有 PostgreSQL、任务队列和 GPUStack 路由。队列上限、单副本安全并发、全局硬上限、同步预留比例、进程数和每进程槽位由运维配置，动态计算使用这些边界。GPUStack 副本的创建与删除继续由现有调节器管理，相关工作见 [#39](https://github.com/WTaoGitHub/cybercafe-maas/issues/39)。

## 2. 容量观测与预算发布

| 环节 | 首版设计 |
| --- | --- |
| 容量池 | 用受信的 GPUStack 实例来源、集群、部署 ID 和路由目标绑定逻辑模型。指向同一部署和副本池的别名使用同一个容量池 ID，执行和排队都按该 ID 汇总。首个试点限于可验证的单部署路由。目标归属不明、部分重叠、多目标回退或变更中路由须先验证覆盖关系，再纳管。绑定和运行预算独立于现有任务的模型指纹。 |
| 副本证据 | 用 GPUStack 原生 worker、模型实例和路由目标信息。实例须为 `running`、worker 为 `ready` 且未维护或排空、路由已指向该部署，并满足经试点验证的网关就绪条件。缺失、冲突或未知的副本不获得新额度。计划副本数和 `ready_replicas` 用于对照。网关状态无法从当前版本直接确认时，先在隔离试点用小流量探针验证就绪判据及传播延迟。 |
| 刷新 | 复用原生分页读取和 watch。生命周期事件唤醒刷新，合并高频心跳，完整轮询兜底。试点候选为每 10 秒对账、单次读取预算 5 秒、快照有效期 30 秒。确认失效即减，新增副本至少两次完整观测且间隔不少于 5 秒再增。订阅断开时继续轮询。一轮读取不完整或不一致时，不刷新受影响容量池的有效期。 |
| 发布 | 在现有 MaaS observer 中增加独立容量循环，使用只读 GPUStack 凭据，沿用现有任务库。在事务外读取和计算，在同一短事务中发布配置版本、观测代次、有效期、模型及全局额度。单写者发布，较旧观测或过期配置不能覆盖新预算。API 和执行器在准入事务内读取同一代次，使用取得共享锁后的数据库时间验证有效期。 |
| 失败与恢复 | 最近完整快照在有效期内可继续使用。确认容量为零时立即设为零。过期、启动时无可信快照或映射失效时，受影响的池停止新增同步发放及异步派发，并从全局计算中剔除。恢复按新增容量判据确认。运维可区分真实为零、快照过期和绑定错误。 |

复用点包括[原生列表与订阅](../../maas_platform/gpu_daily_watch.py)、[副本对账](../../maas_platform/replica_reconcile.py)、[路由目标读取](../../maas_platform/cluster_maintenance.py)和[版本证据](GPUSTACK-SOURCE-EVIDENCE.json)。容量循环不以 E17 日报的采样周期或副本变更计划作为派发依据。数据库时间和行锁行为见 [PostgreSQL 时间函数](https://www.postgresql.org/docs/16/functions-datetime.html)与[行级锁](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS)。

### 额度公式

- 容量池有效额度 `M = min(池硬上限, 已确认可服务的安全并发)`。同质副本用可服务副本数乘以实测单副本并发。共享 GPU 或其他资源的池须采用可同时满足的联合预算，避免各池独立计算造成重复计入。
- 全局有效额度 `G = min(全局硬上限, 各不重复容量池联合可提供的总额度)`。执行准入另受项目硬上限约束。单项目试点中项目硬上限和全局硬上限设齐。
- 对全局及启用同步保护的池，设有效额度为 `T`、预留比例为 `p`，同步预留 `R = ceil(T × p)`，异步并发上限 `A = T − R`。用整数比例配置和计算，未启用模型级预留的池取 `R = 0`。异步须同时满足 `同步占用 + 异步占用 + 1 ≤ T` 和 `异步占用 + 1 ≤ A`。同步须满足总占用上限，可用全部空闲额度。
- 以 **25%** 起测，`T=8` 时 `R=2`、`A=6`。若此时同步已占 5，异步最多占 3。`T=1` 且启用同步保护时，异步上限为 0，排队任务仍遵守各自截止时间。25% 和运行硬上限以实测为准。

容量策略配置包含逻辑模型绑定、各池实测容量档案、硬上限、等待上限、同步预留比例和快照时效。启动时校验映射唯一性、比例范围和上限关系。数据库迁移采用新增结构，默认保留静态模式。启用时校验所有纳管推理入口使用同一配置版本，未绑定的远端模型需先补齐映射。现有运维观测应显示每池可服务副本数、快照年龄、代次、有效总额度、同步预留、异步上限、同步占用、异步领取与授权数、队列深度和拒绝或归队原因。

## 3. 数据库准入与任务状态

复用 [TaskService](../../maas_platform/service.py) 和 [SyncIngress](../../maas_platform/sync_ingress.py) 已有的 `maintenance.id=1` 行锁。预算发布、检查并领取、最终派发授权和导致 `UNKNOWN` 的状态更新使用一致的事务顺序。事务只包含本地状态操作。任何 GPUStack HTTP 调用都在收到事务提交成功的确认、释放锁之后进行。

| 路径 | 检查与状态改变 |
| --- | --- |
| 异步提交 | 先保留幂等重放与冲突判断，再检查模型池、项目和全局等待上限，保持原有文件配额及输入校验。复用 `_accept()` 作为最终原子判断。URL 下载入口可预查同一规则，下载后的 `_accept()` 仍是最终判断。 |
| 异步领取 | 只有空闲本地槽位才在同一事务中领取一个任务并预留占用。预留阶段统计已授权占用与已领取未授权的任务，从符合条件的任务中按现有队列顺序选择。跳过容量不足池，避免一个慢模型堵住其他模型。没有额度时留在队列，有界等待后再检查。 |
| 异步发送前 | 准备好输入后，在 `begin_backend()` 的短事务中读最新预算、核验任务 token、租约和截止时间。最终复核使用已授权占用，包含同步 `DISPATCHING` 和已经取得发送意图且仍占用执行资源的异步任务。待复核的领取不占最终派发名额，同一任务从预留转为授权只计一次。通过时写入持久发送意图，提交后立即发送。 |
| 复核失败 | 确认仍是本次领取且无发送意图，在同一事务中回退本次领取，沿用 `DEFERRED`，保留 ID、输入、幂等关系和原截止时间，不消耗推理重试预算。若已取消或过期，按对应终态处理。归队后避免紧循环重新领取。提交结果不明时不发请求，按现有持久记录核对。已有发送意图的请求走完成或恢复路径，远端结果不明进入 `UNKNOWN`。 |
| 同步准入 | 保持由 API 直接调用 GPUStack。输入准备使用独立的本地并发及时间预算，动态模式下在准备结束、接近发送时完成最终事务，检查模型、项目和全局额度并插入 `sync_activity`。待复核的异步领取不得挡住同步使用最后的可用授权额度。容量占满返回 `429/SYNC_CAPACITY`。确认零容量或快照失效时返回可重试的 503，且不上送 GPUStack。维护探针和全局 `UNKNOWN` 保护沿用现有边界。 |

例如，额度从高位降为 4 时已有 3 个授权占用，另有 5 个任务正在准备。若各层异步上限也允许，最多有 1 个通过最终复核，其余按归队规则回退。降额前已经授权的在途占用可以短暂超过新限额，复核会停止新增授权，直至占用收敛。同步与异步的成功事件和计量仍以现有唯一键及持久状态提交为准。

首版继续使用一个持久队列。全局、项目及模型池各有等待上限。为保证硬上限且让已受理任务归队，准入时计入该范围已经排队的任务及可能返回队列的活跃任务所保留的位置。领取后保留该位置，能够确定后续不会归队时释放。重试等待继续计入上限，避免回退或允许的重试挤破队列。保留位置只影响新的受理。任务过期清理从是否能领取中分离，容量为零、暂停或隔离时仍能过期和查询。首版沿用有界队列和原截止时间，零容量时可受理合规的异步任务等待，满额继续返回 `429/QUEUE_FULL`。冷启动客户 API 验收与 [#41](https://github.com/WTaoGitHub/cybercafe-maas/issues/41) 联动。

## 4. 执行器改造

保留 Python。每个执行器进程有一个常驻 `asyncio` 事件循环，按本地槽位调度最多指定数量的活跃任务。领取一笔后即开始准备，复核通过后发送。同一进程可以调度多笔远端 I/O，槽位贯穿准备、发送和结果持久化。使用进程内共享且有界的 HTTPX 连接池，逐请求显式传递凭据，保持 Cookie 隔离、现有超时和无自动重放。连接池用法见 [HTTPX 异步客户端文档](https://www.python-httpx.org/async/#opening-and-closing-clients)。

对 [OCR](../../maas_platform/ocr_connector.py) 拆开输入准备、推理和结果校验。同步的数据库及文件调用进有界处理池，文件和文档重处理另外限制并发及缓冲体积。复用[文档 OCR](../../maas_platform/document_ocr.py)适配器的执行和计量约束，保留受限处理路径，文档或本地适配器通过回归后再扩大其并发。每进程集中续租，按 token 和租约状态防止过期任务被续活，并监控数据库池等待。周期恢复独立于逐笔领取。

退出时停止领取，未进入发送阶段的任务按既有安全归队规则收敛，已发送的任务在宽限期内继续续租和提交。进程崩溃后的恢复继续以持久发送意图为边界。现有全局 `UNKNOWN` 隔离仍生效。按模型隔离的后续工作见 [#2](https://github.com/WTaoGitHub/cybercafe-maas/issues/2)。

## 6. 起测、验收与回退

四卡试点计划部署 A/B/C/D 共 2/4/4/10 个副本。验证每副本并发 1 以及同卡共同承载能力后，才将总容量 20 作为候选。先从全局硬上限 8、2 个进程 × 4 槽位、25% 同步预留和 Q25 起测。用同一负载对照 4 × 2。逐档增加到 12、16、20 前，按实测确认进程槽位、内存、连接池以及 GPUStack 有足够容量。Q100 和 Q1000 独立对照，比较同步优先下的各模型按期完成数及等待 P95。实际等待池深度用保守完成速率和允许排队时间确定。

- **容量变化**：覆盖就绪前后、批量掉线、降至 1、降至 0、恢复、观测器中断和重启。记录原生状态变化、预算发布、首次准入和实际派发的时间，分别报告发现延迟与执行生效延迟。试点候选目标为原生 API 可见降额后 15 秒内生效。停止观测后至迟在快照有效期结束时停止受影响池的新派发。另行记录 worker 实际失联到原生 API 可见的时间。
- **并发和隔离**：从授权日志核对每一笔新增授权满足当时各层上限，区分降额前已经授权的跨档占用。使用具备足够模型额度的流量验证 `8/2/6`。纯同步可以占满 8 个，异步积压时最多占 6 个，同步仍可占剩余 2 个。记录同步成功率、429、P95、异步过期率和按期完成数。队列、CPU、内存、连接池、锁等待、逐卡资源和网关响应纳入同一报告。
- **任务正确性**：核对安全归队、原截止时间、重试预算和唯一计量。已过期或取消的任务不上送。远端结果不明时保留 `UNKNOWN`，容量恢复也不能解除隔离。试点不得重启 XZ-31-001、XZ-31-002 或执行等效操作。

启用按单个 MaaS 任务库为单位，所有 API 和执行器使用同一模式及配置版本。受控步骤是先只观测，再暂停派发并排空旧模式在途占用，核对预算与健康状态后启用。回退时同样先暂停并确认已授权的任务收敛，恢复上一版静态限额配置，完成探针再接单。保留数据库迁移、队列任务和发送意图。无法确认已发任务收尾时保持隔离，交由现有恢复流程处理。
