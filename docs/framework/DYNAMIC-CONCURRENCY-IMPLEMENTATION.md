# MaaS 动态模型并发：设计与实施方案

2026-11-20。跟踪 [Issue #60](https://github.com/WTaoGitHub/cybercafe-maas/issues/60)，决策来源见[讨论记录](DYNAMIC-CONCURRENCY-DISCUSSION.md)。现有测试控制端的三模型已通过真实副本变化、Q25 持续混跑、预算过期和静态回退验收。日常入口已启用常态动态准入。 [常态验收记录](#三模型常态动态准入验收)

## 1. 交付目标

MaaS 自动发现各模型实际可服务的副本变化，更新模型和全局有效并发、同步预留和异步派发上限。变更须反映到实际准入和派发。副本恢复后，少量固定 Python 执行器能够使用新增容量。确认容量下降后立即发布新上限，未获得最终派发授权的任务按新预算复核。同步和异步使用同一占用口径，后端终态提交后自动归还占用，未确认结束的执行继续受 `UNKNOWN` 保护。

使用现有 PostgreSQL、任务队列和 GPUStack 路由。自动模式按单副本安全并发、逐卡资源预算和实际就绪副本计算模型及全局上限。同步预留比例和队列上限由运维配置。带显式全局或模型上限的容量策略沿用原限额语义。GPUStack 副本的创建与删除继续由现有调节器管理。 [调节器 Issue #39](https://github.com/WTaoGitHub/cybercafe-maas/issues/39)

容量模块按配置中的模型池集合工作，模型名称、数量和顺序由部署决定。符合既有推理、路由及资源契约的模型通过目录、凭据授权和容量策略增减。GPUStack 继续自动放置，MaaS 依据实际就绪副本计算额度。新增推理协议、执行终态机制或多 GPU 副本形态时，在相应的适配与观测层补齐可复用能力。当前实机试点覆盖 PP-OCRv4、Unlimited-OCR-2 NFS、OvisOCR3。

## 2. 容量观测与预算发布

容量计算采用独立代码模块，由现有 MaaS observer 作为后台任务运行。给定副本快照和容量策略，计算逻辑可单独测试。observer 将预算及有效期发布到现有 PostgreSQL。同步准入、异步领取和发送前复核在各自的数据库事务内读取预算并执行限制。首版沿用现有服务和部署单元，以只观测模式验证计算结果后再启用限制。

| 环节 | 首版设计 |
| --- | --- |
| 容量池 | 用受信的 GPUStack 实例来源、集群、部署 ID 和路由目标绑定逻辑模型。指向同一部署和副本池的别名使用同一个容量池 ID，执行和排队都按该 ID 汇总。首个试点限于可验证的单部署路由。目标归属不明、部分重叠、多目标回退或变更中路由须先验证覆盖关系，再纳管。绑定和运行预算独立于现有任务的模型指纹。 |
| 副本证据 | 用 GPUStack 原生 worker、模型实例和路由目标信息。实例须为 `running`、worker 为 `ready` 且未维护或排空、路由已指向该部署，并满足经试点验证的网关就绪条件。缺失、冲突或未知的副本不获得新额度。计划副本数和 `ready_replicas` 用于对照。网关状态无法从当前版本直接确认时，先在隔离试点用小流量探针验证就绪判据及传播延迟。 |
| 刷新 | 复用原生分页读取和 watch。生命周期事件唤醒刷新，合并高频心跳，完整轮询兜底。试点候选为每 10 秒对账、单次读取预算 5 秒、快照有效期 30 秒。确认失效即减，新增副本至少两次完整观测且间隔不少于 5 秒再增。订阅断开时继续轮询。一轮读取不完整或不一致时，不刷新受影响容量池的有效期。 |
| 发布 | 在现有 MaaS observer 中增加独立容量循环，使用只读 GPUStack 凭据，沿用现有任务库。在事务外读取和计算，在同一短事务中发布配置版本、观测代次、有效期、模型及全局额度。单写者发布，较旧观测或过期配置不能覆盖新预算。API 和执行器在准入事务内读取同一代次，使用取得共享锁后的数据库时间验证有效期。 |
| 失败与恢复 | 最近完整快照在有效期内可继续使用。确认容量为零时立即设为零。过期、启动时无可信快照或映射失效时，受影响的池停止新增同步发放及异步派发，并从全局计算中剔除。恢复按新增容量判据确认。运维可区分真实为零、快照过期和绑定错误。 |

复用点包括[原生列表与订阅](../../maas_platform/gpu_daily_watch.py)、[副本对账](../../maas_platform/replica_reconcile.py)、[路由目标读取](../../maas_platform/cluster_maintenance.py)和[版本证据](GPUSTACK-SOURCE-EVIDENCE.json)。容量循环不以 E17 日报的采样周期或副本变更计划作为派发依据。数据库时间和行锁行为见 [PostgreSQL 时间函数](https://www.postgresql.org/docs/16/functions-datetime.html)与[行级锁](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS)。

### 额度公式

- 容量池有效额度 `M = 合格就绪副本数 × 单副本安全并发`。同卡副本先按逐卡资源预算确认可共同运行。显式配置 `hard_limit` 的池额外受该值约束。
- 全局有效额度 `G = 各不重复容量池联合可提供的总额度`。自动模式将每个项目的有效额度取为同一快照的全局额度，共享占用继续受全局约束。显式配置 `global_limit` 时，全局与项目保留原限额边界。
- 对全局及启用同步保护的池，设有效额度为 `T`、预留比例为 `p`，同步预留 `R = ceil(T × p)`，异步并发上限 `A = T − R`。用整数比例配置和计算，未启用模型级预留的池取 `R = 0`。异步须同时满足 `同步占用 + 异步占用 + 1 ≤ T` 和 `异步占用 + 1 ≤ A`。同步须满足总占用上限，可用全部空闲额度。
- 以 **25%** 起测，`T=8` 时 `R=2`、`A=6`。若此时同步已占 5，异步最多占 3。`T=1` 且启用同步保护时，异步上限为 0，排队任务仍遵守各自截止时间。25% 和运行硬上限以实测为准。

自动放置由 GPUStack 负责。为 GPU 型号启用每卡预算后，MaaS 按实例实际落点汇总同卡占用，计入启动中的实例。每个单卡副本的占用取其原生显存分配和按核定并发实测的显存上界中的较大值。每卡总占用通过预算检查后，只有已就绪且可路由的副本贡献额度。用代表性混合负载校准显存上界和单副本并发。无法证明安全的卡暂停计额，能命中该卡的聚合路由也暂停派发。 [部署配置](../../deploy/maas/README.md#动态容量只观测)

容量策略配置包含逻辑模型绑定、各池实测容量档案、硬上限、等待上限、同步预留比例和快照时效。启动时校验映射唯一性、比例范围和上限关系。数据库迁移采用新增结构，默认保留静态模式。启用时校验所有纳管推理入口使用同一配置版本，未绑定的远端模型需先补齐映射。运维观测应区分每池可服务副本、新预算代次和时效、有效总额度、同步预留、异步上限、领取预留、已授权占用、`UNKNOWN` 占用及隔离范围，并显示队列深度和拒绝或归队原因。

## 3. 数据库准入与任务状态

复用 [TaskService](../../maas_platform/service.py) 和 [SyncIngress](../../maas_platform/sync_ingress.py) 已有的 `maintenance.id=1` 行锁。预算发布、检查并领取、最终派发授权、进入 `UNKNOWN` 和终态释放采用一致的事务顺序。事务只包含本地状态操作。任何 GPUStack HTTP 调用都在收到事务提交成功的确认、释放锁之后进行。

| 路径 | 检查与状态改变 |
| --- | --- |
| 异步提交 | 先保留幂等重放与冲突判断，再检查模型池、项目和全局等待上限，保持原有文件配额及输入校验。复用 `_accept()` 作为最终原子判断。URL 下载入口可预查同一规则，下载后的 `_accept()` 仍是最终判断。 |
| 异步领取 | 只有空闲本地槽位才在同一事务中领取一个任务并预留占用。预留阶段统计已授权占用与已领取未授权的任务，从符合条件的任务中按现有队列顺序选择。跳过容量不足池，避免一个慢模型堵住其他模型。没有额度时留在队列，有界等待后再检查。 |
| 异步发送前 | 准备好输入后，在 `begin_backend()` 的短事务中读最新预算、核验任务 token、租约和截止时间。最终复核统计同步和异步已授权的 `DISPATCHING` 及纳入该预算的 `UNKNOWN`。同一任务从预留转为授权只计一次。通过时持久化本次 token、发送意图和已验证的落点范围，提交后立即发送。 |
| 复核失败 | 确认仍是本次领取且无发送意图，在同一事务中回退本次领取，沿用 `DEFERRED`，保留 ID、输入、幂等关系和原截止时间，不消耗推理重试预算。若已取消或过期，按对应终态处理。归队后避免紧循环重新领取。提交结果不明时不发请求，按现有持久记录核对。已有发送意图的请求走完成或恢复路径，远端结果不明进入 `UNKNOWN`。 |
| 同步准入 | 保持由 API 直接调用 GPUStack。输入准备使用独立的本地并发及时间预算，动态模式下在准备结束、接近发送时完成最终事务，检查模型、项目和全局额度，在 `sync_activity` 持久化 token 和已验证的落点范围。待复核的异步领取不得挡住同步使用最后的可用授权额度。容量占满返回 `429/SYNC_CAPACITY`。确认零容量或快照失效时返回可重试的 503。命中 `UNKNOWN` 隔离返回 `503/BACKEND_QUARANTINED`。 |

例如，额度从高位降为 4 时已有 3 个授权占用，另有 5 个任务正在准备。若各层异步上限也允许，最多有 1 个通过最终复核，其余按归队规则回退。降额前已经授权的在途占用可以短暂超过新限额，复核会停止新增授权，直至占用收敛。同步与异步的成功事件和计量仍以现有唯一键及持久状态提交为准。

首版继续使用一个持久队列。全局、项目及模型池各有等待上限。为保证硬上限且让已受理任务归队，准入时计入该范围已经排队的任务及可能返回队列的活跃任务所保留的位置。领取后保留该位置，能够确定后续不会归队时释放。重试等待继续计入上限，避免回退或允许的重试挤破队列。保留位置只影响新的受理。任务过期清理从是否能领取中分离，容量为零、暂停或隔离时仍能过期和查询。首版沿用有界队列和原截止时间，零容量时可受理合规的异步任务等待，满额继续返回 `429/QUEUE_FULL`。冷启动客户 API 验收与 [#41](https://github.com/WTaoGitHub/cybercafe-maas/issues/41) 联动。

### 额度归还与 UNKNOWN

共享推理额度由 PostgreSQL 持久状态计算。复用 `backend_activity`、`sync_activity` 和现有执行 token。未写入发送意图的任务安全归队时，同一事务释放领取预留。已经取得授权的执行在可信终态提交后退出动态派发占用统计。异步复用 `complete_backend()`，同步复用 `SyncIngress.finish()`，按 token 更新对应执行，异步同时匹配任务 ID。状态更新只允许从 `DISPATCHING` 或 `UNKNOWN` 进入终态，重复完成或恢复操作只生效一次。收尾时仍由执行器本地槽位约束校验、存储和计量。静态模式仍按活动任务计数，动态模式使用迁移 `014` 的后端终态标记排除仅在本地收尾的异步任务。

已授权但无法确认远端结束的执行进入 `UNKNOWN`。本地处理可以收尾，远端执行继续计入共享占用。原派发返回完整可信终态时自动结清，已结束的任务维持原状态，结果和计量沿用既有事务。后端查询或取消可以作为后续证据来源，条件是响应能对应本次执行，并证明已结束。超时、断连、租约到期、普通健康检查、worker 恢复、仅收到取消收件确认都不能作为结清依据。原请求不自动重跑。连接彻底丢失且没有自动证据时，继续走 `resolve-backend` 或 `resolve-sync` 人工核实流程。

首版沿用[当前隔离契约](../../deploy/maas/INFERENCE-QUARANTINE.md)。发送前记录逻辑模型、上游路由以及动态模式下的部署池，在可能受影响的范围内停止新增派发。历史记录缺少路由证据时沿用整库保护。`UNKNOWN` 继续计入当前全局和项目预算。新上限自预算事务提交起生效，即使旧授权占用暂时高于新上限。派发余量取 `max(0, 新上限 − 该层占用)`，同时受模型池、同步预留和隔离约束。例如原上限 100、占用 80、其中 40 变为 `UNKNOWN`，确认新上限 50 后新增派发为 0。上限维持 50 时，占用低于 50 且其他准入检查通过才恢复派发。

逐 GPU 隔离沿用 [E1 路由候选](E1-DESIGN.md#候选推理传输) 的可验证落点约束。容量策略可为一个逻辑池绑定多条单卡路由。每条路由只有一个部署目标，重试仍只能到原 GPU。观测器按当前就绪副本发布可选路由，MaaS 在发送前把路由和 GPU UUID 写入派发账本，实际 GPU 的认证回执独立确认执行权。能够确认落点的 `UNKNOWN` 阻止该卡上所有新派发。其他卡可使用尚有余量的全局、项目、模型和异步额度。原 `UNKNOWN` 继续按共享账本计入这些上限。路由、归属或落点缺乏足够证据时按保守范围保护。 [配置及回执约束](../../deploy/maas/INFERENCE-QUARANTINE.md#逐-gpu-隔离候选)

## 4. 执行器改造

每个 Python 执行器进程运行一个常驻 `asyncio` 事件循环。自动模式下，执行器逐笔领取并并行等待远端响应，实际派发遵守实时异步预算，进程数保持 `MAAS_EXECUTOR_REPLICAS`。本地槽位贯穿准备、推理和结果持久化。进程启动时根据可用内存与文件描述符估算安全在途量，达到该量时在执行器日志记录具体限制。无法测得内存时沿用 `MAAS_EXECUTOR_SLOTS` 作为本地保护。显式限额及静态模式继续使用该参数作为本地槽位数。进程内复用有界 HTTPX 连接池，逐请求传递凭据并沿用超时和单次发送规则。 [HTTPX 异步客户端文档](https://www.python-httpx.org/async/#opening-and-closing-clients)

对 [OCR](../../maas_platform/ocr_connector.py) 拆开输入准备、推理和结果校验。同步的数据库及文件调用进有界处理池，文件和文档重处理另外限制并发及缓冲体积。复用[文档 OCR](../../maas_platform/document_ocr.py)适配器的执行和计量约束，保留受限处理路径，文档或本地适配器通过回归后再扩大其并发。每进程集中续租，按 token 和租约状态防止过期任务被续活，并监控数据库池等待。周期恢复独立于逐笔领取。

退出时停止领取，未进入发送阶段的任务按既有安全归队规则收敛，已发送的任务在宽限期内继续续租和提交。进程崩溃后的恢复以持久发送意图为边界，共享推理额度按实际终态证据结清。本地槽位随本地工作结束释放。现有路由和部署池隔离见 [#2](https://github.com/WTaoGitHub/cybercafe-maas/issues/2) 和 [#62](https://github.com/WTaoGitHub/cybercafe-maas/issues/62)。

## 5. 开发顺序与完成条件

阶段 1 的只观测模块已实现，可在隔离环境配置验证。真实 GPUStack 的路由就绪证据及容量档案待试点确认。配置见[部署说明](../../deploy/maas/README.md#动态容量只观测)。

阶段 2 的共享准入已接入。任务库中的模式和策略摘要统一约束 API 与执行器。默认继续使用静态限额，切换在暂停且排空后通过私有 CLI 执行。隔离 PostgreSQL 已覆盖同步占满 8、并发执行器最多领取 6、发送前降额归队和回退。共库小规模联调验证了不同 GPU 上两条模型路径的并发，逐资源故障隔离与负载验证待试点。见 [#60 联调记录](https://github.com/WTaoGitHub/cybercafe-maas/issues/60#issuecomment-6972583307)。

阶段 2a 已通过隔离 PostgreSQL 验证。额度在可信终态提交后可立即复用，重复或错配的终态不能多释放。已覆盖 100→50 与 40 个 `UNKNOWN` 的收敛过程、预算发布与同步释放竞态、迟到响应和原任务无自动重放。

阶段 3 已通过隔离 PostgreSQL 和模拟 GPUStack 验证。单进程双槽下，首笔立即发出，两个推理可同时在途并批量续租，第三笔等槽位释放后发出。共享客户端逐请求使用各自凭据。退出时已发送任务完成并计量一次，未发送任务归队或继续排队。复跑命令为 `MAAS_TEST_DATABASE_URL=... python -m pytest tests/maas/test_async_executor_integration.py -q`，数据库名须以 `_test` 结尾且专供本次验证。

2. 先用只观测模式核对三个池的路由和额度。逐模型低负载测得安全并发，再验证 PP-OCRv4 与 OvisOCR3 的共卡混合负载。联合预算通过后才登记相应的共享 GPU 布局。首轮总额度按已验证的可服务资源确定。`8/2/6` 是模拟验证档位，实机在实测容量达到后复验。
3. 在当前测试环境暂停并排空后启用动态准入。验证同步预留、降额、未发送归队和静态回退，按结果确定执行器进程、槽位和队列深度。以 Q25 起测，后续按保守完成速率和允许排队时间对照 Q100、Q1000。

- **容量变化**：覆盖就绪前后、批量掉线、降至 1、降至 0、恢复、观测器中断和重启。记录原生状态变化、预算发布、首次准入和实际派发的时间，分别报告发现延迟与执行生效延迟。试点候选目标为原生 API 可见降额后 15 秒内生效。停止观测后至迟在快照有效期结束时停止受影响池的新派发。另行记录 worker 实际失联到原生 API 可见的时间。
- **并发和隔离**：从授权日志核对每一笔新增授权满足当时各层上限，区分降额前已经授权的跨档占用。按实测容量复核同步能使用符合规则的空闲额度，异步积压遵守同步预留。记录同步成功率、429、P95、异步过期率和按期完成数。队列、CPU、内存、连接池、锁等待、逐卡资源和网关响应纳入同一报告。
- **任务正确性**：核对安全归队、原截止时间、重试预算和唯一计量。已过期或取消的任务不上送。远端结果不明时保留 `UNKNOWN`，容量恢复也不能解除隔离。试点不得重启 XZ-31-001、XZ-31-002 或执行等效操作。

启用按单个 MaaS 任务库为单位，所有 API 和执行器使用同一模式及配置版本。受控步骤是先只观测，再暂停派发并排空旧模式在途占用，核对预算与健康状态后启用。回退时同样先暂停并确认已授权的任务收敛，恢复上一版静态限额配置，完成探针再接单。保留数据库迁移、队列任务和发送意图。无法确认已发任务收尾时保持隔离，交由现有恢复流程处理。
