# P0：协议、容量及验收基线

## 固定的首批契约

- `/maas/v1`是新任务命名空间；GPUStack原有`/v1`负责同步/流式，不由任务层重复代理。
- 提交外层固定model/input/parameters/timeout_seconds/max_attempts。input由模型自己的schema定义；当前mock使用input.artifact_id，不强行固定所有模型的payload。
- 202仅表示事务接受；成功必须结果先持久化。幂等键按project隔离，同内容返回原任务200，不同内容409。
- TaskView固定任务状态、revision、attempts、结果引用、错误码和时间。状态机包括排队、运行、重试等待、取消请求及三个终态。
- 统一错误code/message/retryable/request_id；artifact下载按project鉴权，过期410。

协议由现有Pydantic模型导出，核心响应增加TaskView声明；不把P0静态schema当成真实OCR适配器已完成。

## 初始运行参数（不是外部SLA）

| 参数 | 首批值 | 验收与边界 |
|---|---:|---|
| 输入/输出上限 | 10/20 MiB | 当前框架控制字节，图片解码像素限制由具体适配器负责 |
| JSON提交体上限 | 64 KiB | 大文件先上传artifact |
| 全局/项目排队上限 | 1000/100 | 超限429；接受任务仍可能因deadline明确失败 |
| 全局/项目执行槽 | 2/1 | 上界而非承诺吞吐；不等于每卡GPU资源隔离 |
| 租约/心跳 | 30/5秒 | 心跳必须小于租约一半，持续续租 |
| 输入/结果保留 | 各24小时 | 活动输入引用不清理；历史任务及用量保留 |
| 最小磁盘余量 | 2 GiB | 不足拒绝新输入/任务；生产备份与容量告警属后续阶段 |
| 默认任务总deadline | 120秒 | 包含排队/尝试/退避 |
| mock/候选OCR最大运行时 | 30/60秒 | OCR值为P2初始候选，需真实输入测试 |
| 业务重试 | mock最多3次；网络模糊POST禁止自动重放 | 上游持续503已观测3次实际调用，不叠加无界重试 |

数字型限制支持MAAS_*环境变量；非法值、NaN心跳、project上限超过global、非PostgreSQL配置等启动时拒绝。Compose模板传递对应配置，但001尚无Compose插件，本期继续使用已验证的docker run，安装插件不是P0/P2关键路径。

当前001约392 GiB可用空间（以验收记录为准），足以受控试点，不代表24小时任意业务量可保存。并发2时的最大输出约40MiB，不应把磁盘耗尽边缘当作运行常态。空间配额、孤儿文件巡检、备份恢复及告警仍属P3/P4。

## 阶段验收目标

- P1/P2：已收到202的任务记录遗失数0；每任务成功事件最多1；跨project成功访问数0。
- 性能初始目标：控制端内网4客户端提交P95不高于1秒；符合条件的mock租约失效后5秒内可重新领取。这些目标在P2/P4实测，不在P0冒充已达到的SLA。
- 真实模型质量与容量单独验收，历史OCR四副本15.11张/秒不直接作为任务平台吞吐承诺。
- 单控制端可重启恢复，不承诺硬盘损坏零丢失或高可用。恢复与生产备份目标需P4实测。

## 已解决/后移的依赖

1. v2.2.3运行版本与源码基线一致；已有Python3.11容器及独立PostgreSQL测试库可用。
2. key/project安全绑定、组织模型ACL及task/artifact对象隔离已实测；注册歧义失败关闭。
3. 真实入口/重试、generic代理和usage缺口已有记录及明确策略；没有修改原OCR入口来强行消除差异。
4. 版本固定原语已验证，P2执行专用版本目标与同内容镜像分发，不依赖main或公共镜像仓库。
5. 域名、TLS、生产secret系统、8小时负载不是P0依赖；不得因此宣称已可公网商用。
