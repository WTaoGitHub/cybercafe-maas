# 多部署启动效率验收

2026-11-13 · 热缓存预热与九轮通过，冷缓存待独立环境 · [Issue #39](https://github.com/WTaoGitHub/cybercafe-maas/issues/39)

本轮先补同一调节器的热缓存启动效率，不改变正式OCR的策略和2/2规模。复用上一轮已清理、无未知写入的A/B/C三个独立部署；其他部署均保护。每部署min1/max2、weight1/priority1，每副本使用原生3.5GiB声明。两卡各三个试点申报空位，共六个目标副本。只有固定容量、完整快照和原有服务核对通过才能执行。

## 固定矩阵

先做一次上限2的完整预热，确认两张当前GPU均实际运行过相同批准引擎。热缓存指当前worker已有镜像和模型文件，不代表CUDA进程/上下文复用，也不控制操作系统页缓存。预热不计入档位比较。

| 轮次 | 执行顺序 | 不变量 |
| --- | --- | --- |
| 1 | 1→2→4 | 各六目标副本、相同模型/资源/首副本规则 |
| 2 | 2→4→1 | 相同1秒对账/1秒稳定期、逐笔+1 |
| 3 | 4→1→2 | 上限1串行；2/4显式启用parallel_startup |

每档三轮，交错顺序避免全部串行先测。当前保守预留会暂时扣住有未完成实例的整张GPU，两卡下上限4未必可达到四个同时启动，必须报告实测峰值，不能声称已验证四卡并行或4最优。

## 观测与验收

起点为已完成Observe/显式adopt后启用Apply的时刻，测量当前闲置容量的兑现，不伪造新worker到达事件。按约0.5秒外部读取记录目标、Ready、原生状态/落点/申报、各卡状态和调节状态；管理API耗时会增加采样间隔。缺失的下载/初始化阶段标为未观测到，不能补造。

- 首个原生Ready、六副本全部Ready的首次观测时间。
- 每部署首次Ready后固定等待2秒，再各发一次独立OCR探针；记录首次及三个模型均成功的完成时间。这是本探针节奏下的成功上界，不是最早路由可用时间。失败或超时不自动重放。
- 实际在途峰值、6笔自动+1、资源/授权边界及全部Ready实例稳定性。未知日志不清理，失败不自动运维归零。
- 正式OCR先做5笔低负载基线、启动期间约每10秒一笔独立探针；全部成功才通过。小样本延迟仅供同环境对照，不等于客户负载或SLA。
- 资源指标优先使用原生worker状态及控制端只读快照；未取得网络/磁盘吞吐时明确不可用，不新建SSH采集门禁。

临时容器、共享状态/journal及每轮调节子进程独立。发送器只允许A/B/C逐笔+1至2；每轮结束先暂停并正常停止试点进程，确认journal空和受保护对象未变，再明确运维归零等待实例删除。以原生API增加专用推理路由，创建仅推理权限/限定模型/有期限的临时key，结束核对后删除本轮路由并撤销key。生产管理凭据不用于推理探针。

每轮上界180秒；异常最多两次有界诊断，仍不能继续则停止保留，不重放未知请求、不调门槛、不拼接失败结果。不得重启VM、worker、Docker引擎、GPUStack或正式API/E17，不恢复collector。

## 冷缓存边界与收尾

先核对能否隔离镜像与模型文件。已有worker共享现役Docker镜像/层与模型目录时，不通过清空它们制造冷缓存，也不把新tag但层命中冒充冷拉取。若需要独立克隆或管理员提供环境，冷缓存保持待验收，交付已完成热缓存结果和前置条件；不替管理员创建/回收VM。

最终核对正式配置、原实例ID、常驻容器启动时间、正式journal和旧故障未知journal、客户异步OCR唯一计量及日报/SQL。备份与原始记录优先保存Mac、核SHA，公开报告匿名。每档报告三轮原始值、均值/中位数和范围；样本过少不宣称P95或最优配置。是否调整常驻并行参数必须在报告中给出建议，不能自动晋级。后续稳定观察与回退交接另行推进。
