# GPUStack 上线驱动的模型副本试点

对应 [GitHub Issue #39](https://github.com/WTaoGitHub/cybercafe-maas/issues/39)。控制器运行在 GPUStack Server 所在主机，当前绑定 GPUStack v2.2.3、一个隔离的调度范围、最多两个单 GPU worker 和三个明确绑定的测试部署。

## 决策规则

- 使用 worker watch 唤醒对账，每十秒也做一次全量对账。按 worker ID 关联注册记录，用 GPU UUID 检测重复设备。计入 `ready`、可达、未维护、符合三个部署共同选择条件的设备。多个在线记录报告同一个 GPU 时暂停扩容。
- 可用显存按每卡的总量减去 GPUStack 汇总的已分配额度和系统保留计算。对三种副本的新增组合做逐卡放置检查。GPUStack 仍决定实际落点。
- 优先保障首个实例。资源不足时按优先级依次最大化能覆盖的服务数，同级用配置顺序打破平局。全部保底可行后，先使用可容纳的副本容量，再在同容量方案中选择最贴近目标比例的整数分配。当前只能追加，比例会受现有落点和各服务上限约束。
- 每次只更新一个部署的目标副本数，增加一个副本。已配置副本未全部在合格节点进入 `running` 时等待原生收敛。写入之前重新核对目标模型，写入结果不确定时退出。不会主动缩容、抢占、迁移、创建或删除部署。
- `running` 是对账时使用的原生状态。实机验收另对三个测试路由发 OCR 请求，以验证运行状态背后确有可用服务。

## 运行

提前用相同权重、镜像和后端创建三个独立部署。每个部署以实际验证过的显存额度填写 `GPUSTACK_MODEL_VRAM_CLAIM`，并在配置中填入相同的字节值。三个部署必须使用相同的 worker selector、关闭 CPU offload 和跨 worker 分布式推理，并使用同一个试点后端。试点期间由一个操作者独占部署变更。

私有配置文件示例，模型 ID 和后端名称需按实际部署填写。这里的三个显存值用于已经验证的同构 PP-OCRv4 实机配置。

```json
{
  "cluster_id": 1,
  "backend": "pilot-ocr-custom",
  "services": [
    {"id": 101, "name": "maas-replica-pilot-a", "claim_bytes": 3758096384, "priority": 1, "weight": 2, "limit": 2},
    {"id": 102, "name": "maas-replica-pilot-b", "claim_bytes": 3758096384, "priority": 1, "weight": 3, "limit": 3},
    {"id": 103, "name": "maas-replica-pilot-c", "claim_bytes": 3758096384, "priority": 2, "weight": 5, "limit": 5}
  ]
}
```

配置和 API key 文件均需为私有普通文件（例如模式 0600）。先运行一次只读对账。

```sh
python3 -m maas_platform.replica_controller \
  --config /path/to/private-policy.json --key-file /path/to/private-api-key --once
```

省略 `--once` 持续监听。默认只输出 JSON 决策记录，显式传入 `--apply` 才允许更新。试点集群中有其他活跃部署时拒绝执行。停止控制器会停止后续扩容，已交给 GPUStack 的副本仍由 GPUStack 管理。

## 验证矩阵

| 情形 | A/B/C 使用 2/3/3.5 GiB 的期望 |
| --- | --- |
| 单卡剩余 3.5 GiB | A 或 B 先获得首个实例 |
| 单卡剩余 5 GiB | A、B 各 1 个 |
| 单卡剩余 8.5 GiB，初始为空 | `1:1:1` |
| 两卡剩余 6 和 2.5 GiB，初始为空 | 总量够但逐卡放不下三种，目标 `1:1:0` |
| 初始 `1:1:1`，新增 GPU 后逐卡剩余 7 和 15 GiB | 目标 `2:3:5` |
| 重复事件、原生副本仍在启动 | 等待原生收敛，避免重复写入 |

两张 RTX 4080 SUPER 的名义可调度容量约 16 GiB/卡。异构预算的十副本合计 30.5 GiB，在计算层存在逐卡放置。历史 PP-OCRv4 实测单副本显存峰值约 2.86 GiB，实机使用三个 3.5 GiB 声明。每卡最多四个，双卡验收目标为 `2:2:4`。原常驻服务有八个副本，实机试验使用排空的维护窗口。

收尾只读复核显示，原部署为 8/8 可用、两卡各 4 个，两台 worker 均 `ready` 且可达，MaaS 接单已恢复，UNKNOWN 为 0，试点模型和路由残留均为 0。只启停了 worker 8 容器。两台 VM 始终运行。控制器未设为常驻任务。

**结论**：两卡范围内，worker 上线触发策略计算、逐步下发副本数以及 GPUStack 放置启动的链路实测通过。A/B/C 三个测试路由的 OCR 请求验收未完成。异构 2/3/3.5 GiB 的整数决策、逐卡放置和完整 `2:3:5` 通过本地验证，实机证明的是同一安全显存额度下的 `1:1:2 → 2:2:4`。

本地针对性测试 14 项通过。MaaS 全量回归在与本次改动无关的既有网络边界测试上失败，单独运行可复现。隔离该项后，538 项通过、137 项按环境跳过。

## 资源减少时的处理

节点离开容量池后，先读 GPUStack 的目标副本、运行实例、待调度实例及逐卡显存。已分配在离线节点上的副本不能作为可用实例。比例扩容暂停，优先等待 GPUStack 完成原生重调度。

如果可用资源无法恢复所有目标副本，可把「保住三个服务的首个实例」和「回收多少额外副本」拆为两步。先计算保底是否可放置，再提出最小调整。三个服务均有可用实例时，保持现有可用副本。若某服务缺少首个实例，只考虑会在合格 GPU 上实际释放所需显存的方案。控制器只记录 `manual_floor_recovery` 建议，由操作员确认并执行。即使开启 `--apply`，缩容建议也只写日志。每个服务的最后一个可用实例仍受保护。

| 两卡降为一卡后的状态 | 离线验证结果 |
| --- | --- |
| 幸存实例为 `1:1:2`，剩余不足一个副本 | 保持 `1:1:2`。 |
| 幸存实例为 `1:0:3`，剩余不足一个副本 | 追加策略无法补 B。若人工批准并确认同一张卡释放 1 个额外 C 的额度，可恢复为 `1:1:2`。 |
| 三个服务均无可用实例，仅有一个或两个同规格名额 | 按保底优先级选择 A 或 B，或分别启动 A、B。 |

离线表使用已验证的统一 3.5 GiB 额度。若进入自动缩容设计，需要处理两个额外条件。第一，GPUStack 降低模型总副本时可能先删除待调度实例，因此要用实际逐卡释放量确认缩容结果。第二，缩容和补首个实例之间要重新核对节点状态和维护归属，避免用已经失效的容量快照执行后续操作。本轮实现了只读缩容建议，并用离线用例验证建议、保护最后一个实例及禁止自动缩容。

## 2026-11-04 三个测试路由补验
