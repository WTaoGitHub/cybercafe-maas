# 同一调节器多模型联动实测

2026-11-13 · 工具已实现，真实执行待验收 · [Issue #39](https://github.com/WTaoGitHub/cybercafe-maas/issues/39)

新建独立A/B/C三个OCR部署，复用已验证镜像与3.5GiB原生申报，由同一试点调节器同时管理；不把三轮单模型测试当成多模型。另建不受调节器管制的容量占位部署D，只用于明确记录的运维资源占用/释放。原有模型、引擎、常驻API/E17及worker均保护，不做VM/worker/Docker/Server重启，不改网络或节点标签。

## 冻结预期

每个受管部署 min=1/max=3，初始 priority=1/weight=1；调节在途1、逐笔±1，共享单一journal。执行前根据两卡总量、保留与其他模型计算申报冻结容量，必须每卡还能容纳3个3.5GiB试点副本（合计6），否则停止而非临时改变门槛。

| 案例 | 操作与固定验收 |
| --- | --- |
| bootstrap_equal | 全0接管，Apply；前三笔依次让A/B/C从0到1，再补到2/2/2，6笔自动更新，无模型被额外副本饿死 |
| weight_change | 先2/2/2，改权重2:1:1；允许3/2/1或3/1/2的整数舍入，持续保持，无越过min/max或无谓反复调整 |
| priority_recovery | A/B/C仅允许同一卡，D占一格，只剩2格；priority1/2/3时先A1/B1，C仍0（从未启动，不是缩到0）；释放D后自动1/1/1，无新worker事件也能继续 |
| pending_contraction | 2/2/2 Ready基础上显式将三个目标都提高为3，制造真实资源不足Pending；每部署连续有效观察满180秒后收敛2/2/2，全部6个Ready ID保留，保持10秒不反弹 |
| minimum_pending | 从2/2/2暂停，将A运维降到1并用D占住释放格；规则min均改2，A指定3制造2个Pending。恢复后满180秒只将A降到指定2（Ready仍1），B/C各2不动；全部原5个Ready保留，允许1个Pending，保持10秒不降到下限以下 |
| pause_resume | 2/2/2暂停，运维改到1/1/1、权重2:1:1；至少8秒无自动动作，恢复按新权重返回允许的6副本分配 |

priority数字越小优先级越高，当前优先保障最低覆盖；剩余配额同时看weight、max和落点，不解释为高优先级可以占满所有资源。权重不是任意容量下严格比例承诺。本轮只有上述可独立计算的小规模期望，不宣称所有整数/约束组合都已验证。

## 工具与安全

`maas_platform/replica_multi_trial.py` 冻结六格小规模预期，提供三个明确模型ID的副本发送记录器；拒绝D/正式部署、归零、超过3、低于当前缩容下限及配置改写。每笔实际发送记录当前目标向量、请求、单调时间及对应Pending观察状态。`scripts/maas/replica_multi_live.py` 运行同一生产订阅/分页/对账/写入代码和独立OS子进程，隔离E17观测持久化，不争用正式SQL/采样锁。

临时容器设置PYTHONPATH=/app，独立私有目录700/文件600，restart=no。原生Pending安全缩容证明必须现场重新核验固定v2.2.3版本/评分代码与设置，不能套旧未知版本或跳过健康保护。进程/策略/模型状态和原始日志仅私有归档，优先Mac备份核SHA。每case结束暂停/自然停止试点调节器、确认journal空，才运维归零和恢复选择器；未知写入不自动重发、删除或重新接管。

异常最多两次有界诊断，仍不可继续立即停止；保留真实失败，不改判/拼接。正式模型配置/Ready/实例ID逐案例比较，结束检查OCR/唯一计量、日报、UNKNOWN、正式journal及常驻容器启动时间。仅验证策略与正确性，不优化Pending恢复耗时、冷缓存性能或千节点规模。
