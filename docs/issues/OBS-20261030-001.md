# OBS-20261030-001：共享文件写入锁竞争（仅观察）

日期：2026-10-30。来源：用户决定“记录下来，保持观察，暂时不考虑增强”。状态：MONITORING，潜在容量风险，尚未证明是当前实际瓶颈；不列入待开发增强，不赋予实施优先级，不改变现有排期。

## 现状与影响范围

上传和异步结果保存共用artifact目录的`.lifecycle.lock`，从文件写入、存储配额检查一直覆盖数据库事务提交。因此不同进程即使写入不同文件，这部分操作也会串行，其他写入者需要等待。模型推理仍可并行，普通下载不取得这把文件锁，但仍受数据库及磁盘资源影响。

GC修复已将合法文件批量核对移出写锁，并限制清理工作量；没有取消上传/结果写入之间的串行保护。`.gc-coordinator.lock`只协调一个清理进程，职责不同。本项属于#21关联的观察范围，不把它当作GC修复未完成或已证实的新故障。

## 当前决定

保留现有锁及其保护的文件/元数据一致性、并发存储配额、活动输入和删除安全。暂不缩小写入临界区、按项目分锁、设计配额预留/并发提交、改存储后端或实现其他并行写入增强；不能仅通过移除锁提高测试数字。尤其全局配额仍跨项目约束，不能假设项目分锁即可安全替换。

不新增代码、指标埋点、常驻监控、定时任务、压力测试或部署变更；“保持观察”指在后续已安排的运行/容量验证中留意相关现象，不另外开启周期自动化。

## 后续观察信号

- 上传耗时与模型已完成到结果提交的延迟，特别是P95/P99或随执行器数、文件大小、写入频率增长的变化。
- 推理尚有余量但结果提交排队、写入相关延迟与并发写入重叠的现象；同时核对数据库提交/锁等待、磁盘I/O及其他开销，不能只据相关性归因文件锁。
- 当前没有专用文件锁等待指标，不声称现有监控已能直接量化锁竞争。优先复用后续正常验证的现有日志与时序；若需新埋点、专项试验或短时诊断，另行评估范围，不由本记录自动开展。

只有取得可重复、可区分锁/数据库/磁盘影响的证据，并确认其显著影响目标吞吐或延迟，才重新向用户提出是否启动增强；本记录不自动转为实施授权。当前未开展新的锁性能实验，不给出瓶颈占比或提升预测。
